#### 5.1 교과목 목표

이 과목의 목표는 AI 서비스가 사용하는 데이터가 **정확하고, 추적 가능하며, 안전하게 관리되는지 검증하는 체계**를 이해하고 구현하는 것이다.

1단계에서는 AI 서비스와 데이터 플랫폼의 전체 아키텍처를 정의했다.  
2단계에서는 데이터를 수집하고 Raw Zone, Dead Letter, Data Contract 구조를 만들었다.  
3단계에서는 Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환하는 Airflow 파이프라인을 만들었다.  
4단계에서는 Kafka/Spark 기반 실시간 이벤트 처리와 WebSocket 대시보드 연결을 만들었다.

5단계에서는 지금까지 만든 데이터 흐름이 **정말 믿을 수 있는 데이터 흐름인지** 점검한다.

AI 서비스에서 데이터가 들어왔다고 해서 바로 믿을 수 있는 것은 아니다.  
필수값이 비어 있을 수 있고, 중복 데이터가 있을 수 있으며, 스키마가 바뀌었을 수 있고, 특정 센서의 데이터 분포가 갑자기 달라졌을 수 있다.  
또한 작업자 위치 데이터처럼 민감할 수 있는 데이터는 권한과 비식별화 기준도 필요하다.

따라서 이 과목에서는 다음을 학습한다.
```text
데이터 품질이란 무엇인가?
AI 서비스에서 데이터 품질은 왜 중요한가?
Data Contract와 Quality Rule은 어떻게 연결되는가?
Raw, Staging, Mart 데이터는 각각 어떤 품질 기준을 가져야 하는가?
dbt Test 또는 SQL Test로 무엇을 검증할 수 있는가?
Freshness 검사는 왜 필요한가?
Schema Compatibility는 왜 필요한가?
Data Lineage는 왜 필요한가?
Drift는 단순 오류와 무엇이 다른가?
작업자 위치 데이터는 왜 권한 관리와 의사익명화가 필요한가?
문서 데이터와 피드백 데이터에도 품질 기준이 필요한가?
품질 실패 결과는 어떻게 리포트와 운영 지표로 남겨야 하는가?
```

산업안전 관제플랫폼 실습에서는 센서 데이터, 전력 데이터, 작업자 위치 데이터, 알람 데이터, AI 추론 결과, RAG 문서 메타데이터, 사용자 피드백 데이터가 AI와 RAG에 사용되기 전에 품질 기준을 통과하도록 검증하고, 데이터 계보와 권한, 민감정보 관리 기준을 적용한다.

---
#### 5.2 이 과목의 위치

5단계는 4단계까지 만든 데이터 흐름을 검증하고, 추적하고, 관리하는 단계이다.
```text
1단계: 어떤 데이터를 다룰지와 전체 구조를 정의한다.
→ 2단계: 데이터를 수집하고 Raw Zone에 저장한다.
→ 3단계: Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환한다.
→ 4단계: 실시간 이벤트를 Kafka/Spark로 처리하고 Dashboard에 연결한다.
→ 5단계: 데이터 품질, 계보, 거버넌스 기준을 적용한다.
→ 6단계: 검증된 문서 데이터를 RAG 벡터 파이프라인으로 연결한다.
→ 7단계: 피드백 데이터와 운영 지표를 DataOps 구조로 연결한다.
```

5단계는 새로운 기능을 많이 추가하는 단계라기보다, 앞에서 만든 데이터 흐름을 신뢰할 수 있는 구조로 점검하는 단계이다.

즉, 5단계는 다음 질문에 답하는 단계이다.
```text
이 데이터는 믿을 수 있는가?
이 데이터는 어디서 와서 어디로 갔는가?
이 데이터는 누가 볼 수 있는가?
이 데이터는 AI와 RAG가 사용해도 안전한가?
```


#### 5.9 품질 기준 설계

데이터 품질은 단순히 “에러가 없는 데이터”를 의미하지 않는다.  
AI 서비스에서 데이터 품질은 다음 기준을 포함한다.

```text
완전성:
필수값이 빠지지 않았는가?

유일성:
중복 event_id가 없는가?

정확성:
값의 단위와 범위가 올바른가?

일관성:
schema_version과 필드 구조가 맞는가?

참조 무결성:
sensor_id, worker_id, zone_id가 기준정보와 연결되는가?

신선도:
최근 데이터가 정해진 시간 안에 들어오고 있는가?

시간 정합성:
event_time과 ingestion_time의 차이가 허용 범위 안인가?

보안성:
민감 데이터가 권한 없이 노출되지 않는가?

추적성:
특정 데이터가 어디서 와서 어디로 갔는지 확인 가능한가?
```

#### 5.12 SQL Test와 dbt Test의 차이

초보자는 처음부터 dbt 문법을 모두 외우기보다, SQL Test의 의미를 먼저 이해해야 한다.

| 구분 | SQL Test | dbt Test |
|---|---|---|
| 작성 방식 | 직접 SQL로 실패 조건 조회 | YAML 또는 SQL로 테스트 정의 |
| 장점 | 원리를 이해하기 쉽다 | 반복 실행과 문서화에 좋다 |
| 사용 시점 | 초보자 미니 실습 | 실제 프로젝트 구조화 |
| 예시 | `where event_id is null` | `not_null`, `unique` |
| 수업 적용 | 먼저 SQL로 확인 | 이후 dbt Test로 정리 |

##### SQL Test 예시
```sql
select *
from stg_gas_measurements
where event_id is null;
```

##### dbt Test 의미
```text
위 SQL처럼 실패 데이터를 찾는 규칙을 dbt 안에 등록해 반복 실행할 수 있게 만든다.
```

#### 5.13 Freshness와 Schema Compatibility

##### Freshness

Freshness는 데이터가 정해진 시간 안에 계속 들어오고 있는지 확인하는 검사이다.
```text
예시:
gas.sensor.raw 이벤트가 최근 5분 안에 들어왔는가?
worker.location.raw 이벤트가 최근 1분 안에 들어왔는가?
AI 추론 로그가 최근 10분 안에 들어왔는가?
```

Freshness가 중요한 이유는 다음과 같다.
```text
센서가 멈췄는지 확인할 수 있다.
Kafka Consumer가 멈췄는지 확인할 수 있다.
대시보드가 오래된 데이터를 보여주는지 확인할 수 있다.
AI가 현재 상황이 아닌 과거 데이터를 보고 판단하는 문제를 막을 수 있다.
```

##### Schema Compatibility

Schema Compatibility는 데이터 구조가 바뀌었을 때 기존 파이프라인이 깨지지 않는지 확인하는 기준이다.
```text
허용 가능한 변경:
선택 필드 추가
새 schema_version 추가
enum 값 추가 시 처리 정책 명시

주의가 필요한 변경:
필수 필드 삭제
필드 타입 변경
단위 변경
event_time 의미 변경
```

#### 5.15 Drift 탐지 기준

Drift는 데이터의 분포나 의미가 시간이 지나면서 바뀌는 현상이다.  
단순히 값 하나가 잘못 들어온 오류와 다르다.

##### Data Drift 예시
```text
특정 가스 센서의 평균값이 평소보다 계속 높아지는 경우
특정 센서만 이벤트 수가 급격히 줄어드는 경우
전력 사용량 패턴이 이전 주와 달라지는 경우
작업자 위치 이벤트가 특정 구역에 과도하게 몰리는 경우
```

##### Schema Drift 예시
```text
새로운 필드가 갑자기 추가되는 경우
기존 필드의 타입이 문자열에서 숫자로 바뀌는 경우
gas_type enum에 새로운 값이 추가되는 경우
schema_version 없이 payload 구조가 바뀌는 경우
```

##### AI/RAG 운영 Drift 예시
```text
특정 알람 유형의 오탐 비율이 증가하는 경우
AI 추론 실패율이 특정 시간대에 증가하는 경우
RAG 검색 실패율이 증가하는 경우
문서 최신성이 오래되어 부정확한 매뉴얼이 반복 검색되는 경우
사용자 피드백에서 '도움 안 됨' 비율이 증가하는 경우
```

#### 5.16 PII와 거버넌스 기준

산업안전 관제플랫폼에는 작업자 위치와 알람 처리 이력이 포함된다.  
이 데이터는 개인 또는 근무 이력과 연결될 수 있으므로 접근 권한과 비식별화 기준이 필요하다.

##### 민감할 수 있는 데이터
```text
worker_id
worker_name
worker_location
zone_entry_time
alarm_acknowledged_by
feedback_user_id
operator_comment
```

##### 권장 처리 기준
```text
작업자 실명과 위치 이벤트를 분리한다.
분석용 데이터에는 pseudonymous_worker_id를 사용한다.
운영자 화면과 분석용 Mart의 접근 권한을 구분한다.
RAG 문서에는 access_level을 부여한다.
피드백 comment에는 불필요한 개인정보를 남기지 않는다.
API Key, DB Password, Webhook URL은 코드에 직접 작성하지 않는다.
```

##### Access Control Matrix 예시

| 역할 | 볼 수 있는 데이터 | 제한되는 데이터 |
|---|---|---|
| 관리자 | 전체 알람, 품질 리포트, 운영 지표 | Secret 값 직접 조회 제한 |
| 현장 운영자 | 담당 구역 알람, 작업자 현재 상태 | 전체 작업자 이력 다운로드 제한 |
| 데이터 분석가 | 익명화된 Mart, 품질 결과, Drift 결과 | 실명, 연락처, 민감 코멘트 |
| 강사/학생 | 수업용 샘플 데이터, 익명화 데이터 | 실제 개인정보, 실제 현장 정보 |
| 외부 API | 허용된 문서와 응답 결과 | 내부 품질 리포트, 원본 피드백 |

#### 5.20 데이터 엔지니어링 디자인 패턴 적용

5단계에서는 데이터 품질, 데이터 보안, 데이터 관찰 가능성 패턴을 중심으로 적용한다.  
패턴을 암기하는 것이 목적이 아니라, “AI가 사용하는 데이터가 신뢰 가능한지 어떻게 확인할 것인가”를 설계하는 것이 목적이다.

| 패턴 영역 | 적용 패턴 | 5단계 적용 방식 |
|---|---|---|
| 데이터 품질 | 감사-쓰기-감사-배포(AWAP) | Raw 수집 후 감사, Staging 쓰기 후 감사, Mart 배포 전 감사 |
| 데이터 품질 | 제약 조건 적용자 | 필수값, 범위, 중복, 참조 무결성 검증 |
| 데이터 품질 | 스키마 호환성 적용자 | schema_version 기준으로 스키마 변경 관리 |
| 데이터 품질 | 스키마 마이그레이터 | 필드 추가 또는 타입 변경 시 전환 정책 정의 |
| 데이터 품질 | 오프라인 옵서버 | 일별 데이터 품질 리포트 생성 |
| 데이터 품질 | 온라인 옵서버 | 실시간 품질 실패율 모니터링 기준 정의 |
| 데이터 보안 | 테이블에 대한 세밀한 접근자 | workers, feedback_logs 접근 권한 분리 |
| 데이터 보안 | 자원에 대한 세밀한 접근자 | 구역별 알람과 문서 접근 제한 |
| 데이터 보안 | 의사 익명화기 | worker_id를 분석용 ID로 변환 |
| 데이터 보안 | 비밀 포인터 | DB Password, API Key를 Secret으로 관리 |
| 데이터 관찰 가능성 | 데이터셋 추적기 | Raw에서 Mart까지 데이터 이동 경로 추적 |
| 데이터 관찰 가능성 | 세밀한 추적기 | 특정 event_id가 어떤 처리 단계를 거쳤는지 추적 |
| 데이터 관찰 가능성 | 지연 탐지기 | event_time과 ingestion_time 차이 관찰 |
| 데이터 관찰 가능성 | 흐름 중단 탐지기 | 일정 시간 이벤트가 들어오지 않는 상태 탐지 |

#### 5.23 5단계에서 하지 않는 것

5단계는 데이터 품질, 계보, 거버넌스 기준을 만드는 단계이다.  
다음 작업은 이후 단계에서 다룬다.
```text
RAG 문서 Chunking과 Embedding 전체 구현하지 않기
Vector DB 검색 API 완성하지 않기
RAG 답변 생성 기능 완성하지 않기
피드백 API 전체 구현하지 않기
재학습 후보 데이터셋 자동 생성 완성하지 않기
Prometheus/Grafana 운영 대시보드 전체 완성하지 않기
Docker Compose 전체 운영 통합 완성하지 않기
Kubernetes 배포까지 확장하지 않기
```

단, 6단계와 7단계로 연결될 수 있도록 다음 기준은 미리 만든다.
```text
RAG 문서 메타데이터 품질 기준
document_id, version, access_level, checksum 기준
문서 freshness 기준
피드백 데이터 품질 기준
AI/RAG 운영 로그 품질 기준
DataOps 모니터링으로 넘길 품질 Metric 기준
```

```text
5단계 품질 결과가 6단계 RAG 파이프라인과 7단계 DataOps 운영으로 어떻게 연결되는가?
```

#### 5.25 6단계와의 연결

5단계의 결과물은 6단계의 입력이 된다.
```text
5단계 결과물
- 데이터 품질 기준
- dbt Test / SQL Test
- 품질 실패 결과
- Data Lineage 문서
- Drift 탐지 기준
- PII 정책
- Access Control Matrix
- RAG 문서 데이터 품질 Gate

6단계에서 할 일
- 품질 기준을 통과한 문서를 RAG 파이프라인 입력으로 사용한다.
- document_id, version, access_level, checksum을 기준으로 문서를 관리한다.
- 문서 Chunking과 Embedding 전에 원본 문서의 최신성과 권한을 확인한다.
- RAG 검색 결과에 출처와 문서 버전을 표시한다.
- RAG 검색 로그와 피드백은 7단계 DataOps 운영 데이터로 연결한다.
```

따라서 5단계의 핵심은 다음 한 문장으로 정리할 수 있다.
```text
5단계는 AI와 RAG가 사용할 데이터를 그냥 믿는 것이 아니라,
품질 기준으로 검증하고,
계보로 추적하고,
권한과 보안 기준으로 관리하여
운영 가능한 데이터 플랫폼으로 만드는 단계이다.
```
