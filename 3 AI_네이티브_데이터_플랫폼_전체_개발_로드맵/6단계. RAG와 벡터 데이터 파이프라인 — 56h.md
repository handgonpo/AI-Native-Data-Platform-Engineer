#### 6.1 교과목 목표

이 과목의 목표는 산업안전 문서와 비정형 데이터를 **RAG 서비스가 검색하고 활용할 수 있는 벡터 데이터 파이프라인으로 변환하는 구조**를 이해하고 구현하는 것이다.

1단계에서는 AI 서비스와 데이터 플랫폼의 전체 아키텍처를 정의했다.  
2단계에서는 센서, 전력, 작업자 위치, 로그, 피드백 데이터를 수집하고 Raw Zone에 저장했다.  
3단계에서는 Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환하는 Airflow 파이프라인을 만들었다.  
4단계에서는 Kafka/Spark 기반 실시간 이벤트 처리와 WebSocket 대시보드 연결을 만들었다.  
5단계에서는 AI와 RAG가 사용할 데이터의 품질, 계보, 거버넌스 기준을 만들었다.

6단계에서는 5단계에서 정의한 문서 품질 기준을 바탕으로, 산업안전 대응 매뉴얼과 임계치 정의서 같은 문서를 RAG 검색이 가능한 구조로 변환한다.

RAG는 단순히 문서를 임베딩해서 Vector DB에 넣는 기능이 아니다.  
신뢰 가능한 RAG 서비스를 만들려면 문서 원본, 문서 버전, 문서 권한, Chunk, Metadata, Embedding, Vector DB, 검색 API, 출처 표시, 문서 최신성, 검색 로그, 사용자 피드백까지 함께 설계해야 한다.

따라서 이 과목에서는 다음을 학습한다.
```text
RAG란 무엇인가?
RAG는 일반 검색과 무엇이 다른가?
문서 데이터는 센서 이벤트 데이터와 무엇이 다른가?
문서 원본은 어떻게 저장하고 관리해야 하는가?
문서 메타데이터는 왜 필요한가?
Chunking은 왜 필요한가?
Chunk size와 overlap은 검색 품질에 어떤 영향을 주는가?
Embedding은 무엇이며 왜 필요한가?
Vector DB는 어떤 역할을 하는가?
Keyword Search와 Vector Search는 무엇이 다른가?
Hybrid Search는 왜 필요한가?
Metadata Filter는 왜 중요한가?
RAG 답변에는 왜 출처가 표시되어야 하는가?
문서 최신성, 버전, 권한은 어떻게 관리해야 하는가?
RAG 검색 로그와 피드백은 7단계 DataOps와 어떻게 연결되는가?
```

산업안전 관제플랫폼 실습에서는 가스별 임계치 정의서, 유해가스 대응 매뉴얼, 장비 문서, 산업안전 절차서, 현장 운영자 매뉴얼을 수집하고, Chunking, Metadata 부여, Embedding 생성, Vector DB 저장, RAG 검색 API, 출처 표시 응답, 알람-RAG 연결 구조를 구현한다.

#### 6.2 이 과목의 위치

6단계는 5단계에서 정의한 문서 품질 기준을 통과한 문서를 RAG용 벡터 데이터로 변환하는 단계이다.
```text
1단계: 어떤 데이터를 다룰지와 전체 구조를 정의한다.
→ 2단계: 데이터를 수집하고 Raw Zone에 저장한다.
→ 3단계: Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환한다.
→ 4단계: 실시간 이벤트를 Kafka/Spark로 처리하고 Dashboard에 연결한다.
→ 5단계: 데이터 품질, 계보, 거버넌스 기준을 적용한다.
→ 6단계: 산업안전 문서를 RAG 벡터 데이터 파이프라인으로 변환한다.
→ 7단계: RAG 검색 로그와 피드백을 DataOps 운영 데이터로 연결한다.
```

6단계는 단순 챗봇을 만드는 단계가 아니다.  
문서 데이터를 AI 서비스가 사용할 수 있는 **검색 가능한 데이터셋**으로 바꾸는 단계이다.

즉, 6단계는 다음 질문에 답하는 단계이다.
```text
이 문서는 어디서 왔는가?
이 문서는 최신인가?
이 문서는 누가 볼 수 있는가?
이 문서는 어떤 알람과 연결되는가?
이 문서의 어느 부분이 검색되었는가?
RAG 답변의 출처를 추적할 수 있는가?
```

#### 6.3 핵심 질문

```text
산업안전 문서를 AI 서비스가 신뢰할 수 있게 검색하려면,
문서를 어떻게 수집하고,
어떻게 나누고,
어떤 메타데이터를 붙이고,
어떻게 벡터화하고,

```

이 질문을 다음 관점으로 나누어 이해한다.
```text
문서 수집 관점:
문서 원본은 어디서 오고, 어떤 형식으로 저장되는가?

문서 품질 관점:
문서 버전, 최신성, 출처, 권한은 어떻게 확인하는가?

Chunking 관점:
문서를 어떤 기준으로 나누어야 검색 품질이 좋아지는가?

Metadata 관점:
문서 조각에 어떤 정보를 붙여야 알람 상황에 맞게 검색할 수 있는가?

Embedding 관점:
문장과 문서를 숫자 벡터로 바꾸는 이유는 무엇인가?

Vector DB 관점:
벡터 검색을 위해 어떤 저장소를 사용할 수 있는가?

검색 관점:
Keyword Search, Vector Search, Hybrid Search는 각각 언제 필요한가?

RAG 응답 관점:
답변에 출처, 문서명, 페이지, 섹션을 어떻게 표시할 것인가?

서비스 연결 관점:
알람 발생 시 관련 매뉴얼을 어떻게 자동으로 검색할 것인가?

운영 관점:
RAG 검색 실패, 부정확한 답변, 사용자 피드백은 어떻게 기록할 것인가?
```

#### 6.6 수업 운영 방식

6단계는 총 56시간이며, 7일 × 8시간 구조로 운영한다.
```text
하루 8시간
= 범용 이론 3시간
+ 미니 실습과 질문 답변
+ 산업안전 관제플랫폼 응용 실습 5시간
```

수업 순서는 다음을 기준으로 한다.
```text
범용 이론 설명
→ 간단한 미니 실습
→ 이해도 점검 질문
→ 산업안전 관제플랫폼 응용 실습
→ 코드/데이터/문서 산출물 정리
```

6단계는 처음부터 완성형 LLM 챗봇을 만드는 것이 목적이 아니다.  
초보자가 먼저 이해해야 할 것은 **문서 원본이 어떤 과정을 거쳐 검색 가능한 벡터 데이터가 되는가**이다.

따라서 수업은 다음 순서로 진행한다.
```text
작은 문서로 Chunking 실습
→ Metadata 붙이기
→ Embedding 생성
→ Vector DB 저장
→ 검색 결과 확인
→ 산업안전 매뉴얼에 적용
→ 알람과 RAG 검색 연결
→ 검색 품질과 출처 점검
```

#### 6.9 Document Metadata 설계

Document Metadata는 문서 원본을 추적하기 위한 정보이다.  
RAG 검색 결과를 신뢰하려면, 검색된 Chunk가 어떤 문서에서 왔는지 확인할 수 있어야 한다.

##### Document Metadata 필드
```text
document_id
source_doc
document_type
title
version
published_at
ingested_at
owner
access_level
language
file_path
file_type
checksum
freshness_status
status
```

##### 필드 설명

| 필드 | 의미 |
|---|---|
| `document_id` | 문서를 식별하는 고유 ID |
| `source_doc` | 원본 문서명 |
| `document_type` | 임계치 정의서, 대응 매뉴얼, 장비 문서 등 |
| `version` | 문서 버전 |
| `published_at` | 문서 발행일 |
| `ingested_at` | RAG 파이프라인에 등록된 시각 |
| `owner` | 문서 담당자 또는 담당 조직 |
| `access_level` | 공개, 내부, 관리자 전용 등 접근 권한 |
| `checksum` | 문서 내용 변경 여부 확인용 해시 |
| `freshness_status` | 최신, 오래됨, 검토 필요 상태 |

#### 6.10 Chunk Metadata 설계

Chunk Metadata는 문서 조각을 검색할 때 필요한 정보이다.  
RAG 검색은 보통 문서 전체가 아니라 Chunk 단위로 이루어진다.

##### Chunk Metadata 필드
```text
chunk_id
document_id
source_doc
document_type
page_no
section_title
chunk_index
chunk_text
gas_type
risk_type
risk_level
equipment_type
zone_type
procedure_type
access_level
version
published_at
ingested_at
checksum
freshness_status
```

##### Chunk Metadata가 필요한 이유
```text
검색 결과의 출처를 표시하기 위해
알람 유형에 맞는 문서만 검색하기 위해
권한이 없는 문서를 제외하기 위해
오래된 문서가 우선 검색되지 않게 하기 위해
같은 문서의 중복 Chunk를 구분하기 위해
문서 변경 시 어떤 Chunk를 다시 임베딩해야 하는지 확인하기 위해
```

#### 6.12 RAG 처리 흐름

6단계의 전체 처리 흐름은 다음과 같다.
```text

        ↓
Document Metadata 생성
        ↓
문서 원본 저장
        ↓
Text Extraction
        ↓
Chunking
        ↓
Chunk Metadata 생성
        ↓
Embedding 생성
        ↓
Vector DB 저장
        ↓
검색 API 구성
        ↓
알람 유형 기반 Metadata Filter 적용
        ↓
RAG 답변 생성
        ↓
출처 표시
        ↓
RAG Query Log 저장
```

##### 산업안전 알람과 RAG 연결 예시
```text

        ↓

risk_level = danger
zone_id = A_ZONE
        ↓
RAG API에 관련 매뉴얼 검색 요청
        ↓
metadata filter:
gas_type = CO
risk_level = danger
access_level <= operator
        ↓
대시보드 알람 상세에 대응 매뉴얼 표시
```

##### 예시 응답
```text
[위험] CO 230ppm / A구역 / 작업자 W-001

권장 대응:
1. 작업자 즉시 대피
2. 환기 장치 가동
3. 전원 차단 여부 확인
4. 현장 관리자에게 알림

출처:
- 가스별 임계치 정의서, p.3
- 유해가스 대응 매뉴얼, section 2.1
```

#### 6.13 Chunking 전략

Chunking은 문서를 검색 가능한 작은 단위로 나누는 작업이다.  
Chunk가 너무 크면 검색 결과가 넓고 부정확해질 수 있고, 너무 작으면 문맥이 끊길 수 있다.

##### Chunking 기준
```text
문단 기준 분할
제목/소제목 기준 분할
페이지 기준 보조 정보 유지
chunk_size 기준 분할
overlap 기준 문맥 유지
표와 목록은 의미가 끊기지 않도록 보존
```

##### 권장 초안
```text
chunk_size:
500~800자 또는 300~500 token 수준

overlap:
50~100자 또는 50 token 수준

metadata:
document_id, page_no, section_title, risk_type, gas_type 포함
```

##### 초보자가 기억할 기준
```text
Chunking의 목적은 문서를 작게 자르는 것이 아니라,
검색했을 때 질문에 맞는 의미 단위가 잘 찾아지도록 나누는 것이다.
```

#### 6.14 Embedding과 Vector DB

Embedding은 문장이나 문서를 숫자 벡터로 바꾸는 작업이다.  
Vector DB는 이 벡터를 저장하고, 질문과 의미가 비슷한 문서 조각을 찾는 저장소이다.

##### Embedding 흐름
```text
chunk_text
        ↓
embedding model
        ↓
embedding vector
        ↓
vector store
        ↓
similarity search
```

##### Vector DB 선택 기준

| 저장소 | 장점 | 수업 적용 |
|---|---|---|
| Chroma | 설치와 실습이 비교적 쉬움 | 초보자 로컬 실습에 적합 |
| FAISS | 빠른 벡터 검색, 파일 기반 실습 가능 | 검색 원리 이해에 적합 |
| pgvector | PostgreSQL 안에서 벡터 검색 가능 | 서비스 DB와 통합 구조 설명에 적합 |

수업에서는 하나를 필수로 선택하고, 나머지는 비교 개념으로 설명한다.  
초보자 실습에서는 Chroma 또는 FAISS로 시작하고, PostgreSQL과 통합 관점에서는 pgvector를 설명할 수 있다.

#### 6.15 검색 방식 설계

RAG 검색은 Vector Search만으로 충분하지 않을 수 있다.  
산업안전 문서에서는 정확한 키워드도 중요하고, 의미 기반 검색도 중요하다.

##### Keyword Search

Keyword Search는 특정 단어가 포함된 문서를 찾는 방식이다.
```text
예시:
CO
H2S
환기
대피
전원 차단
```

##### Vector Search

Vector Search는 질문과 의미가 비슷한 문서 조각을 찾는 방식이다.
```text
예시 질문:
CO 수치가 높을 때 어떻게 대응해야 하나요?
```

##### Hybrid Search

Hybrid Search는 Keyword Search와 Vector Search를 함께 사용하는 방식이다.
```text
예시:
gas_type = CO Metadata Filter
+ "대피" Keyword
+ Vector Search Similarity
```

##### Metadata Filter

Metadata Filter는 검색 대상을 좁히기 위해 사용한다.
```text
gas_type = CO
risk_level = danger
document_type = safety_manual
access_level <= operator
freshness_status = current
```

| 데이터 가치 | 메타데이터 데코레이터 | Chunk에 gas_type, risk_level, source_doc, page_no 추가 |
| 데이터 가치 | 정적 조이너 | 알람 risk_type과 문서 metadata를 조인해 관련 문서 검색 |
| 데이터 가치 | 래퍼 | 원본 문서를 RAG가 사용할 수 있는 Chunk 단위 데이터로 변환 |
| 데이터 스토리지 | 메타데이터 강화기 | 검색 품질 향상을 위해 풍부한 metadata 추가 |
| 데이터 스토리지 | 매니페스트 | 문서 목록, 버전, checksum, 임베딩 생성 상태 관리 |
| 데이터 스토리지 | 버킷 | 문서 유형, 위험 유형, 접근 권한별 저장 구조 분리 |
| 데이터 품질 | 스키마 호환성 적용자 | document metadata schema 변경 관리 |
| 데이터 품질 | 오프라인 옵서버 | 검색 품질 평가 리포트 생성 |
| 데이터 보안 | 자원에 대한 세밀한 접근자 | access_level 기준 문서 검색 제한 |
| 데이터 관찰 가능성 | 데이터셋 추적기 | raw document에서 vector index까지 문서 계보 추적 |

#### 6.23 6단계에서 하지 않는 것

6단계는 RAG와 벡터 데이터 파이프라인을 만드는 단계이다.  
다음 작업은 이후 단계 또는 프로젝트 단계에서 다룬다.
```text
완성형 챗봇 UI를 깊게 만들지 않기
복잡한 LLM 프롬프트 엔지니어링에 과도하게 집중하지 않기
모든 문서를 자동으로 완벽하게 파싱하려고 하지 않기
RAG 피드백 대시보드 전체 구현하지 않기
재학습 후보 데이터셋 자동 생성 완성하지 않기
Prometheus/Grafana 운영 대시보드 전체 완성하지 않기
문서 권한 관리 시스템을 실제 운영 수준으로 완성하지 않기
Kubernetes 배포까지 확장하지 않기
```

단, 7단계와 연결될 수 있도록 다음 기준은 미리 만든다.
```text
RAG Query Log 구조
RAG Feedback 구조
검색 실패 케이스 분류 기준
출처 누락 응답 기준
검색 latency 기준
RAG 부정 피드백 집계 기준
```

#### 6.25 7단계와의 연결

6단계의 결과물은 7단계의 입력이 된다.
```text
6단계 결과물
- 문서 원본
- Document Metadata
- Chunk Metadata
- Embedding
- Vector DB
- RAG Search API
- 출처 포함 응답
- RAG Query Log
- 검색 품질 리포트
- 검색 실패 케이스

7단계에서 할 일
- RAG 답변 피드백을 수집한다.
- 도움이 되지 않은 답변을 실패 케이스로 분류한다.
- 출처 없는 답변과 낮은 검색 품질을 모니터링한다.
- 반복 질문과 재질문을 운영 지표로 만든다.
- RAG 부정 피드백을 문서 개선 후보와 재학습 후보 데이터로 전환한다.
```

따라서 6단계의 핵심은 다음 한 문장으로 정리할 수 있다.
```text
6단계는 문서를 단순 파일로 보관하는 것이 아니라,
AI 서비스가 검색하고 근거로 사용할 수 있도록
문서 원본, Chunk, Metadata, Embedding, Vector DB, 출처, 검색 로그까지
하나의 데이터 파이프라인으로 만드는 단계이다.
```
