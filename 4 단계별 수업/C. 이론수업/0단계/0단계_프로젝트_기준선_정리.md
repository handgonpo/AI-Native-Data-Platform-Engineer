
> 과정명: AI 네이티브 데이터 플랫폼 엔지니어 과정  
> 문서 목적: 이 과정에서 본격적인 개발 전에 프로젝트의 목적, 범위, 데이터, 구조, 용어, 산출물 기준을 스스로 정리할 수 있도록 돕는 0단계 이론 및 실습 자료  
> 적용 방식: 범용 이론 설명 → 범용 데이터 예제 실습 → 개인/팀 프로젝트 기준선 작성 → 이후 산업안전 관제플랫폼 실습에 적용  
> 주의: 이 문서는 산업안전 관제플랫폼의 상세 구현 문서가 아니다. 산업안전 관제플랫폼을 풀기 전에 필요한 범용 프로젝트 기준선 정리 방법을 배우기 위한 문서이다.

---

## 0. 이 문서의 결론

프로젝트 기준선 정리는 개발을 시작하기 전에 다음 질문에 답하는 작업이다.
```text
이 프로젝트는 무엇을 해결하려는가?
누가 사용하는가?
어떤 데이터가 발생하는가?
그 데이터는 어디로 들어오는가?
원본 데이터와 검증 데이터는 어떻게 나누는가?
AI, RAG, 대시보드, 피드백은 어떤 데이터를 사용하는가?
이번 수업 또는 프로젝트에서 만들 범위는 어디까지인가?
어떤 문서, 코드, 샘플 데이터, 브랜치를 남겨야 하는가?
```

기준선은 영어로 **Baseline**이라고 부른다.  
쉽게 말하면 다음과 같다.
```text
앞으로 프로젝트를 개발할 때 흔들리지 않도록 미리 정해두는 출발 기준
```

주니어는 프로젝트를 시작하면 보통 코드를 먼저 작성하려고 한다.
```text
models.py부터 만들면 되나?
화면부터 만들면 되나?
API부터 만들면 되나?
DB 테이블부터 만들면 되나?
Docker부터 붙이면 되나?
AI 모델부터 붙이면 되나?
```

하지만 AI 네이티브 데이터 플랫폼 프로젝트에서는 바로 코드를 작성하면 구조가 쉽게 무너진다.  
왜냐하면 이 과정은 단순 웹 기능을 만드는 과정이 아니라, 데이터가 발생하고, 수집되고, 검증되고, 저장되고, AI와 RAG와 운영 피드백으로 연결되는 전체 흐름을 만드는 과정이기 때문이다.

따라서 0단계의 핵심은 다음 한 문장으로 정리할 수 있다.
```text
0단계는 코드를 쓰기 전에 프로젝트의 기준 언어와 기준 구조를 맞추는 단계이다.
```

## 1. 0단계의 목표

0단계의 목표는 다음을 스스로 정리할 수 있게 하는 것이다.
```text
프로젝트 목적
문제 정의
도메인 정의
사용자 역할
업무 흐름
데이터 소스
데이터 유형
도메인 이벤트
데이터 흐름
시스템 경계
용어와 네이밍 컨벤션
폴더 구조
브랜치 전략
최종 시연 기준
산출물 기준
완료 체크리스트
```

0단계가 끝나면 다음 질문에 답할 수 있어야 한다.
```text
내 프로젝트는 어떤 문제를 해결하는가?
내 프로젝트의 주요 사용자는 누구인가?
내 프로젝트에서 발생하는 데이터는 무엇인가?
그 데이터는 API, 파일, 로그, 이벤트, 문서 중 어떤 방식으로 들어오는가?
Raw, Staging, Mart로 나누어야 하는 데이터는 무엇인가?
AI 학습 데이터, 추론 데이터, RAG 데이터, 피드백 데이터는 각각 무엇인가?
내가 만들 시스템과 만들지 않을 시스템의 경계는 어디인가?
폴더명, 파일명, 테이블명, 이벤트명은 어떤 규칙으로 만들 것인가?
최종적으로 무엇을 보여주면 프로젝트가 완성되었다고 말할 수 있는가?
```

## 2. 0단계에서 중요한 관점

0단계는 산업안전 관제플랫폼을 바로 분석하는 시간이 아니다.  
먼저 모든 데이터 프로젝트에 공통으로 적용되는 기준선 정리 방법을 배운다.

그 다음에 같은 질문을 산업안전 관제플랫폼에 적용한다.

수업 흐름은 다음과 같다.
```text
범용 개념 이해
→ 범용 데이터 예제 분석
→ 내 프로젝트 기준선 작성
→ 산업안전 관제플랫폼에 같은 방식으로 적용
```

이 순서가 중요한 이유는 다음과 같다.
```text
산업안전 도메인만 외우면 다른 프로젝트에 적용하기 어렵다.
기준선 정리 방법을 배우면 쇼핑몰, 교육, 금융, 제조, 헬스케어, 산업안전 프로젝트에 모두 적용할 수 있다.
취업 포트폴리오에서는 특정 도메인보다 “프로젝트를 구조화하는 능력”이 중요하다.
```

## 4. 0단계에서 하는 일

0단계에서는 다음을 작성한다.
```text
프로젝트 개요
문제 정의
도메인 정의
사용자 역할
데이터 소스
데이터 유형
도메인 이벤트 후보
Raw / Staging / Mart 기준
시스템 경계
네이밍 컨벤션
폴더 구조
브랜치 전략
최종 시연 시나리오
완료 체크리스트
```

0단계에서는 아래와 같은 기능은 이후에 구현한다.
```text
models.py 작성하지 않기
migration 하지 않기
실제 DB 테이블 만들지 않기
Collector API 구현하지 않기
Sensor Simulator 구현하지 않기
Airflow DAG 작성하지 않기
Kafka Producer/Consumer 작성하지 않기
RAG 임베딩 생성하지 않기
AI 모델 학습하지 않기
Docker/Kubernetes 붙이지 않기
Prometheus/Grafana 설정하지 않기
```

0단계에서 코드를 전혀 쓰지 말라는 뜻은 아니다.  
다만 코드는 “기능 구현”이 아니라 “기준선 이해를 위한 작은 예제” 수준으로만 사용한다.

예를 들어 0단계에서 가능한 실습은 다음과 같다.
```text
샘플 JSON 작성
도메인 이벤트 이름 정하기
폴더 구조 만들기
README 초안 작성
Mermaid로 데이터 흐름도 작성
Markdown 표로 데이터 소스 정리
```

## 5. 왜 기준선 문서를 먼저 작성해야 하는가?

문서 없이 개발하면 생기는 문제
```text
팀원마다 프로젝트 목적을 다르게 이해한다.
같은 데이터를 서로 다른 이름으로 부른다.
DB 테이블 이름과 API 이름이 제각각이 된다.
Raw 데이터와 검증된 데이터가 섞인다.
대시보드가 원본 데이터를 직접 조회한다.
AI 학습 데이터셋을 나중에 만들 수 없다.
RAG 문서와 일반 첨부파일이 구분되지 않는다.
피드백 데이터가 단순 메모로 남아 개선 데이터가 되지 못한다.
브랜치 이름이 뒤죽박죽이 되어 어느 단계인지 헷갈린다.
```

기준선 문서가 있으면 좋은 점
```text
프로젝트 목표가 고정된다.
팀원들이 같은 용어를 사용한다.
데이터 흐름이 먼저 보인다.
기능 구현 순서가 명확해진다.
브랜치와 산출물 기준이 정리된다.
팀원들이 어느 단계까지 완성했는지 확인할 수 있다.
나중에 포트폴리오 설명 문장으로 바로 사용할 수 있다.
```


==`[참고]`==
취업 목적 과정에서 중요한 것은 “코드를 많이 썼다”가 아니다.  
면접관이 궁금해하는 것은 다음이다.
```text
이 사람은 왜 이 구조를 만들었는가?
데이터가 어디서 들어와 어디로 가는지 설명할 수 있는가?
원본 데이터와 분석용 데이터를 구분할 수 있는가?
오류 데이터와 중복 데이터 처리를 고려했는가?
AI가 사용하는 데이터와 서비스 로그를 구분할 수 있는가?
프로젝트 산출물이 문서와 코드로 정리되어 있는가?
```

따라서 0단계 기준선 문서는 포트폴리오의 출발점이다.

## 6. 핵심 용어 상세 설명

##### 1. 프로젝트: 프로젝트는 특정 문제를 해결하기 위해 일정 기간 동안 만드는 결과물이다.

예를 들어 다음은 모두 프로젝트가 될 수 있다.
```text
쇼핑몰 주문 데이터 분석 플랫폼
교육 LMS 학습 부진 탐지 시스템
제조 설비 이상탐지 플랫폼
부동산 허위매물 탐지 시스템
산업안전 관제 데이터 플랫폼
```

프로젝트는 단순히 코드 폴더가 아니다.  
프로젝트에는 목적, 사용자, 데이터, 기능, 일정, 산출물, 평가 기준이 함께 포함된다.

##### 2. 도메인: 도메인은 프로젝트가 다루는 업무 세계이다.
예를 들어 쇼핑몰 프로젝트에서 도메인은 `쇼핑몰` 또는 `전자상거래`이다. 
그 안에 들어가는 기능은 `상품 조회`, `장바구니 담기`, `주문하기`, `결제하기`, `리뷰 작성하기`이다
즉, 도메인이 더 큰 범위이고, 기능은 도메인 안에 포함되는 동작이다.

예를 들어 다음과 같이 생각할 수 있다.

| 프로젝트 예시       | 도메인          |
| ------------- | ------------ |
| 쇼핑몰 주문 분석 시스템 | 전자상거래 / 쇼핑몰  |
| 학습 부진 탐지 시스템  | 교육 / LMS     |
| 설비 이상탐지 시스템   | 제조 / 설비 관리   |
| 이상거래 탐지 시스템   | 금융 / 거래 관리   |
| 병원 예약 관리 시스템  | 헬스케어 / 병원 예약 |
| 산업안전 관제플랫폼    | 산업안전 / 현장 관제 |

쇼핑몰 도메인 안에 포함되는 요소:
```text
상품
주문
결제
배송
장바구니
리뷰
쿠폰
고객 문의
```

교육 도메인 안에 포함되는 요소:
```text
수강생
강사
강의
출석
과제
퀴즈
학습 시간
질문
피드백
```

제조 도메인 안에 포함되는 요소:
```text
설비
공정
센서
온도
진동
전력
불량률
작업자
점검 이력
```

도메인을 정리한다는 것은 “이 프로젝트에서 어떤 업무 세계를 다루는지”를 정리하는 것이다.

##### 3. 도메인 요소:  도메인 요소는 프로젝트 안에 등장하는 핵심 대상이다.
| 도메인  | 도메인 요소 예시                |
| ---- | ------------------------ |
| 쇼핑몰  | 고객, 상품, 주문, 결제, 배송, 리뷰   |
| 교육   | 수강생, 강사, 강의, 과제, 퀴즈, 질문  |
| 제조   | 설비, 센서, 공정, 불량, 점검, 작업자  |
| 금융   | 고객, 계좌, 거래, 카드, 이상거래, 상담 |
| 헬스케어 | 사용자, 측정값, 활동량, 문진, 리포트   |
| 산업안전 | 센서, 전력장비, 작업자, 위험구역, 알람  |
도메인 요소는 나중에 데이터 모델, 이벤트, API, 테이블 이름의 기준이 된다.

##### 4 사용자 역할: 사용자 역할은 시스템을 사용하는 사람 또는 시스템의 책임 단위이다.

예를 들어 쇼핑몰에서는 다음 역할이 있다.
```text
고객
판매자
관리자
배송 담당자
CS 담당자
결제 시스템
```

교육 시스템에서는 다음 역할이 있다.
```text
수강생
강사
운영 매니저
관리자
자동 채점 시스템
```

사용자 역할을 정리해야 하는 이유는 다음과 같다.
```text
누가 어떤 데이터를 생성하는지 알 수 있다.
누가 어떤 화면을 봐야 하는지 알 수 있다.
누가 어떤 데이터를 수정할 수 있는지 알 수 있다.
나중에 권한과 보안 기준을 만들 수 있다.
```

##### 5 업무 흐름: 업무 흐름은 사람이 실제로 일을 처리하는 순서이다.

세분화 해서 구분하면
```
업무 흐름 = 사람이 실제 업무를 처리하는 전체 순서
기능 흐름 = 특정 기능 하나를 실행했을 때 사용자가 거치는 화면/동작 순서
시스템 처리 흐름 = 기능 실행 후 서버, DB, API가 내부에서 처리하는 순서
데이터 흐름 = 데이터가 생성되어 저장·검증·가공·활용되는 순서
```

예를 들어 쇼핑몰에서 `주문하기` 버튼을 누르는 것은 하나의 기능이다.
하지만 쇼핑몰의 업무 흐름은 그보다 크다

예를 들어 쇼핑몰 업무 흐름은 다음과 같다.
```text
상품을 찾는다
→ 상품을 비교한다
→ 장바구니에 담는다
→ 주문한다
→ 결제한다
→ 배송을 기다린다
→ 상품을 받는다
→ 리뷰를 작성한다
→ 문제가 있으면 문의하거나 반품한다
```
이 전체가 **업무 흐름**이다.

그중 `주문하기` 기능 하나를 자세히 보면 다음과 같습니다.
```
주문 버튼 클릭
→ 배송지 입력
→ 쿠폰 적용
→ 결제 수단 선택
→ 최종 금액 확인
→ 결제 요청
→ 주문 완료 화면 표시
```
이것은 **기능 흐름**이다.

그리고 사용자가 `결제하기`를 눌렀을 때 시스템 내부에서는 다음 일이 일어날 수 있다
```
결제 요청 API 호출
→ 주문 데이터 검증
→ 재고 확인
→ 결제 서버 요청
→ 결제 성공/실패 응답 수신
→ 주문 상태 변경
→ 결제 로그 저장
→ 알림 발송
```
이것은 **시스템 처리 흐름**이다.

데이터 플랫폼 관점에서는 또 다르게 본다
```
order_created 이벤트 발생
→ Raw 주문 데이터 저장
→ Staging에서 필수값과 타입 검증
→ Mart에서 고객별 주문 요약 생성
→ 추천 모델 학습 데이터셋에 반영
→ 대시보드 매출 지표에 반영
```
이것은 **데이터 흐름**이다.

즉, 다시 정리하면
업무 흐름은 사람이 실제 업무를 처리하는 순서이다.  
  
쉽게 말하면, 업무 흐름은 “사용자가 어떤 목적을 달성하기 위해 실제로 어떤 순서로 행동하는가?”를 정리한 것이다.  
  
업무 흐름은 기능 하나만을 의미하지 않는다.  
기능 하나를 눌렀을 때 이어지는 내부 처리 흐름과도 다르다.  
  
업무 흐름, 기능 흐름, 시스템 처리 흐름, 데이터 흐름은 다음처럼 구분할 수 있다.

| 구분        | 의미                            | 예시                                        |
| --------- | ----------------------------- | ----------------------------------------- |
| 업무 흐름     | 사람이 실제 일을 처리하는 전체 순서          | 상품 조회 → 주문 → 결제 → 배송 → 리뷰                 |
| 기능 흐름     | 특정 기능 하나를 사용할 때의 화면 또는 동작 순서  | 주문 버튼 클릭 → 배송지 입력 → 결제 수단 선택 → 주문 완료      |
| 시스템 처리 흐름 | 기능 실행 후 서버와 DB가 내부에서 처리하는 순서  | API 호출 → 검증 → DB 저장 → 결제 서버 연동            |
| 데이터 흐름    | 데이터가 생성되어 저장, 검증, 가공, 활용되는 순서 | Raw 저장 → Staging 검증 → Mart 생성 → AI/RAG 활용 |

#### `[중간문제]`업무 흐름, 기능 흐름, 시스템 처리 흐름, 데이터 흐름 구분 

```
업무 흐름 = 사람이 실제 업무를 처리하는 전체 순서  
기능 흐름 = 특정 기능 하나를 실행했을 때 사용자가 거치는 화면/동작 순서  
시스템 처리 흐름 = 기능 실행 후 서버, DB, API가 내부에서 처리하는 순서  
데이터 흐름 = 데이터가 생성되어 저장·검증·가공·활용되는 순서
```

특히 AI 네이티브 데이터 플랫폼 과정에서는 이 구분이 매우 중요하다.
이 네 가지를 구분하는 이유는 다음과 같다.
```
업무 흐름을 알아야 사용자의 실제 목적을 이해할 수 있다.
기능 흐름을 알아야 화면과 API를 설계할 수 있다.
시스템 처리 흐름을 알아야 서버와 DB의 내부 처리를 설계할 수 있다.
데이터 흐름을 알아야 Raw, Staging, Mart, AI, RAG, 피드백 데이터 구조를 설계할 수 있다.
```

주니어는 보통 기능부터 생각한다.
```
로그인 기능
주문 기능
결제 기능
수강 신청 기능
알람 확인 기능
```
하지만 데이터 플랫폼 관점에서는 기능보다 먼저 다음 질문을 해야 한다.
```
사람은 실제로 어떤 순서로 일을 처리하는가?
그 과정에서 어떤 기능을 사용하는가?
기능이 실행되면 시스템 내부에서는 어떤 처리가 일어나는가?
그 과정에서 어떤 데이터가 생성되고 어디로 이동하는가?
```
---
아래 문제를 풀면 다음 능력을 얻는다
```
업무를 기능으로 분해하는 능력
기능을 시스템 처리 구조로 바꾸는 능력
시스템 처리를 데이터 흐름으로 바꾸는 능력
데이터 흐름을 Raw, Staging, Mart, AI/RAG/피드백 구조로 설계하는 능력
```
이것이 바로 AI 네이티브 데이터 플랫폼 엔지니어에게 필요한 핵심 사고이다.

##### 6 데이터 소스: 데이터 소스는 데이터가 처음 발생하는 위치이다.
```
데이터 소스 = 데이터가 처음 발생하거나 들어오는 출처
테이블 = 데이터를 저장하는 장소
필드 = 테이블이나 JSON 안에 들어 있는 하나의 항목
```

예를 들어 쇼핑몰에서 주문 데이터가 있다고 하면:
```
데이터 소스:
고객이 주문서를 작성하는 웹/앱 주문 화면

데이터:
주문 정보

저장 테이블:
orders

필드:
order_id, user_id, product_id, quantity, price, order_time
```

즉, **데이터 소스는 `order_id` 같은 필드가 아니라, 그 주문 데이터가 어디서 생겼는지**를 말한다.
```
이 데이터는 어디서 생겼는가?  
누가 만들었는가?  
어떤 시스템이나 파일에서 들어왔는가?  
어떤 방식으로 우리 시스템에 전달되는가?
```

| 구분          | 의미                    | 예시                                            |
| ----------- | --------------------- | --------------------------------------------- |
| 데이터 소스    . | 데이터가 처음 발생하거나 들어오는 출처 | 주문 화면, 모바일 앱, 센서 장비, 외부 API, CSV 파일           |
| 데이터         | 소스에서 만들어진 정보 묶음       | 주문 데이터, 센서 측정값, 결제 로그, 사용자 피드백                |
| 테이블         | 데이터를 저장하는 DB 공간       | `orders`, `sensor_events`, `feedback_logs`    |
| 필드          | 데이터 안의 개별 항목          | `order_id`, `user_id`, `event_time`, `amount` |
예를 들어 쇼핑몰 주문 데이터를 보면 다음과 같다.
```
데이터 소스:
고객이 주문을 입력하는 웹/앱 주문 화면

데이터:
주문 데이터

저장 테이블:
orders

필드:
order_id
user_id
product_id
quantity
price
order_time
payment_status
```


데이터 소스와 필드의 차이
```
데이터 소스 = 센서 장비
필드 = sensor_id, gas_value, event_time

데이터 소스 = 주문 화면 또는 주문 API
필드 = order_id, user_id, product_id, price

데이터 소스 = 퀴즈 제출 화면
필드 = student_id, quiz_id, score, submitted_at

데이터 소스 = 운영자 피드백 화면
필드 = feedback_id, alarm_id, feedback_type, comment
```

데이터 소스의 종류 : 데이터 소스는 여러 형태가 있다.
```text
사용자 입력 폼
모바일 앱
웹사이트 클릭 로그
외부 API
CSV 파일
Excel 파일
PDF 문서
센서 장비
서비스 로그
운영자 피드백
데이터베이스 테이블
메시지 큐
Kafka Topic
```

각 소스는 데이터가 들어오는 방식이 다르다.

| 데이터 소스       | 데이터가 들어오는 방식    | 예시                        |
| ------------ | --------------- | ------------------------- |
| 사용자 입력 폼     | 사용자가 화면에 입력     | 회원가입, 주문, 피드백             |
| 모바일 앱        | 앱에서 API 호출      | 위치 데이터, 활동 로그             |
| 웹사이트 클릭 로그   | 사용자의 클릭 행동 기록   | 상품 조회, 검색어, 페이지 이동        |
| 외부 API       | 다른 시스템에서 데이터 제공 | 날씨 API, 결제 API, 공공데이터 API |
| CSV/Excel 파일 | 파일 업로드 또는 배치 처리 | 주문 목록, 학생 명단, 기준정보        |
| PDF 문서       | 문서 수집 후 텍스트 추출  | 매뉴얼, 보고서, 정책 문서           |
| 센서 장비        | 장비가 주기적으로 값 전송  | 온도, 진동, 가스 농도             |
| 서비스 로그       | 시스템이 자동으로 남김    | API 호출 로그, 오류 로그          |
| 운영자 피드백      | 사람이 판단 후 입력     | 오탐, 정탐, 미탐, 조치 결과         |

데이터 소스를 정리할 때 함께 적어야 하는 것
데이터 소스를 정리할 때는 단순히 이름만 쓰면 부족하다.

| 항목     | 의미              | 예시                           |
| ------ | --------------- | ---------------------------- |
| 데이터 이름 | 어떤 데이터인지        | 주문 데이터, 센서 데이터, 퀴즈 제출 데이터    |
| 발생 주체  | 누가 또는 무엇이 만드는지  | 고객, 수강생, 센서 장비, 외부 시스템       |
| 발생 방식  | 어떻게 들어오는지       | 화면 입력, API 호출, 파일 업로드, 센서 전송 |
| 발생 주기  | 얼마나 자주 생기는지     | 실시간, 1초마다, 매일, 필요할 때         |
| 데이터 형식 | 어떤 형태인지         | JSON, CSV, Excel, PDF, Log   |
| 저장 위치  | 어디에 저장할지        | Raw Zone, DB 테이블, Vector DB  |
| 사용 목적  | 어디에 쓸지          | 대시보드, AI 학습, RAG 검색, 품질 분석   |
| 품질 위험  | 어떤 문제가 생길 수 있는지 | 누락, 중복, 지연, 타입 오류, 단위 오류     |

예를 들어 산업안전 가스 센서 데이터를 정리하면 다음과 같다.

| 항목     | 내용                          |
| ------ | --------------------------- |
| 데이터 이름 | 가스 센서 측정 데이터                |
| 발생 주체  | 가스 센서 장비                    |
| 발생 방식  | 센서 장비가 API 또는 메시지로 전송       |
| 발생 주기  | 1초 또는 5초마다                  |
| 데이터 형식 | JSON                        |
| 저장 위치  | Raw Zone, 이후 Staging, Mart  |
| 사용 목적  | 위험도 판단, 알람 생성, AI 이상탐지      |
| 품질 위험  | 센서값 누락, 단위 오류, 중복 전송, 지연 도착 |

 왜 데이터 소스를 먼저 정리해야 하는가?
데이터 소스를 먼저 정리해야 이후 설계가 가능하다.
```
데이터 소스를 알아야 어떤 API가 필요한지 알 수 있다.
데이터 소스를 알아야 어떤 파일 구조가 필요한지 알 수 있다.
데이터 소스를 알아야 어떤 Schema가 필요한지 알 수 있다.
데이터 소스를 알아야 Raw에 무엇을 저장할지 정할 수 있다.
데이터 소스를 알아야 어떤 검증 규칙이 필요한지 알 수 있다.
데이터 소스를 알아야 어떤 데이터가 AI, RAG, 대시보드, 피드백에 쓰이는지 알 수 있다.
```

예를 들어 데이터 소스가 센서 장비라면 다음을 고려해야 한다.
```
값이 주기적으로 들어오는가?
데이터가 늦게 도착할 수 있는가?
같은 데이터가 중복으로 들어올 수 있는가?
센서 단위가 정확한가?
센서 ID가 등록된 센서인지 확인해야 하는가?
```

데이터 소스가 PDF 문서라면 고려할 내용이 달라진다.
```
문서 원본을 어디에 저장할 것인가?
텍스트 추출이 가능한가?
문서 버전은 무엇인가?
누가 볼 수 있는 문서인가?
RAG 검색에 사용할 메타데이터는 무엇인가?
```

즉, 데이터 소스에 따라 수집 방식, 저장 방식, 검증 방식, 활용 방식이 달라진다.

| 데이터 이름                               . | 데이터 <br>소스    | 발생 <br>주체 | 발생 <br>방식         | 형식       | 사용 <br>목적           | 품질 위험              |
| -------------------------------------- | ------------- | --------- | ----------------- | -------- | ------------------- | ------------------ |
| 주문 데이터                                 | 쇼핑몰 <br>주문 화면 | 고객        | 주문 버튼 클릭        . | JSON     | 매출 분석, 추천         . | 주문 누락, 결제 상태 불일치   |
| 퀴즈 제출 <br>데이터                          | LMS 퀴즈 화면     | 수강생       | 제출 버튼 클릭          | JSON     | 학습 부진 탐지            | 점수 누락, <br>중복 제출   |
| 센서 측정 <br>데이터                          | 온도 센서 장비      | 센서        | 주기적 <br>전송        | JSON     | 이상탐지                | 지연, 중복, <br>단위 오류  |
| 매뉴얼 문서                                 | PDF 파일        | 운영자/관리자   | 파일 <br>업로드        | PDF      | RAG 검색              | 오래된 문서, 출처 불명      |
| 피드백 데이터                                | 운영자 피드백 화면    | 운영자       | 화면 입력             | JSON     | 재학습 후보              | 주관적 판단, 누락         |
| API 로그                                 | 서비스 <br>서버    | 시스템       | 자동 기록             | Log/JSON | 운영 분석               | trace_id 누락, 시간 오류 |

##### 7 이벤트: 이벤트는 업무에서 발생한 중요한 사건이다.

예를 들어 쇼핑몰에서 고객이 주문 버튼을 눌러 주문이 만들어졌다면, 그 사건을 이벤트로 표현한다.

이벤트의 종류:

이벤트라는 말은 여러 분야에서 사용된다.  
프론트엔드에서는 버튼 클릭, 마우스 이동, 스크롤 같은 사용자 행동도 이벤트라고 부른다.  
백엔드에서는 주문 생성, 결제 실패, 알람 생성 같은 업무 사건을 이벤트라고 부른다.  
데이터 엔지니어링에서는 데이터 수집, 검증 실패, 파이프라인 완료, 품질 실패 같은 데이터 처리 사건도 이벤트라고 부른다.

따라서 이벤트를 이해할 때는 먼저 다음을 구분해야 한다.
```
프론트엔드 이벤트:  
사용자가 화면에서 한 행동  
  
도메인 이벤트:  
업무에서 실제로 발생한 중요한 사건  
  
데이터 이벤트:  
데이터가 생성, 수집, 저장, 검증, 변환되는 사건  
  
AI/RAG 이벤트:  
AI 추론, RAG 검색, 답변 생성, 실패, 피드백과 관련된 사건  
  
운영 이벤트:  
파이프라인 실패, 품질 실패, 지연, SLA 위반처럼 운영 중 감지되는 사건
```

이 과정에서는 모든 이벤트를 같은 비중으로 다루지 않는다.  
AI 네이티브 데이터 플랫폼 엔지니어 과정에서는 다음 순서로 이벤트를 이해하는 것이 좋다.
```
1. 도메인 업무 이벤트
2. 데이터 수집 이벤트
3. 센서/측정 이벤트
4. 위치/지오펜싱 이벤트
5. AI 판단 이벤트
6. 알람/조치 이벤트
7. RAG 문서/검색 이벤트
8. 피드백/라벨 이벤트
9. 데이터 파이프라인 이벤트
10. 데이터 품질 이벤트
11. 운영/관찰 가능성 이벤트
12. 보안/권한 이벤트
13. UI 이벤트
```

### 🔗 [[이벤트 종류 및 설명]] 상세설명클릭


AI 네이티브 데이터 플랫폼에서는 코딩을 바로 시작하기 전에, 먼저 **어떤 이벤트가 발생하는지 파악하고 이벤트명을 정리한 뒤**, 그 이벤트를 기준으로 API, 함수, Schema, Raw 저장소, Kafka Topic 등을 계획하는 것이 좋다

핵심 순서
```
1. 업무 흐름을 본다
→ 2. 중요한 사건을 찾는다
→ 3. 이벤트명을 정한다
→ 4. 이벤트별 데이터 구조를 정한다
→ 5. 관련 API, 함수, Schema, 저장 위치, Topic 이름을 맞춘다
→ 6. 그 기준으로 코딩을 시작한다
```

예를 들어 쇼핑몰에서 “주문이 생성된다”는 사건을 찾았다면:
```
업무 사건:
주문이 생성되었다

이벤트명:
order_created
```

그다음 이 이벤트를 기준으로 관련 구조를 미리 맞춘다

| 구분          | 예시                             |
| ----------- | ------------------------------ |
| 이벤트명        | `order_created`                |
| 의미          | 주문이 생성되었다                      |
| API 경로      | `POST /api/orders`             |
| View 함수     | `create_order()`               |
| 이벤트 생성 함수   | `create_order_created_event()` |
| 이벤트 처리 함수   | `handle_order_created()`       |
| Schema 파일   | `order_created.schema.json`    |
| Raw 저장 경로   | `data_lake/raw/order_events/`  |
| Kafka Topic | `order.created`                |
| 샘플 파일       | `order_created.sample.json`    |
즉, 이벤트명은 단순 이름이 아니라 **코드와 데이터 구조를 연결하는 기준 이름**이다
0단계에서는 먼저 **후보 이벤트 목록**을 만들고, 1~2단계로 가면서 API, Schema, Raw 저장 구조를 구체화하면 된다.

정리하면
```
코딩 전에 이벤트를 먼저 계획한다.
이벤트명은 데이터 설계의 기준이 된다.
이벤트명을 기준으로 API, 함수, 클래스, Schema, Raw, Staging, Kafka Topic 이름을 일관되게 맞춘다.
이렇게 해야 나중에 데이터 수집, 파이프라인, AI 학습, RAG, 피드백, 운영 지표까지 연결하기 쉽다.
```

그래서 0단계 기준선 정리에서 해야 할 일은 다음이다
```
이 플랫폼에서 어떤 중요한 사건이 발생하는가?
그 사건을 어떤 이벤트명으로 부를 것인가?
각 이벤트는 어떤 데이터를 가져야 하는가?
각 이벤트는 어디에 저장되고, 이후 어떤 단계에서 사용되는가?
```

##### 9 Raw, Staging, Mart: AI 데이터 플랫폼에서는 데이터를 목적에 따라 나눈다.
| 구분      | 의미                | 예시                            |
| ------- | ----------------- | ----------------------------- |
| Raw     | 원본에 가까운 데이터       | API로 들어온 JSONL, 원본 CSV, 원본 로그 |
| Staging | 검증되고 정리된 중간 데이터   | 타입 변환, 필수값 검증, 중복 제거된 데이터     |
| Mart    | 특정 목적에 맞게 가공된 데이터 | 대시보드용 집계, AI 학습 데이터셋, 알람 요약   |

쉽게 말하면 다음과 같다.
```text
Raw는 원본 보관용
Staging은 검증된 작업용
Mart는 목적별 사용용
```

#### 10 시스템 경계: 시스템 경계는 이번 프로젝트에서 만들 것과 만들지 않을 것을 구분하는 기준이다.

예를 들어 쇼핑몰 데이터 플랫폼에서는 다음처럼 정할 수 있다.
```text
만드는 것:
주문 데이터 수집
Raw 저장
주문 Mart 생성
추천 후보 데이터셋 생성

만들지 않는 것:
실제 카드 결제
실제 배송 시스템
실제 문자 발송
```

시스템 경계를 정하지 않으면 프로젝트 범위가 계속 커진다.

## 7. 범용 도메인 예시

0단계는 특정 산업 도메인만 배우는 시간이 아니다.  
다양한 도메인을 예시로 기준선 정리 방법을 연습해야 한다.

쇼핑몰 데이터 플랫폼 예시
```text
프로젝트 목적:
고객 행동과 주문 데이터를 수집하여 추천, 재구매 분석, 이상 주문 탐지를 위한 데이터 기반을 만든다.

사용자 역할:
고객, 판매자, 관리자, 추천 시스템, 결제 시스템

데이터 소스:
주문 데이터, 결제 로그, 장바구니 로그, 상품 조회 로그, 리뷰 데이터, CS 문의

주요 이벤트:
product_viewed
cart_item_added
order_created
payment_completed
payment_failed
review_submitted
cs_ticket_created

Raw:
원본 주문 JSON, 결제 로그, 클릭 로그

Staging:
검증된 주문, 결제, 리뷰, 고객 행동 데이터

Mart:
고객별 구매 요약, 상품별 판매 요약, 추천 후보 데이터셋

AI 활용:
추천 모델, 이상 주문 탐지, 수요 예측

피드백:
추천 클릭 여부, 구매 전환 여부, 리뷰 만족도
```

교육 LMS 데이터 플랫폼 예시
```text
프로젝트 목적:
수강생의 학습 활동 데이터를 수집하여 학습 부진을 조기에 탐지하고 맞춤형 피드백을 제공한다.

데이터 소스:
강의 시청 로그, 퀴즈 제출, 과제 제출, 출석, 질문 게시판, 피드백
```

제조 설비 데이터 플랫폼 예시

```text
프로젝트 목적:

데이터 소스:
온도 센서, 진동 센서, 전력 사용량, 점검 기록, 불량률 데이터

machine_temperature_measured
```

```text
거래 로그, 로그인 로그, 카드 사용 내역, 상담 기록, 신고 데이터
```

## 11. 0단계 개인 과제

자신이 선택한 도메인 하나를 기준으로 1페이지 기준선 문서를 작성한다.

```text
도메인은 자유롭게 선택한다.
단, 데이터 소스가 최소 3개 이상 있어야 한다.
AI 또는 RAG 또는 피드백 데이터가 최소 1개 이상 포함되어야 한다.
Raw / Staging / Mart 구분이 있어야 한다.
최종 시연 시나리오가 있어야 한다.
```

제출 산출물
```text
docs/project-overview.md
docs/data-source-map.md
docs/domain-event-map.md
docs/baseline-data-flow.md
docs/final-demo-scenario.md
```

###### 작성 기준
| 기준     | 확인 내용                      |
| ------ | -------------------------- |
| 문제 정의  | 해결하려는 문제가 명확한가?            |
| 데이터 소스 | 데이터가 어디서 발생하는지 설명되어 있는가?   |
| 데이터 흐름 | 수집부터 활용까지 흐름이 이어지는가?       |

| 시스템 경계 | 만들 것과 만들지 않을 것을 구분했는가?     |

## 12. 0단계에서 산업안전 관제플랫폼으로 치환하는 방법

0단계의 핵심은 범용 기준선 정리 방법을 배우는 것이다.  
산업안전 관제플랫폼은 이 기준을 적용하는 예제 중 하나이다.

다음처럼 치환하면 된다.

| 범용 기준 | 산업안전 관제플랫폼 적용 예시 |
|---|---|
| 데이터 소스 | 센서, 전력 장비, 작업자 위치, 알람, 매뉴얼, 피드백 |
| 도메인 이벤트 | gas_sensor_measured, worker_location_updated, alarm_created |
| Raw 데이터 | 원본 센서 JSONL, 원본 로그, 원본 문서 |
| Staging 데이터 | 검증된 센서값, 작업자 위치, 알람 이벤트 |
| Mart 데이터 | 위험도 요약, 알람 요약, AI 학습 후보 데이터셋 |
| RAG 데이터 | 가스 임계치 정의서, 대응 매뉴얼, 장비 문서 |
| 피드백 데이터 | 오탐/정탐/미탐, 운영자 조치 결과 |
| 품질 기준 | 필수값, 범위, 중복, 지연, schema_version |
| 관찰 가능성 | 수집 지연, 흐름 중단, SLA 위반, 데이터 계보 |

즉, 산업안전 관제플랫폼은 0단계에서 배운 질문을 그대로 적용하는 실습 도메인이다.

## 14. 주니어가 자주 헷갈리는 부분

도메인과 기능의 차이
```text
도메인:
프로젝트가 다루는 업무 세계

기능:
그 업무 세계 안에서 사용자가 수행하는 동작
```
예를 들어 쇼핑몰에서 `주문`은 도메인 요소이고, `주문하기`는 기능이다.


이벤트와 API의 차이
```text
이벤트:
업무에서 발생한 사건

API:
그 사건이나 데이터를 시스템에 전달하는 입구
```

예를 들어 `order_created`는 이벤트이고, `POST /api/orders`는 API일 수 있다.


Raw와 Staging의 차이
```text
Raw:
원본 보존

Staging:
검증과 정리

Mart:
목적별 사용
```

Raw를 바로 대시보드나 AI에 사용하면 나중에 오류 추적이 어렵다.


로그와 피드백의 차이
```text
로그:
시스템이 자동으로 남기는 기록

피드백:
사용자나 운영자가 판단 결과에 대해 남기는 평가
```

AI 서비스에서는 로그와 피드백 모두 개선 데이터가 될 수 있다.


기준선과 요구사항의 차이
```text
요구사항:
무엇을 만들어야 하는지에 대한 요청

기준선:
그 요구사항을 개발하기 위해 미리 고정하는 구조와 규칙
```

## 15. 다음 단계와의 연결

0단계에서 만든 기준선은 1단계와 2단계의 입력이 된다.
```text
0단계 결과물
→ 프로젝트 목적
→ 문제 정의
→ 데이터 소스
→ 도메인 이벤트
→ 데이터 흐름
→ 시스템 경계
→ 컨벤션
→ 폴더/브랜치 기준
```

이 결과물은 다음 단계에서 사용된다.
```text
1단계:
AI 서비스와 데이터 플랫폼 아키텍처 작성

2단계:
Data Contract, Schema, Collector API 설계

3단계:
Raw → Staging → Mart 파이프라인 설계

4단계:
실시간 이벤트 Topic과 Dashboard 흐름 설계

5단계:
데이터 품질, 계보, 권한 기준 설계

6단계:
RAG 문서 Metadata와 Vector Pipeline 설계

7단계:
피드백 데이터와 DataOps Metric 설계
```

## 16. 최종 정리

0단계 프로젝트 기준선 정리는 개발을 늦추는 문서 작업이 아니다.  
오히려 개발을 빠르고 안전하게 만드는 출발점이다.

초보자는 프로젝트를 시작할 때 코드를 먼저 작성하고 싶어한다.  
하지만 AI 네이티브 데이터 플랫폼 프로젝트에서는 데이터가 어떻게 발생하고, 어디에 저장되고, 어떻게 검증되고, 어떤 목적의 데이터셋으로 바뀌는지를 먼저 이해해야 한다.

0단계에서 반드시 기억해야 할 문장은 다음이다.
```text
기준선은 프로젝트가 흔들리지 않도록 만드는 출발 기준이다.
```

그리고 AI 네이티브 데이터 플랫폼 과정에서는 다음 문장이 가장 중요하다.
```text
AI는 모델만으로 움직이지 않는다.
AI를 움직이게 하는 것은 신뢰 가능한 데이터 흐름과 운영 가능한 데이터 플랫폼이다.
```

0단계에서 기준선을 제대로 정리하면 이후 1단계부터 7단계까지의 실습은 단순한 코드 따라치기가 아니라, 하나의 일관된 데이터 플랫폼을 완성하는 과정이 된다.
