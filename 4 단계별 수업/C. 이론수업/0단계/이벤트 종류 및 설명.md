### 1. 도메인 업무 이벤트

도메인 업무 이벤트는 실제 업무에서 발생한 중요한 사건이다.

이벤트 중 가장 먼저 이해해야 하는 것이 도메인 업무 이벤트이다.  
왜냐하면 데이터 플랫폼은 결국 업무에서 발생한 데이터를 수집하고 처리하기 때문이다.

예시는 다음과 같다.

| 도메인  | 이벤트 예시                  | 의미           |
| ---- | ----------------------- | ------------ |
| 쇼핑몰  | `order_created`         | 주문이 생성되었다    |
| 쇼핑몰  | `payment_failed`        | 결제가 실패했다     |
| 교육   | `quiz_submitted`        | 퀴즈가 제출되었다    |
| 교육   | `assignment_uploaded`   | 과제가 업로드되었다   |
| 제조   | `maintenance_requested` | 점검 요청이 등록되었다 |
| 산업안전 | `alarm_created`         | 알람이 생성되었다    |

도메인 업무 이벤트는 나중에 API, Schema, Raw 저장, Staging 검증, Mart 생성의 기준이 된다.

예를 들어 쇼핑몰에서 `order_created` 이벤트가 있으면 다음과 연결된다.
```
order_created 이벤트
→ 주문 수집 API
→ 주문 Raw 데이터
→ 주문 Staging 데이터
→ 고객별 주문 Mart
→ 추천 모델 학습 데이터셋
```

### 2. 데이터 수집 이벤트

데이터 수집 이벤트는 외부 데이터가 우리 시스템으로 들어오는 사건이다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`data_received`|데이터가 시스템에 수신되었다|
|`file_uploaded`|파일이 업로드되었다|
|`api_payload_received`|API 요청 데이터가 수신되었다|
|`external_data_imported`|외부 데이터가 적재되었다|
|`raw_event_stored`|Raw 데이터가 저장되었다|
데이터 수집 이벤트는 2단계 데이터 수집과 레이크하우스 설계에서 중요하다.

예를 들어 다음 흐름에서 발생한다.
```
외부 시스템 또는 사용자 입력
→ Collector API 호출
→ 데이터 수신
→ Raw Zone 저장
→ 수집 성공 또는 실패 기록
```

산업안전 관제플랫폼에서는 다음처럼 볼 수 있다.
```
gas_sensor_payload_received
→ raw_gas_event_stored
```

---
#### 부가설명:
이벤트명은 엔지니어가 임의로 아무렇게나 붙이는 이름이 아니라,  
데이터 설계자/백엔드 엔지니어가 업무 흐름을 보고 “어떤 사건을 데이터로 남길 것인가”를 정한 뒤, 그 사건에 붙이는 표준 이름이다.
```
이벤트명 = 업무에서 발생한 중요한 사건을 코드와 데이터에서 일관되게 부르기 위한 이름
```
예를 들어 주문이 생성되는 사건을 `order_created`라고 정하면, 이후 관련된 코드와 파일도 이 이름을 기준으로 맞춘다.
```
주문이 생성되었다
→ 이벤트명: order_created
→ API: POST /api/orders
→ View 함수: create_order()
→ 이벤트 생성 함수: create_order_created_event()
→ 이벤트 처리 함수: handle_order_created()
→ 클래스: OrderCreatedEvent
→ Schema 파일: order_created.schema.json
→ Raw 저장: raw_order_events
→ Kafka Topic: order.created
→ 샘플 파일: order_created.sample.json
```
즉, 이벤트명은 단순한 이름이 아니라 **프로젝트 전체의 연결 기준**이다.

| 구분             | 예시                             |
| -------------- | ------------------------------ |
| 이벤트명           | `order_created`                |
| 의미             | 주문이 생성되었다                      |
| 화면 기능          | 주문하기                           |
| API 경로         | `POST /api/orders`             |
| Django View 함수 | `create_order()`               |
| 이벤트 생성 함수      | `create_order_created_event()` |
| 이벤트 처리 함수      | `handle_order_created()`       |
| Pydantic 클래스   | `OrderCreatedEvent`            |
| JSON Schema 파일 | `order_created.schema.json`    |
| Raw 저장 경로      | `data_lake/raw/order_events/`  |
| Raw 테이블        | `raw_order_events`             |
| Staging 테이블    | `stg_orders`                   |
| Kafka Topic    | `order.created`                |
| 샘플 파일          | `order_created.sample.json`    |

### 3. 센서/측정 이벤트

센서/측정 이벤트는 장비나 시스템이 특정 값을 측정했을 때 발생하는 이벤트이다.

AI 데이터 플랫폼에서는 매우 중요한 이벤트이다.  
왜냐하면 센서값은 실시간 판단, 이상탐지, 알람, 대시보드, AI 학습 데이터셋으로 연결되기 때문이다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`temperature_measured`|온도가 측정되었다|
|`gas_sensor_measured`|가스 센서값이 측정되었다|
|`power_usage_measured`|전력 사용량이 측정되었다|
|`vibration_measured`|진동값이 측정되었다|
|`heart_rate_measured`|심박수가 측정되었다|

산업안전 관제플랫폼에서는 다음 이벤트가 중요하다.
```
gas_sensor_measured
power_usage_measured
worker_location_updated
```

이 이벤트들은 다음 데이터 흐름으로 이어진다.
```
센서값 측정
→ Raw 센서 이벤트 저장
→ Staging에서 sensor_id, value, unit, event_time 검증
→ Mart에서 구역별 위험도 요약 생성
→ AI 이상탐지 또는 임계치 판단
→ 알람 생성
```

### 4. 위치/지오펜싱 이벤트

산업안전 관제플랫폼 실습에서 `지오펜싱 이벤트`는 이 매우 중요한 이벤트에 해당된다.

지오펜싱은 특정 위치가 위험구역 안에 들어왔는지, 밖으로 나갔는지 판단하는 개념이다.  
산업안전 관제플랫폼에서는 작업자가 위험구역에 진입했는지를 판단하는 데 사용된다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`worker_location_updated`|작업자 위치가 갱신되었다|
|`worker_entered_danger_zone`|작업자가 위험구역에 진입했다|
|`worker_exited_danger_zone`|작업자가 위험구역에서 벗어났다|
|`geofence_intrusion_detected`|지오펜스 침입이 감지되었다|
|`geofence_violation_resolved`|지오펜스 위반 상태가 해소되었다|

위치 이벤트는 단순 UI 이벤트가 아니다.  
실제 위험 판단과 알람 생성으로 이어지는 도메인/데이터 이벤트이다.

예를 들어 다음과 같다.
```
worker_location_updated
→ 위치 좌표 Raw 저장
→ Staging에서 worker_id, latitude, longitude, event_time 검증
→ 위험구역 좌표와 비교
→ worker_entered_danger_zone 이벤트 발생
→ alarm_created 이벤트 발생
→ 운영자 대시보드에 표시
```

### 5. AI 판단 이벤트

AI 판단 이벤트는 AI 모델이나 규칙 엔진이 어떤 판단 결과를 만들었을 때 발생하는 이벤트이다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`risk_detected`|위험이 감지되었다|
|`anomaly_detected`|이상이 탐지되었다|
|`prediction_created`|예측 결과가 생성되었다|
|`risk_score_calculated`|위험 점수가 계산되었다|
|`model_inference_failed`|모델 추론이 실패했다|

AI 네이티브 데이터 플랫폼에서는 AI 판단 이벤트를 반드시 저장해야 한다.  
왜냐하면 나중에 다음을 확인해야 하기 때문이다.
```
AI가 언제 판단했는가?
어떤 데이터를 보고 판단했는가?
위험 점수는 얼마였는가?
판단 결과가 맞았는가?
운영자가 오탐/정탐/미탐으로 피드백했는가?
```

예를 들어 산업안전에서는 다음 흐름이 가능하다.
```
gas_sensor_measured
→ AI 이상탐지 모델 호출
→ gas_anomaly_detected
→ risk_score_calculated
→ alarm_created
```

### 6. 알람/조치 이벤트

알람/조치 이벤트는 위험이 감지된 뒤 운영자가 확인하고 대응하는 과정에서 발생하는 이벤트이다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`alarm_created`|알람이 생성되었다|
|`alarm_acknowledged`|운영자가 알람을 확인했다|
|`alarm_escalated`|알람이 상위 단계로 escalated 되었다|
|`action_started`|조치가 시작되었다|
|`action_completed`|조치가 완료되었다|
|`alarm_resolved`|알람이 해결되었다|

산업안전 관제플랫폼에서는 매우 중요하다.
```
위험 감지
→ alarm_created
→ 운영자 확인
→ alarm_acknowledged
→ 대응 조치
→ action_completed
→ alarm_resolved
```

이 이벤트들은 단순 상태값이 아니라 운영 이력 데이터이다.  
나중에 운영 품질, 대응 시간, 재학습 후보, 리포트에 활용된다.

### 7. RAG 문서/검색 이벤트

RAG 문서/검색 이벤트는 문서가 등록되거나, 검색되거나, 답변 생성에 사용될 때 발생하는 이벤트이다.

6단계 RAG와 벡터 데이터 파이프라인에서 중요하다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`document_registered`|문서가 등록되었다|
|`document_chunked`|문서가 Chunk로 나뉘었다|
|`embedding_created`|임베딩이 생성되었다|
|`vector_index_updated`|Vector DB가 갱신되었다|
|`rag_query_submitted`|RAG 질문이 제출되었다|
|`rag_documents_retrieved`|관련 문서가 검색되었다|
|`rag_answer_generated`|RAG 답변이 생성되었다|
|`rag_answer_failed`|RAG 답변 생성이 실패했다|

예를 들어 산업안전에서 알람 발생 후 대응 매뉴얼을 검색하면 다음 이벤트가 발생할 수 있다.
```
alarm_created
→ rag_query_submitted
→ rag_documents_retrieved
→ rag_answer_generated
→ rag_answer_viewed
```

RAG 이벤트는 반드시 출처와 연결되어야 한다.
```
어떤 질문이 들어왔는가?
어떤 문서가 검색되었는가?
어떤 Chunk가 사용되었는가?
답변에 어떤 출처가 표시되었는가?
사용자가 답변을 유용하다고 평가했는가?
```

### 8. 피드백/라벨 이벤트

피드백/라벨 이벤트는 운영자나 사용자가 AI 판단, 알람, RAG 답변에 대해 평가를 남겼을 때 발생한다.

7단계 DataOps 운영에서 매우 중요하다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`feedback_submitted`|피드백이 제출되었다|
|`alarm_labeled_true_positive`|알람이 정탐으로 라벨링되었다|
|`alarm_labeled_false_positive`|알람이 오탐으로 라벨링되었다|
|`missed_detection_reported`|미탐이 보고되었다|
|`rag_answer_rated`|RAG 답변이 평가되었다|
|`retraining_candidate_created`|재학습 후보가 생성되었다|

AI 서비스는 한 번 만들고 끝나지 않는다.  
피드백 이벤트가 있어야 AI를 개선할 수 있다.

예를 들어 다음과 같다.
```
alarm_created
→ 운영자 확인
→ feedback_submitted
→ alarm_labeled_false_positive
→ retraining_candidate_created
```

이 흐름이 있어야 오탐 데이터를 재학습 후보로 만들 수 있다.

### 9. 데이터 파이프라인 이벤트

데이터 파이프라인 이벤트는 Airflow나 Python 파이프라인이 실행되면서 발생하는 이벤트이다.
3단계에서 중요하다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`pipeline_started`|파이프라인이 시작되었다|
|`pipeline_completed`|파이프라인이 완료되었다|
|`pipeline_failed`|파이프라인이 실패했다|
|`staging_created`|Staging 데이터가 생성되었다|
|`mart_created`|Mart 데이터가 생성되었다|
|`backfill_started`|Backfill이 시작되었다|
|`backfill_completed`|Backfill이 완료되었다|
|`checkpoint_saved`|Checkpoint가 저장되었다|

예를 들어 Raw 데이터를 Staging으로 변환하는 파이프라인에서는 다음 이벤트가 중요하다.
```
raw_to_staging_pipeline_started
→ staging_created
→ quality_report_created
→ checkpoint_saved
→ raw_to_staging_pipeline_completed
```

이 이벤트가 있어야 운영 중 파이프라인 상태를 추적할 수 있다.

### 10. 데이터 품질 이벤트

데이터 품질 이벤트는 데이터 검증이나 품질 점검에서 문제가 발견되었을 때 발생한다.
5단계 데이터 품질, 계보, 거버넌스에서 중요하다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`validation_failed`|데이터 검증이 실패했다|
|`schema_mismatch_detected`|Schema 불일치가 감지되었다|
|`null_value_detected`|필수값 누락이 감지되었다|
|`duplicate_detected`|중복 데이터가 감지되었다|
|`late_event_detected`|지연 데이터가 감지되었다|
|`quality_check_failed`|품질 점검이 실패했다|
|`data_drift_detected`|데이터 분포 변화가 감지되었다|

예를 들어 센서 데이터에서 필수값이 누락되면 다음처럼 볼 수 있다.
```
gas_sensor_measured
→ validation_failed
→ dead_letter_stored
→ quality_check_failed
```

품질 이벤트를 남기면 다음을 알 수 있다.
```
어떤 데이터가 실패했는가?
왜 실패했는가?
어디에 저장되었는가?
재처리가 필요한가?
품질 리포트에 반영되었는가?
```

### 11. 운영/관찰 가능성 이벤트

운영/관찰 가능성 이벤트는 데이터 흐름이 정상적으로 운영되는지 감지하는 이벤트이다.
7단계 DataOps에서 중요하다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`data_flow_stopped`|데이터 흐름이 중단되었다|
|`consumer_lag_detected`|Kafka Consumer Lag가 감지되었다|
|`freshness_sla_violated`|Freshness SLA가 위반되었다|
|`dashboard_metric_delayed`|대시보드 Metric 반영이 지연되었다|
|`api_latency_exceeded`|API 응답 시간이 기준을 초과했다|
|`service_health_check_failed`|서비스 헬스체크가 실패했다|

이 이벤트들은 기능 개발보다는 운영 안정성과 관련이 있다.

예를 들어 다음 상황에서 필요하다.
```
센서 데이터가 5분 동안 들어오지 않음
→ data_flow_stopped

Kafka Consumer가 데이터를 따라가지 못함
→ consumer_lag_detected

대시보드 지표가 1분 이상 늦게 반영됨
→ dashboard_metric_delayed
```

---

### 12. 보안/권한 이벤트

보안/권한 이벤트는 사용자의 접근, 권한 위반, 민감 데이터 조회와 관련된 사건이다.
5단계 거버넌스와 7단계 운영에서 중요하다.

예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`user_logged_in`|사용자가 로그인했다|
|`user_login_failed`|로그인에 실패했다|
|`access_denied`|접근이 거부되었다|
|`sensitive_data_viewed`|민감 데이터가 조회되었다|
|`permission_changed`|권한이 변경되었다|
|`secret_accessed`|Secret 정보 접근이 발생했다|

AI 데이터 플랫폼에서는 보안 이벤트도 중요하다.  
특히 작업자 위치, 사용자 피드백, 문서 권한, 운영 로그는 민감할 수 있기 때문이다.

---

### 13. UI 이벤트

UI 이벤트는 사용자가 화면에서 한 행동이다.
예시는 다음과 같다.

|이벤트명|의미|
|---|---|
|`button_clicked`|버튼이 클릭되었다|
|`page_viewed`|페이지가 조회되었다|
|`modal_opened`|모달이 열렸다|
|`form_submitted`|폼이 제출되었다|
|`mouse_wheel_scrolled`|마우스 휠이 스크롤되었다|
|`tab_changed`|탭이 변경되었다|
|`filter_applied`|필터가 적용되었다|

버튼 이벤트나 마우스휠 이벤트도 이벤트는 맞다.  
하지만 이 과정에서 항상 중요한 것은 아니다.

예를 들어 `마우스휠 이벤트`는 일반적인 데이터 플랫폼에서는 중요도가 낮다.  
하지만 사용자의 행동 분석이 중요한 서비스라면 의미가 있을 수 있다.
```
콘텐츠 추천 서비스:
scroll_depth_changed
video_paused
video_skipped

쇼핑몰:
product_clicked
filter_applied
search_submitted

교육 LMS:
video_paused
video_replayed
quiz_started
```

산업안전 관제플랫폼에서는 단순 마우스휠보다 다음 UI 이벤트가 더 중요할 수 있다.
```
alarm_detail_viewed
alarm_acknowledge_button_clicked
manual_search_requested
feedback_form_submitted
```

다만 데이터 플랫폼 관점에서는 UI 이벤트를 그대로 저장하기보다, 업무적으로 의미 있는 이벤트로 바꾸는 것이 좋다.

예를 들어 다음과 같다.

|UI 이벤트|데이터 플랫폼에서 더 중요한 이벤트|
|---|---|
|`alarm_confirm_button_clicked`|`alarm_acknowledged`|
|`feedback_submit_button_clicked`|`feedback_submitted`|
|`manual_search_button_clicked`|`rag_query_submitted`|
|`order_button_clicked`|`order_created`|
|`payment_button_clicked`|`payment_completed` 또는 `payment_failed`|

즉, 버튼 클릭 자체보다 그 결과로 어떤 업무 사건이 발생했는지가 더 중요하다.

---

## 6.7.2 이 과정에서 우선순위가 높은 이벤트

AI 네이티브 데이터 플랫폼 엔지니어 과정에서는 이벤트를 다음 우선순위로 다루는 것이 좋다.

|우선순위|이벤트 종류|중요한 이유|
|---|---|---|
|1|도메인 업무 이벤트|실제 업무에서 발생한 중요한 사건이기 때문|
|2|데이터 수집 이벤트|Raw 데이터의 출발점이기 때문|
|3|센서/측정 이벤트|실시간 판단과 AI 이상탐지의 입력이기 때문|
|4|위치/지오펜싱 이벤트|위험 판단과 알람 생성에 직접 연결되기 때문|
|5|AI 판단 이벤트|AI 결과와 모델 개선 근거가 되기 때문|
|6|알람/조치 이벤트|운영자의 대응 이력과 피드백으로 이어지기 때문|
|7|RAG 문서/검색 이벤트|문서 검색과 출처 추적에 필요하기 때문|
|8|피드백/라벨 이벤트|재학습 후보 데이터셋의 기준이 되기 때문|
|9|데이터 파이프라인 이벤트|Airflow, Backfill, Checkpoint 운영에 필요하기 때문|
|10|데이터 품질 이벤트|검증 실패, 중복, 지연, Drift 관리에 필요하기 때문|
|11|운영/관찰 가능성 이벤트|SLA, 지연, 장애, 흐름 중단 감지에 필요하기 때문|
|12|보안/권한 이벤트|민감 데이터 접근과 거버넌스 관리에 필요하기 때문|
|13|UI 이벤트|사용자 행동 분석에는 필요하지만 우선순위는 낮음|

정리하면 다음과 같다.
```
이 과정에서 이벤트를 볼 때는
버튼 클릭이나 마우스휠 같은 화면 이벤트보다
데이터가 발생하고, 이동하고, 검증되고, 판단되고, 피드백되는 사건을 먼저 본다.
```

---

## 6.7.3 산업안전 관제플랫폼 기준 이벤트 예시

산업안전 관제플랫폼에서는 다음 이벤트를 우선 정의할 수 있다.

|이벤트 종류|이벤트명|의미|
|---|---|---|
|센서/측정 이벤트|`gas_sensor_measured`|가스 센서값이 측정되었다|
|센서/측정 이벤트|`power_usage_measured`|전력 사용량이 측정되었다|
|위치 이벤트|`worker_location_updated`|작업자 위치가 갱신되었다|
|지오펜싱 이벤트|`worker_entered_danger_zone`|작업자가 위험구역에 진입했다|
|지오펜싱 이벤트|`worker_exited_danger_zone`|작업자가 위험구역에서 벗어났다|
|위험 판단 이벤트|`risk_detected`|위험이 감지되었다|
|AI 판단 이벤트|`anomaly_detected`|AI 이상탐지가 발생했다|
|알람 이벤트|`alarm_created`|알람이 생성되었다|
|알람 이벤트|`alarm_acknowledged`|운영자가 알람을 확인했다|
|조치 이벤트|`action_completed`|조치가 완료되었다|
|RAG 이벤트|`rag_query_submitted`|대응 매뉴얼 검색 질문이 제출되었다|
|RAG 이벤트|`rag_answer_generated`|RAG 답변이 생성되었다|
|피드백 이벤트|`feedback_submitted`|운영자 피드백이 제출되었다|
|라벨 이벤트|`alarm_labeled_false_positive`|알람이 오탐으로 분류되었다|
|품질 이벤트|`validation_failed`|데이터 검증이 실패했다|
|운영 이벤트|`data_flow_stopped`|데이터 흐름이 중단되었다|

이 중에서 초보자가 가장 먼저 이해해야 하는 핵심 이벤트는 다음이다.
```
gas_sensor_measured
→ risk_detected
→ alarm_created
→ alarm_acknowledged
→ rag_query_submitted
→ action_completed
→ feedback_submitted
```

이 흐름은 산업안전 관제플랫폼의 핵심 업무와 데이터 흐름을 동시에 보여준다.

## 6.7.4 UI 이벤트는 어떻게 다루어야 하는가?

버튼 클릭, 마우스휠, 탭 변경, 페이지 이동도 이벤트이다.  
하지만 AI 네이티브 데이터 플랫폼 과정에서는 UI 이벤트를 무조건 많이 저장하는 것이 목적이 아니다.

UI 이벤트는 다음 경우에만 중요하게 다룬다.
```
사용자 행동 분석이 필요한 경우
추천 모델에 사용자 행동이 필요한 경우
서비스 사용성을 분석해야 하는 경우
RAG 검색 결과를 사용자가 어떻게 소비했는지 알아야 하는 경우
운영자가 알람을 실제로 확인했는지 추적해야 하는 경우
```

예를 들어 다음 UI 이벤트는 데이터 플랫폼에서 의미가 있을 수 있다.

|UI 이벤트|의미 있는 데이터 이벤트로 변환|
|---|---|
|알람 상세 클릭|`alarm_detail_viewed`|
|알람 확인 버튼 클릭|`alarm_acknowledged`|
|RAG 검색 버튼 클릭|`rag_query_submitted`|
|피드백 제출 버튼 클릭|`feedback_submitted`|
|대시보드 필터 적용|`dashboard_filter_applied`|

반대로 다음 이벤트는 일반적인 AI 데이터 플랫폼에서는 우선순위가 낮다.
```
mouse_moved
mouse_wheel_scrolled
hover_started
window_resized
```

물론 콘텐츠 추천, UX 분석, 광고 분석 서비스에서는 이런 이벤트도 중요할 수 있다.  
하지만 산업안전 관제플랫폼이나 AI 데이터 플랫폼 수업에서는 먼저 업무적으로 의미 있는 이벤트부터 정의해야 한다.

---

## 6.7.5 이벤트를 정의할 때의 판단 기준

이벤트를 정의할 때는 다음 질문을 사용한다.
```
이 사건은 업무적으로 중요한가?
이 사건은 데이터로 남겨야 하는가?
이 사건은 나중에 분석, AI, RAG, 대시보드, 피드백에 사용되는가?
이 사건이 실패하면 운영상 문제가 되는가?
이 사건이 중복되면 문제가 되는가?
이 사건이 늦게 도착하면 문제가 되는가?
이 사건은 추적되어야 하는가?
```

이 질문에 대부분 “예”라고 답할 수 있다면 이벤트로 정의할 가치가 높다.

예를 들어 다음은 이벤트로 정의할 가치가 높다.
```
order_created
payment_failed
quiz_submitted
gas_sensor_measured
worker_entered_danger_zone
alarm_created
rag_answer_generated
feedback_submitted
validation_failed
pipeline_failed
```

다음은 상황에 따라 다르다.
```
button_clicked
mouse_wheel_scrolled
tab_changed
page_viewed
```

UI 이벤트는 무조건 버리는 것이 아니라, 업무 의미가 있는지 먼저 판단해야 한다.

---

## 6.7.6 최종 정리

이벤트는 크게 다음처럼 나눌 수 있다.
```
1. 도메인 업무 이벤트
2. 데이터 수집 이벤트
3. 센서/측정 이벤트
4. 위치/지오펜싱 이벤트
5. AI 판단 이벤트
6. 알람/조치 이벤트
7. RAG 문서/검색 이벤트
8. 피드백/라벨 이벤트
9. 데이터 파이프라인 이벤트
10. 데이터 품질 이벤트
11. 운영/관찰 가능성 이벤트
12. 보안/권한 이벤트
13. UI 이벤트
```

이 과정에서 가장 중요한 것은 다음이다.
```
이벤트를 단순히 화면에서 발생한 클릭으로만 보지 않는다.
이벤트를 업무와 데이터 흐름에서 발생한 중요한 사건으로 본다.
이벤트는 Raw, Staging, Mart, AI, RAG, 피드백, 운영 지표로 연결될 수 있어야 한다.
```

따라서 AI 네이티브 데이터 플랫폼 엔지니어는 이벤트를 정의할 때 다음 순서로 생각해야 한다.
```
업무 흐름에서 중요한 사건을 찾는다.
→ 그 사건이 데이터로 남아야 하는지 판단한다.
→ event_type 이름을 정한다.
→ payload에 필요한 필드를 정한다.
→ Raw 저장 기준을 정한다.
→ Staging 검증 기준을 정한다.
→ Mart와 AI/RAG/피드백 활용 기준을 정한다.
→ 운영 중 품질과 지연을 관찰할 기준을 정한다.
```
