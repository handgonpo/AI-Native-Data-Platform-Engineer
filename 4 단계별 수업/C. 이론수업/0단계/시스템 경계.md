
시스템 경계는 영어로 **System Boundary**라고 부른다.  
쉽게 말하면 다음과 같다.
```text
이번 프로젝트에서 어디까지 만들고, 어디부터는 만들지 않을지 정하는 기준
```

프로젝트를 시작하면 만들고 싶은 기능이 계속 늘어난다.
```text
결제도 붙일까?
문자 알림도 붙일까?
지도도 붙일까?
AI 모델도 붙일까?
관리자 페이지도 만들까?
실시간 대시보드도 만들까?
모바일 앱도 만들까?
```

하지만 모든 것을 한 번에 만들려고 하면 프로젝트가 끝나지 않는다.  
특히 주니어 프로젝트에서는 **무엇을 만들지 않을지 정하는 것**도 매우 중요하다.

시스템 경계를 정하는 이유는 다음과 같다.
```text
프로젝트 범위가 계속 커지는 것을 막기 위해서
수업 시간 안에 완성 가능한 목표를 정하기 위해서
팀원들이 같은 범위를 이해하도록 하기 위해서
포트폴리오에서 내가 구현한 부분을 명확히 설명하기 위해서
```

##### 10.1 시스템 경계가 필요한 이유

시스템 경계를 정하지 않으면 프로젝트가 계속 커진다.

예를 들어 쇼핑몰 데이터 플랫폼을 만든다고 가정해보자.
처음 목표는 다음처럼 단순할 수 있다.
```text
주문 데이터를 수집한다.
Raw에 저장한다.
주문 데이터를 검증한다.
주문 Mart를 만든다.
추천 후보 데이터셋을 만든다.
```

그런데 시스템 경계를 정하지 않으면 다음 요구가 계속 추가될 수 있다.
```text
실제 카드 결제도 붙이자.
실제 배송 시스템도 만들자.
문자 알림도 보내자.
쿠폰 시스템도 만들자.
리뷰 신고 기능도 만들자.
판매자 정산 기능도 만들자.
```

이렇게 되면 원래 목표였던 **데이터 플랫폼 설계**보다 쇼핑몰 전체 서비스를 만드는 일이 되어버린다.

따라서 시스템 경계는 다음 질문에 답하는 작업이다.
```text
이번 프로젝트의 핵심 목적은 무엇인가?
목적을 보여주기 위해 반드시 필요한 기능은 무엇인가?
있으면 좋지만 이번에는 만들지 않을 기능은 무엇인가?
외부 시스템이라고 가정하고 넘어갈 부분은 무엇인가?
가짜 데이터나 샘플 데이터로 대체할 부분은 무엇인가?
```

#### `[중간문제 1]`

다음 중 시스템 경계를 정하는 이유로 맞는 것을 모두 고르시오.
```text
1. 프로젝트 범위가 계속 커지는 것을 막기 위해서
2. 만들 기능과 만들지 않을 기능을 구분하기 위해서
3. 코드 파일 이름을 자동으로 만들기 위해서
4. 수업 시간 안에 완성 가능한 목표를 정하기 위해서
5. 외부 시스템으로 처리할 부분을 구분하기 위해서
```

정답:
```text
1, 2, 4, 5
```

설명:
```text
시스템 경계는 프로젝트의 범위와 책임을 정하는 기준이다.
코드 파일 이름을 자동으로 만드는 기능은 시스템 경계의 목적이 아니다.
```

##### 10.2 만드는 것과 만들지 않는 것

시스템 경계는 보통 다음 두 가지로 나누어 작성한다.
```text
만드는 것
만들지 않는 것
```

여기서 중요한 것은 “만들지 않는 것”을 부정적으로 생각하지 않는 것이다.  
만들지 않는 것을 정해야 프로젝트의 핵심 목표에 집중할 수 있다.

예를 들어 쇼핑몰 데이터 플랫폼에서는 다음처럼 정할 수 있다.
```text
만드는 것:
주문 데이터 수집
Raw 저장
Staging 검증
주문 Mart 생성
추천 후보 데이터셋 생성

만들지 않는 것:
실제 카드 결제
실제 배송 시스템
실제 문자 발송
실제 판매자 정산
실제 모바일 앱
```

이렇게 정리하면 이번 프로젝트의 목적이 분명해진다.
```text
쇼핑몰 전체 서비스를 만드는 것이 아니라,
쇼핑몰에서 발생한 주문 데이터를 수집하고 AI 추천에 활용할 수 있는 데이터 흐름을 만드는 것이다.
```

##### 10.3 산업안전 관제플랫폼 예시

산업안전 관제플랫폼 프로젝트에서도 시스템 경계가 필요하다.

예를 들어 이번 프로젝트의 목표가 다음과 같다고 하자.
```text
가스 센서, 전력 장비, 작업자 위치 데이터를 수집한다.
위험도를 판단한다.
알람을 생성한다.
대시보드에 보여준다.
AI 학습 데이터셋과 피드백 데이터를 남긴다.
```

그러면 시스템 경계는 다음처럼 정리할 수 있다.

| 구분 | 내용 |
|---|---|
| 만드는 것 | 센서 데이터 수집 API |
| 만드는 것 | Raw 데이터 저장 |
| 만드는 것 | Staging 검증 |
| 만드는 것 | 위험도 판단 Mart 생성 |
| 만드는 것 | 알람 데이터 생성 |
| 만드는 것 | 대시보드 조회 데이터 |
| 만드는 것 | AI 학습 후보 데이터셋 |
| 만드는 것 | 운영자 피드백 데이터 |
| 만들지 않는 것 | 실제 하드웨어 센서 연동 |
| 만들지 않는 것 | 실제 현장 출입 통제 장비 제어 |
| 만들지 않는 것 | 실제 문자 발송 또는 119 신고 연동 |
| 만들지 않는 것 | 실제 기업용 보안 인증 시스템 |
| 만들지 않는 것 | 실제 모바일 앱 배포 |

이렇게 정리하면 프로젝트가 명확해진다.
```text
이번 프로젝트는 실제 공장 전체 시스템을 만드는 것이 아니다.
현장 데이터가 들어왔을 때 수집, 검증, 위험도 판단, 알람, AI 데이터셋, 피드백으로 이어지는 데이터 플랫폼 흐름을 만드는 것이다.
```

##### 10.4 시스템 경계를 작성하는 방법

시스템 경계는 복잡하게 작성할 필요가 없다.  
처음에는 다음 형식으로 작성하면 충분하다.
```text
프로젝트 목적:
이번 프로젝트가 해결하려는 핵심 문제를 쓴다.

만드는 것:
이번 단계에서 직접 구현하거나 설계할 항목을 쓴다.

만들지 않는 것:
이번 프로젝트 범위에서 제외할 항목을 쓴다.

대체 방식:
만들지 않는 것을 어떻게 대신할지 쓴다.
```

예시는 다음과 같다.
```text
프로젝트 목적:
산업안전 데이터를 수집하고 위험도를 판단하여 대시보드와 AI 학습 데이터셋에 연결한다.

만드는 것:
센서 데이터 수집 API
Raw 저장
Staging 검증
위험도 Mart
알람 데이터
피드백 데이터

만들지 않는 것:
실제 센서 하드웨어 연동
실제 문자 발송
실제 현장 장비 제어

대체 방식:
센서 데이터는 샘플 JSON 또는 센서 시뮬레이터로 대체한다.
문자 발송은 로그 저장으로 대체한다.
현장 장비 제어는 알람 상태 변경으로 대체한다.
```

##### 10.5 시스템 경계를 작성할 때 주의할 점

시스템 경계를 작성할 때는 다음을 주의해야 한다.
```text
핵심 목표와 직접 관련 없는 기능은 과감히 제외한다.
실제 외부 시스템은 샘플 데이터, 로그, Mock API로 대체할 수 있다.
포트폴리오에서는 만든 것과 만들지 않은 것을 명확히 설명해야 한다.
만들지 않은 것은 실패가 아니라 범위 조정이다.
```

주니어가 자주 하는 실수는 다음과 같다.
```text
모든 기능을 다 만들려고 한다.
외부 시스템까지 직접 구현하려고 한다.
수업의 핵심인 데이터 흐름보다 화면 기능에 시간을 많이 쓴다.
만들지 않는 것을 정하지 않아 프로젝트가 계속 커진다.
```

##### 10.6 한 문장 정리

시스템 경계는 다음 한 문장으로 정리할 수 있다.
```text
시스템 경계는 이번 프로젝트에서 직접 만들 것과 외부 시스템 또는 이후 단계로 남길 것을 구분하여, 프로젝트 범위가 무리하게 커지지 않도록 하는 기준이다.
```

0단계에서 시스템 경계를 정리한다는 것은 다음을 의미한다.
```text
이번 프로젝트의 핵심 목표를 분명히 한다.
수업 시간 안에 완성 가능한 범위를 정한다.
데이터 플랫폼에서 직접 만들 데이터 흐름을 정한다.
외부 시스템으로 가정하거나 샘플 데이터로 대체할 부분을 정한다.
```

따라서 AI 네이티브 데이터 플랫폼 과정에서 시스템 경계는 단순한 범위 제한이 아니다.  
프로젝트를 끝까지 완성하기 위한 **현실적인 설계 기준**이다.
