컨벤션은 프로젝트 안에서 이름을 짓고 문서를 작성하고 코드를 관리하는 기준이다.

쉽게 말하면 다음과 같다.
```text
컨벤션 = 팀이 같은 방식으로 이름을 짓고, 같은 방식으로 파일과 코드를 관리하기 위한 약속
```

컨벤션에는 다음이 포함된다.
```text
파일명 규칙
폴더명 규칙
테이블명 규칙
이벤트명 규칙
API 경로 규칙
브랜치명 규칙
커밋 메시지 규칙
문서 작성 규칙
```

컨벤션이 없으면 팀원마다 이름을 다르게 만든다.

예를 들어 같은 “가스 센서 측정 이벤트”를 다음처럼 다르게 부를 수 있다.
```text
gas_event
gasSensorEvent
GasData
sensorGasValue
gas_sensor_measured
gas_measurement
```

이렇게 되면 나중에 다음 문제가 생긴다.
```text
어떤 이름이 기준인지 알기 어렵다.
파일을 찾기 어렵다.
API와 테이블 이름이 서로 연결되지 않는다.
이벤트명과 Schema 파일명이 달라진다.
팀원이 작성한 코드를 이해하는 시간이 길어진다.
수정할 때 실수할 가능성이 높아진다.
```

따라서 컨벤션은 단순한 취향 문제가 아니다.  
컨벤션은 프로젝트를 오래 유지보수하기 위한 기준이다.

---

##### 11.1 현업에서 컨벤션을 정하는 방식

현업에서는 보통 다음 순서로 컨벤션을 정한다.
```text
1. 사용하는 기술의 기본 스타일을 따른다.
2. 팀에서 자주 쓰는 이름 패턴을 정한다.
3. 프로젝트 도메인에 맞는 이름 규칙을 추가한다.
4. 문서로 남긴다.
5. 코드 리뷰와 자동 검사 도구로 계속 지킨다.
```

예를 들어 Python 프로젝트라면 보통 다음 기준을 따른다.
```text
Python 파일명 = 소문자 + snake_case
Python 함수명 = 소문자 + snake_case
Python 변수명 = 소문자 + snake_case
Python 클래스명 = PascalCase
상수명 = 대문자 + SNAKE_CASE
```

Django / DRF 프로젝트라면 다음처럼 정할 수 있다.
```text
앱 이름 = 짧고 명확한 소문자
Model 클래스명 = PascalCase
DB 테이블명 = 소문자 + snake_case
Serializer 클래스명 = 대상명 + Serializer
View 클래스명 = 대상명 + ViewSet 또는 APIView
URL 경로 = 복수형 리소스명 사용
```

Git 커밋 메시지는 다음처럼 정할 수 있다.
```text
feat: 새로운 기능 추가
fix: 버그 수정
docs: 문서 수정
refactor: 동작은 같지만 코드 구조 개선
test: 테스트 코드 추가 또는 수정
chore: 설정, 환경, 빌드 작업
```

중요한 것은 “세상에 하나의 정답이 있다”가 아니다.  
중요한 것은 **팀 안에서 하나의 기준을 정하고 계속 지키는 것**이다.

---

##### 11.2 컨벤션을 만들 때의 핵심 원칙

컨벤션을 만들 때는 다음 원칙을 지키면 좋다.

| 원칙 | 설명 | 예시 |
|---|---|---|
| 일관성 | 같은 개념은 항상 같은 이름으로 부른다 | `sensor_id`를 쓰기로 했으면 `sensorId`, `sensor_no`를 섞지 않는다 |
| 명확성 | 이름만 봐도 의미가 보여야 한다 | `data1`보다 `gas_sensor_event`가 좋다 |
| 짧지만 충분하게 | 너무 길지 않되 의미는 남긴다 | `gas_sensor_measured` |
| 도메인 기준 | 업무에서 쓰는 핵심 단어를 사용한다 | `alarm`, `risk`, `zone`, `worker` |
| 기술 기준 준수 | Python, Django, Git 등 도구의 일반 스타일을 따른다 | 함수명은 `snake_case`, 클래스명은 `PascalCase` |
| 검색 가능성 | 파일과 코드 검색이 쉬워야 한다 | 이벤트명과 파일명을 맞춘다 |
| 확장 가능성 | 나중에 이벤트나 기능이 늘어나도 규칙이 깨지지 않아야 한다 | `도메인_행위_상태` 구조 사용 |

##### 11.3 이름 표기 방식 기본 정리

컨벤션을 이해하려면 먼저 이름 표기 방식을 알아야 한다.

| 표기 방식 | 예시 | 주로 쓰는 곳 |
|---|---|---|
| snake_case | `gas_sensor_measured` | Python 파일명, 함수명, 변수명, DB 테이블명, 이벤트명 |
| PascalCase | `GasSensorMeasuredEvent` | Python 클래스명, Django Model, Pydantic 클래스 |
| camelCase | `gasSensorMeasured` | JavaScript 변수명, 일부 JSON 스타일 |
| kebab-case | `gas-sensor-measured` | URL, 브랜치명, 일부 파일명 |
| UPPER_SNAKE_CASE | `MAX_RETRY_COUNT` | 상수 |

이 과정에서는 Python, Django, 데이터 파이프라인을 함께 사용하므로 기본적으로 다음 기준을 추천한다.
```text
파일명 = snake_case
폴더명 = snake_case
Python 함수명 = snake_case
Python 클래스명 = PascalCase
이벤트명 = snake_case
DB 테이블명 = snake_case
API 경로 = kebab-case 또는 복수형 리소스
브랜치명 = slash + snake_case 또는 kebab-case
커밋 메시지 = type(scope): 설명
```

##### 11.4 AI 네이티브 데이터 플랫폼 프로젝트 추천 컨벤션

아래는 이 과정에서 사용할 수 있는 추천 컨벤션이다.

| 구분 | 추천 규칙 | 예시 |
|---|---|---|
| 프로젝트 폴더 | 소문자 + snake_case | `ai_native_data_platform` |
| 앱 폴더 | 소문자 + snake_case | `collector`, `pipeline`, `dashboard` |
| 문서 파일 | 소문자 또는 한글 제목 + snake_case | `data_contract.md`, `branch_strategy.md` |
| 샘플 이벤트 파일 | 이벤트명 + `.sample.json` | `gas_sensor_measured.sample.json` |
| 오류 샘플 파일 | 이벤트명 + 오류유형 + `.sample.json` | `gas_sensor_measured.invalid_type.sample.json` |
| Schema 파일 | 이벤트명 + `.schema.json` | `gas_sensor_measured.schema.json` |

| Python 클래스 | PascalCase | `GasSensorMeasuredEvent` |
| Python 함수 | 동사 + 대상 | `validate_gas_sensor_event()` |
| Django Model | 단수형 PascalCase | `GasSensorEvent` |
| DB 테이블 | 복수형 snake_case | `gas_sensor_events` |
| API 경로 | 복수형 리소스 | `/api/gas-events/` |
| 브랜치명 | 단계/작업명 | `lesson/02_data_collection` |
| 커밋 메시지 | type(scope): 설명 | `feat(collector): add gas event validation` |

##### 11.5 이벤트명 컨벤션

이벤트명은 데이터 플랫폼에서 매우 중요하다.  
이벤트명은 API, Schema, Raw 저장 경로, 처리 함수, 샘플 파일 이름과 연결되기 때문이다.

추천 규칙은 다음과 같다.
```text
이벤트명 = 대상 + 동작 + 상태
```

예시는 다음과 같다.

| 업무 사건 | 이벤트명 |
|---|---|
| 가스 센서값이 측정되었다 | `gas_sensor_measured` |
| 전력 사용량이 측정되었다 | `power_usage_measured` |
| 작업자 위치가 갱신되었다 | `worker_location_updated` |
| 위험 이벤트가 탐지되었다 | `risk_event_detected` |
| 알람이 생성되었다 | `alarm_created` |
| 운영자 피드백이 제출되었다 | `feedback_submitted` |
| RAG 매뉴얼이 검색되었다 | `rag_manual_retrieved` |

좋지 않은 예시는 다음과 같다.

| 좋지 않은 이름 | 문제 |
|---|---|
| `gas` | 너무 넓고 사건이 보이지 않는다 |
| `sensor_data` | 어떤 센서인지, 어떤 사건인지 알기 어렵다 |
| `data_created` | 어떤 데이터인지 알 수 없다 |
| `gasEvent` | Python/데이터 파일 기준과 섞인다 |
| `GasSensorMeasured` | 이벤트명으로는 보통 snake_case가 더 적합하다 |

##### 11.8 API 경로 컨벤션

API 경로는 “무엇을 다루는 API인지”가 보여야 한다.

추천 규칙은 다음과 같다.
```text
/api/리소스명/
```

리소스명은 보통 복수형으로 쓴다.

| 목적 | API 경로 예시 |
|---|---|
| 가스 이벤트 수집 | `POST /api/gas-events/` |

주의할 점은 동사를 API 경로에 너무 많이 넣지 않는 것이다.

| 좋지 않은 API | 개선 예시 |

##### 11.10 커밋 메시지 컨벤션

커밋 메시지는 변경 내용을 짧고 명확하게 남기는 기록이다.

추천 규칙은 다음과 같다.
```text
type(scope): 변경 내용
```

자주 쓰는 type은 다음과 같다.

| type | 의미 | 예시 |
|---|---|---|
| feat | 새로운 기능 추가 | `feat(collector): add gas event endpoint` |
| fix | 버그 수정 | `fix(validation): handle missing sensor_id` |
| docs | 문서 수정 | `docs(contract): update gas event schema` |
| refactor | 구조 개선 | `refactor(pipeline): split staging validation` |
| test | 테스트 추가/수정 | `test(schema): add invalid unit sample` |
| chore | 설정/환경 작업 | `chore(git): update .gitignore` |

좋은 커밋 메시지 예시는 다음과 같다.
```text
feat(collector): add gas sensor event API
fix(staging): reject invalid gas unit
docs(contract): add gas_sensor_measured data contract
test(validation): add missing sensor_id sample
```

좋지 않은 커밋 메시지 예시는 다음과 같다.
```text
수정
작업함
최종
오류 수정
진짜 최종 수정
```

이런 메시지는 나중에 어떤 변경인지 추적하기 어렵다.

##### 11.11 문서 작성 컨벤션

문서도 컨벤션이 필요하다.

문서 제목, 표, 코드 블록, 예시 작성 방식이 매번 달라지면 읽는 사람이 피로해진다.

추천 규칙은 다음과 같다.
```text
문서 제목은 명확하게 작성한다.
각 문서는 목적, 작성 기준, 예시, 확인 문제 순서로 구성한다.
코드나 명령어는 코드 블록으로 작성한다.
표는 기준을 비교할 때 사용한다.
중요한 용어는 한 줄 정의로 먼저 설명한다.
```

문서 구조 예시는 다음과 같다.
```md
# 데이터 계약 정의

## 1. 목적
이 문서가 왜 필요한지 설명한다.

## 2. 핵심 개념
주요 용어를 짧게 설명한다.

## 3. 작성 기준
어떤 규칙으로 작성할지 설명한다.

## 4. 예시
실제 프로젝트 예시를 작성한다.

## 5. 확인 문제
이해했는지 점검한다.
```

##### 11.12 컨벤션 문서 샘플

아래는 프로젝트에서 바로 사용할 수 있는 컨벤션 문서 예시이다.
```md
# 프로젝트 컨벤션

## 1. 목적

이 문서는 AI 네이티브 데이터 플랫폼 프로젝트에서 사용하는 이름 짓기와 작성 규칙을 정의한다.

## 2. 기본 원칙

- 같은 개념은 같은 이름으로 부른다.
- 파일명, 이벤트명, 테이블명은 가능한 한 서로 연결되게 만든다.
- Python 코드는 snake_case와 PascalCase 규칙을 따른다.
- 커밋 메시지는 `type(scope): 설명` 형식을 사용한다.

## 3. 이벤트명 규칙

이벤트명은 `대상_동작_상태` 형태로 작성한다.

| 업무 사건 | 이벤트명 |
|---|---|
| 가스 센서값이 측정되었다 | `gas_sensor_measured` |
| 알람이 생성되었다 | `alarm_created` |
| 피드백이 제출되었다 | `feedback_submitted` |

## 4. 파일명 규칙

| 파일 종류 | 규칙 | 예시 |
|---|---|---|
| 문서 | 소문자 snake_case | `data_contract.md` |
| Schema | 이벤트명 + `.schema.json` | `gas_sensor_measured.schema.json` |
| 샘플 JSON | 이벤트명 + `.sample.json` | `gas_sensor_measured.sample.json` |
| Python 파일 | 소문자 snake_case | `validate_events.py` |

## 5. 테이블명 규칙

| 계층 | 규칙 | 예시 |
|---|---|---|
| Raw | `raw_도메인_이벤트명` | `raw_gas_sensor_events` |
| Staging | `stg_도메인_데이터명` | `stg_gas_measurements` |
| Mart | `mart_목적_데이터명` | `mart_zone_risk_summary` |

## 6. API 경로 규칙

API 경로는 복수형 리소스를 사용한다.

| 목적 | 경로 |
|---|---|
| 가스 이벤트 수집 | `POST /api/gas-events/` |
| 알람 목록 조회 | `GET /api/alarms/` |
| 피드백 제출 | `POST /api/feedback/` |

## 7. 브랜치명 규칙

| 목적 | 예시 |
|---|---|
| 수업 단계 | `lesson/02_data_collection_lakehouse` |
| 기능 개발 | `feature/gas-event-collector` |
| 오류 수정 | `fix/staging-validation-error` |
| 문서 수정 | `docs/update-data-contract` |

## 8. 커밋 메시지 규칙

커밋 메시지는 다음 형식을 따른다.

```text
type(scope): 설명


예시는 다음과 같다.

```text
feat(collector): add gas sensor event API
fix(validation): reject invalid gas unit
docs(contract): update gas event schema
```

##### 11.13 컨벤션을 지키기 위한 방법

컨벤션은 정하는 것보다 지키는 것이 더 어렵다.

현업에서는 보통 다음 방법으로 컨벤션을 지킨다.
```text
README 또는 docs에 컨벤션 문서를 둔다.
새 파일을 만들기 전에 기존 이름 패턴을 먼저 확인한다.
코드 리뷰에서 이름과 구조를 함께 확인한다.
pre-commit, formatter, linter 같은 자동 검사 도구를 사용한다.
팀원이 헷갈릴 때는 컨벤션 문서를 먼저 업데이트한다.
```

주니어가 기억해야 할 기준은 다음이다.
```text
내가 새 이름을 만들기 전에, 이미 비슷한 이름이 있는지 먼저 찾는다.
비슷한 개념은 같은 단어를 사용한다.
한 번 정한 이벤트명은 API, Schema, 파일명, 테이블명에 반복해서 사용한다.
```

예를 들어 `gas_sensor_measured`를 이벤트명으로 정했다면 다음처럼 연결한다.

| 구분 | 이름 |
|---|---|
| 이벤트명 | `gas_sensor_measured` |
| Schema 파일 | `gas_sensor_measured.schema.json` |
| 샘플 파일 | `gas_sensor_measured.sample.json` |
| Python 클래스 | `GasSensorMeasuredEvent` |
| 검증 함수 | `validate_gas_sensor_measured()` |
| Raw 경로 | `data_lake/raw/gas_sensor_measured/` |
| Raw 테이블 | `raw_gas_sensor_events` |

이렇게 하면 프로젝트 전체에서 하나의 기준 이름이 흐르게 된다.

##### 11.14 주니어가 자주 하는 실수

컨벤션을 만들 때 주니어가 자주 하는 실수는 다음과 같다.
```text
영어와 한글 이름을 섞어서 사용한다.
snake_case와 camelCase를 섞어서 사용한다.
같은 의미의 단어를 여러 개 사용한다.
파일명을 final, real_final처럼 만든다.
이벤트명과 파일명이 연결되지 않는다.
테이블명에서 Raw, Staging, Mart 구분이 보이지 않는다.
커밋 메시지를 “수정”, “작업함”처럼 작성한다.
문서마다 제목과 표 형식이 다르다.
```

좋은 컨벤션은 복잡한 규칙이 아니다.  
좋은 컨벤션은 팀원이 봤을 때 “아, 이 이름은 이런 의미구나”라고 바로 이해되는 규칙이다.
