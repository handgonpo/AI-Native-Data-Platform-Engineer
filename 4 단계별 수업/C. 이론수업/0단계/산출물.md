
산출물은 프로젝트가 끝났을 때 남기는 결과물이다.

쉽게 말하면 다음과 같다.
```text
산출물 = 내가 무엇을 설계했고, 무엇을 만들었고, 무엇을 검증했는지 보여주는 증거
```

수업이나 프로젝트를 진행하면 많은 작업을 한다.
```text
문서를 작성한다.
코드를 만든다.
샘플 데이터를 만든다.
API를 구현한다.
테이블을 설계한다.
대시보드를 만든다.
테스트를 실행한다.
최종 시연을 한다.
```

하지만 작업을 했다는 사실만으로는 포트폴리오가 되지 않는다.  
나중에 누군가가 봤을 때 다음 질문에 답할 수 있어야 한다.
```text
이 프로젝트는 어떤 문제를 해결하려고 했는가?
어떤 데이터를 사용했는가?
어떤 구조로 설계했는가?
어떤 코드를 작성했는가?
어떤 기준으로 검증했는가?
최종적으로 무엇이 동작하는가?
```

이 질문에 답할 수 있도록 남겨두는 결과물이 산출물이다.

---

##### 12.1 산출물이 필요한 이유

산출물이 없으면 프로젝트가 끝난 뒤에 설명하기 어렵다.
```text
무엇을 만들었는지 기억에 의존하게 된다.
왜 그런 구조로 만들었는지 설명하기 어렵다.
팀원이 작업한 내용을 추적하기 어렵다.
면접이나 발표에서 증거를 보여주기 어렵다.
다음 단계 개발자가 이어받기 어렵다.
```

반대로 산출물이 있으면 다음이 가능하다.
```text
프로젝트 목적을 설명할 수 있다.
데이터 흐름을 설명할 수 있다.
코드와 문서가 연결된다.
팀원이 같은 기준으로 작업했는지 확인할 수 있다.
수업 결과물이 포트폴리오로 남는다.
면접에서 “왜 이렇게 만들었는지” 설명할 수 있다.
```

따라서 산출물은 단순 제출물이 아니다.  
산출물은 프로젝트의 설계, 구현, 검증, 시연 결과를 남기는 기록이다.

---

##### 12.2 산출물의 종류

산출물은 크게 다섯 가지로 나눌 수 있다.
```text
문서 산출물
코드 산출물
데이터 산출물
검증 산출물
시연/포트폴리오 산출물
```

| 산출물 종류 | 의미 | 예시 |
|---|---|---|
| 문서 산출물 | 프로젝트 기준과 설계를 설명하는 문서 | README, 문제 정의서, 데이터 계약 문서 |
| 코드 산출물 | 실제 동작하는 프로그램 코드 | API 코드, 파이프라인 코드, 검증 코드 |
| 데이터 산출물 | 실습과 검증에 사용하는 데이터 파일 | 샘플 JSON, 테스트 CSV, Raw 예시 |
| 검증 산출물 | 제대로 동작했는지 확인한 결과 | 테스트 결과, 품질 리포트, 실행 로그 |
| 시연/포트폴리오 산출물 | 최종 결과를 보여주는 자료 | 시연 시나리오, 화면 캡처, 발표 자료 |

---

##### 12.3 0단계에서 남겨야 하는 산출물

0단계는 본격적으로 코드를 구현하는 단계가 아니다.  
0단계의 목적은 프로젝트를 시작하기 전에 기준을 정리하는 것이다.

따라서 0단계에서는 다음 산출물이 중요하다.

| 산출물 | 형태 | 의미 |
|---|---|---|
| `README.md` | 문서 | 프로젝트 전체 소개와 실행 기준 |
| 프로젝트 개요 문서 | 문서 | 프로젝트 목적, 대상 사용자, 해결 문제 정리 |
| 문제 정의 문서 | 문서 | 현재 어떤 문제가 있고 왜 해결해야 하는지 정리 |
| 도메인 정의 문서 | 문서 | 프로젝트가 다루는 업무 영역과 핵심 용어 정리 |
| 사용자 역할 문서 | 문서 | 관리자, 운영자, 사용자, 외부 시스템 역할 정리 |
| 데이터 소스 맵 | 문서/표 | 데이터가 어디서 발생하고 어떻게 들어오는지 정리 |
| 이벤트 후보 목록 | 문서/표 | 프로젝트에서 발생하는 중요한 사건 정리 |
| 데이터 흐름도 | Mermaid/이미지 | 데이터가 Raw, Staging, Mart, AI로 이동하는 흐름 |
| 데이터 계약 후보 문서 | 문서 | 이벤트별 필드, 타입, 단위, 오류 기준 초안 |
| 네이밍 컨벤션 문서 | 문서 | 파일명, 이벤트명, 테이블명, 브랜치명 규칙 |
| 폴더 구조 문서 | 문서/트리 | 프로젝트 폴더와 파일 배치 기준 |
| 브랜치 전략 문서 | 문서 | 단계별 Git 브랜치 운영 기준 |
| 시스템 경계 문서 | 문서 | 만들 것과 만들지 않을 것의 범위 |
| 최종 시연 시나리오 | 문서 | 마지막에 어떤 흐름을 보여줄지 정리 |
| 완료 체크리스트 | 문서/체크리스트 | 0단계 완료 기준 확인 |

---

##### 12.4 산출물은 문서만 의미하는가?

산출물은 문서만 의미하지 않는다.

산출물에는 문서, 코드, 데이터, 실행 결과가 모두 포함된다.

예를 들어 AI 네이티브 데이터 플랫폼 과정에서는 다음이 모두 산출물이 될 수 있다.
```text
README.md
docs/data_contract.md
schemas/gas_sensor_measured.schema.json
sample_events/gas_sensor_measured.sample.json
collector/views.py
pipeline/build_staging.py
pipeline/build_mart.py
data_lake/raw/sample.jsonl
reports/quality_report.md
screenshots/dashboard_result.png
demo/final_demo_scenario.md
```

즉, 산출물은 다음 세 가지 질문에 답해야 한다.
```text
무엇을 설계했는가?
무엇을 구현했는가?
무엇이 동작했는가?
```

---

##### 12.5 산출물 예시: 문서 산출물

문서 산출물은 프로젝트를 설명하기 위한 결과물이다.

| 문서 | 설명 | 작성 위치 예시 |
|---|---|---|
| README.md | 프로젝트 전체 소개, 실행 방법, 폴더 구조 요약 | `README.md` |
| 프로젝트 개요 | 목적, 사용자, 핵심 기능 정리 | `docs/project_overview.md` |
| 문제 정의서 | 해결하려는 문제와 필요성 정리 | `docs/problem_definition.md` |
| 도메인 정의서 | 주요 도메인 용어와 업무 개념 정리 | `docs/domain_definition.md` |
| 데이터 소스 맵 | 데이터 발생 위치와 수집 방식 정리 | `docs/data_source_map.md` |
| 데이터 계약 문서 | 이벤트별 필드, 타입, 검증 기준 정리 | `docs/data_contract.md` |
| 컨벤션 문서 | 이름 짓기와 작성 규칙 정리 | `docs/naming_convention.md` |
| 시스템 경계 문서 | 만들 것과 만들지 않을 것 정리 | `docs/system_boundary.md` |
| 브랜치 전략 문서 | 단계별 브랜치 운영 방식 정리 | `docs/branch_strategy.md` |

문서 산출물은 “코드를 설명하는 글”이 아니라,  
코드를 작성하기 전에 기준을 정하고, 코드를 작성한 뒤에는 이유를 설명하는 자료이다.

---

##### 12.6 산출물 예시: 코드 산출물

코드 산출물은 실제 동작하는 프로그램이다.

| 코드 산출물 | 설명 | 예시 |
|---|---|---|
| API 코드 | 데이터를 받거나 조회하는 입구 | Collector API, DRF API |
| Schema 코드 | 데이터 구조와 타입 정의 | Pydantic Model, DRF Serializer |
| 검증 코드 | 필수값, 타입, 단위, 범위 검사 | `validate_event()` |
| Raw 저장 코드 | 원본 데이터를 저장하는 코드 | JSONL 저장, Raw 테이블 저장 |
| Staging 코드 | 검증된 데이터로 변환하는 코드 | `build_staging.py` |
| Mart 코드 | 목적별 데이터셋을 만드는 코드 | `build_mart.py` |
| 테스트 코드 | 정상/오류 동작 확인 | `tests/test_validation.py` |
| 설정 파일 | 실행 환경과 의존성 관리 | `requirements.txt`, `.gitignore` |

코드 산출물은 단순히 파일이 존재한다고 끝나는 것이 아니다.  
실행 가능해야 하고, 어떤 역할을 하는지 문서와 연결되어야 한다.

---

##### 12.7 산출물 예시: 데이터 산출물

데이터 산출물은 실습과 검증에 사용하는 데이터 파일이다.

| 데이터 산출물 | 설명 | 예시 |
|---|---|---|
| 정상 샘플 JSON | 데이터 계약에 맞는 정상 이벤트 | `gas_sensor_measured.sample.json` |
| 오류 샘플 JSON | 검증 실패를 확인하기 위한 데이터 | `gas_sensor_measured.invalid_type.sample.json` |
| Raw 예시 | 수집된 원본 데이터 예시 | `data_lake/raw/gas_events/sample.jsonl` |
| Staging 예시 | 검증 후 정리된 데이터 예시 | `data_lake/staging/gas_measurements/sample.parquet` |
| Mart 예시 | 목적별 가공 데이터 예시 | `data_lake/mart/zone_risk_summary/sample.parquet` |
| 테스트 데이터 | 테스트 실행용 데이터 | `tests/fixtures/gas_events.json` |

데이터 산출물을 남기는 이유는 다음과 같다.
```text
API가 어떤 데이터를 받는지 보여줄 수 있다.
검증 로직이 어떤 데이터를 통과시키고 거부하는지 확인할 수 있다.
Raw, Staging, Mart 차이를 눈으로 확인할 수 있다.
AI 학습 데이터셋이 어떤 형태인지 설명할 수 있다.
```

---

##### 12.8 산출물 예시: 검증 산출물

검증 산출물은 프로젝트가 제대로 동작했는지 확인한 결과이다.

| 검증 산출물 | 설명 | 예시 |
|---|---|---|
| 테스트 결과 | 테스트 실행 성공 여부 | `pytest` 결과 |
| 품질 리포트 | 누락, 타입 오류, 중복, 지연 데이터 현황 | `reports/data_quality_report.md` |
| 실행 로그 | API 수집, 파이프라인 실행 기록 | `logs/pipeline_run.log` |
| 검증 실패 목록 | Dead Letter에 저장된 오류 데이터 | `data_lake/dead_letter/` |
| 완료 체크리스트 | 단계별 완료 여부 확인 | `docs/checklist_stage_00.md` |

검증 산출물은 특히 중요하다.  
왜냐하면 “만들었다”와 “정상적으로 동작했다”는 다른 말이기 때문이다.
```text
만들었다 = 코드나 문서를 작성했다.
검증했다 = 실제로 실행하고 결과를 확인했다.
```

포트폴리오에서는 이 차이가 중요하다.

##### 12.9 산출물 예시: 시연/포트폴리오 산출물

시연/포트폴리오 산출물은 최종 결과를 보여주기 위한 자료이다.

| 산출물 | 설명 | 예시 |
|---|---|---|
| 최종 시연 시나리오 | 어떤 순서로 프로젝트를 보여줄지 정리 | `demo/final_demo_scenario.md` |
| 화면 캡처 | 대시보드, API 응답, 실행 결과 이미지 | `screenshots/dashboard.png` |
| 발표 자료 | 프로젝트 소개와 핵심 구조 설명 | `presentation/final_presentation.pdf` |
| 포트폴리오 요약 | 이력서나 GitHub에 넣을 설명 | `docs/portfolio_summary.md` |
| 회고 문서 | 어려웠던 점, 해결한 점, 개선할 점 정리 | `docs/retrospective.md` |

시연 산출물은 기술을 모르는 사람도 이해할 수 있어야 한다.
```text
무슨 문제를 해결했는가?
어떤 데이터가 들어오는가?
어떻게 처리되는가?
최종 화면에서 무엇을 볼 수 있는가?
내가 맡은 역할은 무엇인가?
```

##### 12.10 산출물은 늘어날 수 있는가?

산출물은 프로젝트 상황에 따라 늘어날 수 있다.  
하지만 아무 문서나 계속 추가하면 오히려 관리가 어려워진다.

현업에서는 보통 다음 기준에 해당할 때 산출물을 추가한다.

| 추가 기준 | 설명 | 예시 |
|---|---|---|
| 의사결정이 필요한가? | 팀이 기준을 맞춰야 하는 내용인가? | 시스템 경계 문서, 컨벤션 문서 |
| 반복해서 참조되는가? | 여러 단계에서 계속 참고해야 하는가? | 데이터 계약 문서, API 명세 |
| 실행과 검증에 필요한가? | 실제 코드를 실행하거나 테스트하는 데 필요한가? | 샘플 JSON, 테스트 데이터 |
| 인수인계가 필요한가? | 다른 사람이 이어받아야 하는가? | 폴더 구조 문서, 실행 가이드 |
| 포트폴리오 증거가 되는가? | 결과를 설명할 때 필요한가? | 시연 시나리오, 화면 캡처 |
| 운영에 필요한가? | 장애, 품질, 배포를 확인해야 하는가? | 품질 리포트, 로그, 체크리스트 |

산출물을 추가하지 않아도 되는 경우도 있다.
```text
한 번만 보고 버릴 내용
이미 README에 충분히 설명된 내용
다른 문서와 거의 중복되는 내용
관리할 사람이 없는 문서
프로젝트 목적과 관련 없는 자료
```

즉, 산출물은 많을수록 좋은 것이 아니다.  
필요한 산출물이 정확한 위치에 있고, 계속 관리되는 것이 중요하다.

---

##### 12.11 현업에서 산출물을 관리하는 방식

현업에서는 산출물을 보통 다음 방식으로 관리한다.
```text
Git 저장소에 문서와 코드를 함께 관리한다.
docs 폴더에 설계 문서를 둔다.
sample_events 또는 fixtures 폴더에 샘플 데이터를 둔다.
reports 폴더에 실행 결과와 품질 리포트를 둔다.
screenshots 또는 demo 폴더에 시연 자료를 둔다.
변경 사항은 커밋 메시지와 Pull Request로 기록한다.
중요 문서는 README에서 링크로 연결한다.
```

추천 폴더 구조는 다음과 같다.
```text
project-root/
├── README.md
├── docs/
│   ├── project_overview.md
```

##### 12.12 산출물 관리 기준

산출물은 다음 기준으로 관리하면 좋다.

| 관리 기준 | 설명 |
|---|---|
| 위치 기준 | 문서, 코드, 데이터, 리포트를 정해진 폴더에 저장한다 |
| 이름 기준 | 컨벤션에 맞는 파일명을 사용한다 |
| 버전 기준 | 변경 이력은 Git 커밋으로 남긴다 |
| 연결 기준 | README에서 주요 산출물로 이동할 수 있게 링크한다 |
| 완료 기준 | 각 산출물이 어떤 상태이면 완료인지 정한다 |
| 검토 기준 | 중요한 산출물은 팀원 리뷰를 거친다 |
| 보관 기준 | 포트폴리오에 필요한 결과는 삭제하지 않고 남긴다 |

예를 들어 데이터 계약 문서의 완료 기준은 다음처럼 정할 수 있다.
```text
이벤트명이 작성되어 있다.
필수 필드와 선택 필드가 구분되어 있다.
필드 타입과 단위가 작성되어 있다.
정상 샘플과 오류 샘플이 있다.
오류 처리 기준이 작성되어 있다.
Raw, Staging, Mart 연결이 설명되어 있다.
```

##### 12.13 단계별 산출물 예시

AI 네이티브 데이터 플랫폼 과정에서는 단계별로 산출물을 나누어 관리하면 좋다.

| 단계 | 주요 산출물 |
|---|---|
| 0단계 기준선 | README, 문제 정의서, 도메인 정의서, 데이터 소스 맵, 컨벤션 문서 |
| 1단계 아키텍처 | 시스템 구조도, 이벤트 목록, API 후보 목록, 폴더 구조 |
| 2단계 데이터 수집 | Collector API, 데이터 계약, Schema, 샘플 JSON, Raw 저장 결과 |
| 3단계 파이프라인 | Staging 변환 코드, Mart 생성 코드, 품질 리포트 |
| 4단계 대시보드/AI | 대시보드 화면, AI 학습 데이터셋, 예측 결과 |
| 5단계 RAG | 문서 수집 결과, 임베딩 데이터, 검색 로그, 답변 로그 |
| 6단계 피드백/DataOps | 피드백 데이터, 재학습 후보 데이터셋, 운영 리포트 |
| 최종 | 시연 시나리오, 발표 자료, 포트폴리오 요약, 회고 문서 |

##### 12.15 산출물 완료 기준

산출물은 “파일이 있다”만으로 완료가 아니다.  
다음 기준을 만족해야 한다.
```text
파일명이 컨벤션에 맞다.
정해진 폴더에 있다.
내용이 프로젝트 목적과 연결된다.
다른 산출물과 중복되지 않는다.
README에서 찾을 수 있다.
팀원이 봐도 이해할 수 있다.
나중 단계에서 실제로 참고할 수 있다.
```

예를 들어 `data_contract.md`가 있다고 해도 다음 상태라면 완료로 보기 어렵다.
```text
필드명만 있고 타입이 없다.
필수 필드와 선택 필드가 구분되어 있지 않다.
정상 샘플만 있고 오류 샘플이 없다.
Raw, Staging, Mart와 연결되지 않는다.
```

반대로 좋은 산출물은 다음과 같다.
```text
무엇을 설명하는 문서인지 제목에서 알 수 있다.
표와 예시가 있다.
작성 기준이 명확하다.
이후 코드 구현과 연결된다.
확인 문제나 체크리스트가 있다.
```

##### 12.16 주니어가 자주 하는 실수

주니어가 산출물을 만들 때 자주 하는 실수는 다음과 같다.
```text
문서를 너무 많이 만들고 관리하지 않는다.
파일 이름이 중복되거나 기준이 없다.
README에 주요 산출물 링크를 남기지 않는다.
코드는 있는데 실행 결과가 없다.
샘플 데이터는 있는데 오류 데이터가 없다.
최종 시연 시나리오가 없다.
무엇이 완료인지 기준을 정하지 않는다.
문서와 코드가 서로 다른 내용을 말한다.
```

산출물은 많다고 좋은 것이 아니다.  
적절한 산출물을 끝까지 관리하는 것이 더 중요하다.

```text
1, 2, 3, 5
```

```text
산출물은 프로젝트 설명, 구현, 검증, 시연에 필요한 결과물이다.
```

```text
2
```

```text
3
```

```text
이미 다른 문서와 완전히 중복되는 문서는 새 산출물로 추가하기보다 기존 문서에 통합하는 것이 좋다.
```
