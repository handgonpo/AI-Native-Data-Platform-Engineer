# 1. 프로젝트 이름

```text
온라인 쇼핑몰 주문 이벤트 데이터 수집 미니 프로젝트
```
이 프로젝트는 쇼핑몰 전체를 만드는 프로젝트가 아니다.

다음 데이터 흐름만 작게 구현한다.
```text
주문 생성 이벤트 발생
→ 이벤트 데이터 수집
→ 데이터 계약 검증
→ 원본 보존
→ 분석 가능한 구조로 변환
→ SQL 조회
```

---

# 2. 프로젝트 목적

온라인 쇼핑몰에서 주문이 생성되면 주문 데이터가 발생한다.

이 데이터를 단순히 업무 데이터베이스에만 저장하는 것이 아니라, 이후 다음 목적으로 활용할 수 있도록 별도의 데이터 흐름으로 수집한다.
```text
일별 주문 건수 분석
매출 집계
고객별 구매 분석
추천 시스템 Feature 생성
이상 주문 탐지
AI 학습 데이터셋 생성
데이터 품질 점검
과거 주문 데이터 재처리
```
따라서 프로젝트 목적은 다음과 같다.

> 쇼핑몰 주문 생성 데이터를 일관된 이벤트 형식으로 수집하고, 데이터 계약에 따라 검증한 뒤, 원본과 오류 데이터를 구분하여 보존하고, 분석 가능한 Staging 데이터로 변환한다.

---

# 3. 해결하려는 문제

쇼핑몰 주문 데이터를 아무 기준 없이 수집하면 다음 문제가 발생할 수 있다.
```text
주문 ID가 없는 데이터가 들어온다.
금액이 문자열이나 음수로 들어온다.
상품 개수가 0으로 들어온다.
날짜 형식이 서로 다르다.
어떤 시스템에서 만든 데이터인지 알 수 없다.
오류 데이터를 삭제해서 원인을 추적하지 못한다.
중첩 JSON이라 SQL 분석이 불편하다.
원본과 분석용 데이터가 섞인다.
```

이 프로젝트는 위 문제를 다음 구조로 해결한다.

| 문제 | 해결 방법 |
|---|---|
| 데이터 구조가 제각각임 | Pydantic 데이터 계약 |
| 오류 데이터가 정상 데이터와 섞임 | Raw와 Dead Letter 분리 |
| 원본을 다시 확인하기 어려움 | Raw JSONL 보존 |
| 중첩된 `payload` 분석이 불편함 | Staging에서 평탄화 |
| 날짜·금액·상품 수의 타입이 다름 | pandas로 타입 표준화 |
| 분석용 DB 서버를 따로 준비해야 함 | DuckDB로 Parquet 직접 조회 |

# 4. 프로젝트 범위

`포함 범위`
```text
주문 생성 이벤트 정의
정상·오류 Sample JSON 작성
FastAPI Collector API
Pydantic 데이터 계약
Raw JSONL 저장
Dead Letter JSONL 저장

Staging Parquet 저장

```


`제외 범위`
다음 기능은 현재 미니 프로젝트의 범위가 아니다.
```text

상품 등록
장바구니
결제 승인
배송 처리
주문 취소
환불
실제 운영용 쇼핑몰 데이터베이스
대시보드 화면
추천 AI 모델
Airflow 자동화
Kafka 실시간 스트리밍
```

이 범위를 명확히 해야 프로젝트가 작은 실습으로 유지된다.

# 5. 최종 시연 시나리오

이 프로젝트가 완성되면 다음 흐름을 시연한다.
```text
1. Collector 서버를 실행한다.
2. 정상 주문 JSON을 API로 보낸다.
3. 정상 주문이 Raw JSONL에 저장되는지 확인한다.
4. 오류 주문 JSON을 API로 보낸다.
5. 오류 원본과 오류 이유가 Dead Letter에 저장되는지 확인한다.
6. Raw JSONL을 Staging Parquet으로 변환한다.
7. payload가 평탄화되었는지 확인한다.
8. DuckDB SQL로 주문 데이터와 주문 요약을 조회한다.
```

# 8. 도메인은 무엇인가?

도메인은 프로젝트가 다루는 업무 영역이다.

이 미니 프로젝트의 도메인은 다음과 같다.
```text
온라인 쇼핑몰의 주문 업무
```

쇼핑몰 전체에는 회원, 상품, 장바구니, 주문, 결제, 배송, 환불 등 여러 업무가 있다.

하지만 이번 실습에서는 범위를 다음으로 제한한다.
```text
고객이 주문을 완료하여
새로운 주문이 생성되는 순간
```

따라서 핵심 도메인 이벤트는 다음과 같다.
```text
order_created
```

---

# 9. 도메인 요소 정의

도메인 요소는 업무 안에 등장하는 핵심 대상이다.

| 도메인 요소 | 설명 | 코드에서 표현되는 값 |
|---|---|---|
| 고객 `Customer` | 주문을 생성한 사용자 | `customer_id` |
| 주문 `Order` | 고객이 생성한 구매 요청 | `order_id` |
| 주문 상품 `Order Item` | 주문에 포함된 상품 | 개별 상품 대신 `item_count`로 축약 |
| 주문 금액 | 주문 상품의 총금액 | `total_amount` |
| 통화 | 금액을 해석하는 화폐 단위 | `currency` |
| 쇼핑몰 시스템 | 주문 이벤트를 생산하는 시스템 | `source_system` |
| 주문 이벤트 | 주문 생성 사실을 전달하는 데이터 | `OrderCreatedEvent` |
| Collector | 이벤트를 받는 시스템 | FastAPI |
| Data Lake | 이벤트를 단계별로 보관하는 저장 영역 | `data_lake/` |

현재 실습에서는 주문 상품 목록 전체를 받지 않는다.

예를 들어 실제 쇼핑몰에서는 다음처럼 상품 배열이 들어올 수 있다.
```json
{
  "items": [
    {
      "product_id": "P-001",
      "quantity": 2,
      "price": 30000
    }
  ]
}
```

하지만 미니 프로젝트에서는 데이터 수집·검증·저장·변환 흐름에 집중하기 위해 다음 값만 사용한다.

```text
item_count
```

이것은 실습 범위를 줄이기 위한 설계 결정이다.

# 10. 사용자와 외부 시스템

## 10.1 주요 행위자

| 행위자 | 역할 |
|---|---|
| 고객 | 쇼핑몰에서 주문을 생성 |

## 10.2 실습에서의 대체 관계

`실제 환경:`
```text
고객
→ 쇼핑몰 주문 서비스
→ order_created 이벤트 생성

```

`현재 실습:`
```text

→ curl 또는 Swagger
→ Collector API 전송
```

즉, Sample JSON과 curl은 실제 쇼핑몰 주문 시스템을 흉내 내는 테스트 도구다.

# 13. 왜 주문 테이블이 아니라 이벤트를 사용하는가?

일반적인 쇼핑몰 백엔드는 주문 정보를 관계형 데이터베이스의 주문 테이블에 저장할 수 있다.
```text
orders 테이블
```

그러나 데이터 플랫폼에서는 주문 테이블의 현재 상태뿐 아니라 **업무에서 어떤 사건이 언제 발생했는지**도 중요하다.

예를 들어:
```text
주문이 생성되었다.
결제가 완료되었다.
주문이 취소되었다.
배송이 시작되었다.
환불이 완료되었다.
```

각 사건을 이벤트로 기록하면 다음 장점이 있다.
```text
사건 발생 시점을 추적할 수 있다.
시스템 간 데이터를 전달하기 쉽다.
과거 상태를 다시 구성할 수 있다.
분석과 AI 학습 데이터의 출처를 남길 수 있다.
이후 Kafka와 실시간 스트리밍으로 확장하기 쉽다.
```

이번 실습은 이 중 첫 번째 이벤트인 `order_created`만 구현한다.

# 14. 이벤트 데이터에 필요한 정보

주문 생성 이벤트를 설명하려면 다음 질문에 답해야 한다.
```text
이 이벤트 한 건을 어떻게 구분하는가?
어떤 사건인가?
어떤 구조 버전인가?
어디에서 발생했는가?
언제 발생했는가?
어떤 주문과 고객에 대한 사건인가?
금액과 상품 수는 얼마인가?
```

이 질문을 필드로 바꾸면 다음과 같다.

| 질문 | 필드 |
|---|---|
| 이벤트 한 건을 어떻게 구분하는가? | `event_id` |
| 어떤 사건인가? | `event_type` |
| 어떤 데이터 구조 버전인가? | `schema_version` |
| 어디에서 발생했는가? | `source_system` |
| 언제 발생했는가? | `event_time` |
| 어떤 주문인가? | `payload.order_id` |
| 어떤 고객인가? | `payload.customer_id` |
| 총금액은 얼마인가? | `payload.total_amount` |
| 통화는 무엇인가? | `payload.currency` |
| 상품은 몇 개인가? | `payload.item_count` |

이 설계가 그대로 `sample_events/order_created.sample.json`이 된다.

# 15. 공통 필드와 payload를 분리한 이유

이벤트 데이터는 두 영역으로 나눈다.

`공통 이벤트 필드`
```text
event_id
event_type
schema_version
source_system
event_time
```

이 값들은 주문뿐 아니라 다른 이벤트에도 공통으로 사용할 수 있다.

예:
```text
payment_completed
order_cancelled
product_viewed
cart_item_added
```

`주문 상세 payload`
```text
order_id
customer_id
total_amount
currency
item_count
```

이 값들은 `order_created` 이벤트에 필요한 주문 도메인 상세정보다.

`분리 구조`
```json
{
  "event_id": "evt-order-001",
  "event_type": "order_created",
  "schema_version": "1.0.0",
  "source_system": "shopping_mall",
  "event_time": "2026-07-21T13:00:00+09:00",
  "payload": {
    "order_id": "ORDER-1001",
    "customer_id": "USER-001",
    "total_amount": 89000,
    "currency": "KRW",
    "item_count": 3
  }
}
```

이 구조를 사용하면 공통 처리와 이벤트별 처리를 분리할 수 있다.
```text
공통 처리
→ 이벤트 ID, 유형, 버전, 출처, 시간

주문 전용 처리
→ 주문 ID, 고객 ID, 금액, 통화, 상품 수
```

그래서 Pydantic 클래스도 두 개로 나눈다.
```python
class OrderPayload(BaseModel):
    ...

class OrderCreatedEvent(BaseModel):
    ...
    payload: OrderPayload
```

# 17. 정상·오류 처리 정책

이벤트를 받았을 때 두 가지 결과가 발생할 수 있다.

`정상 데이터`

`처리:`

```

`오류 데이터`

생산 시스템 오류 추적

데이터 품질 지표 생성
```

이 정책 때문에 다음 두 함수가 필요하다.

# 19. 왜 Raw를 JSONL로 저장하는가?

Collector에는 이벤트가 한 건씩 계속 들어온다.

JSONL은 한 줄에 JSON 객체 하나를 저장한다.
```json
{"event_id":"evt-order-001","event_type":"order_created"}
{"event_id":"evt-order-002","event_type":"order_created"}
```

`장점:`
```text
새 이벤트를 파일 끝에 한 줄씩 추가하기 쉽다.
전체 JSON 배열을 다시 작성할 필요가 없다.
한 줄씩 읽어 처리할 수 있다.
문제가 있는 줄을 찾기 쉽다.
반정형 이벤트 구조를 보존하기 쉽다.
```

그래서 `append_jsonl()` 함수가 만들어졌다.

# 20. 왜 Raw와 Staging을 분리하는가?

`Raw의 목적:`
```text
원본 보존
```

`Staging의 목적:`
```text
분석과 재사용
```

하나의 파일이 두 목적을 모두 담당하게 하면 다음 문제가 생긴다.
```text
정제 과정에서 원본이 변경될 수 있다.
변환 오류가 발생했을 때 원본을 확인하기 어렵다.
새로운 변환 규칙으로 다시 처리하기 어렵다.
AI 데이터의 출처를 추적하기 어렵다.
```

따라서 다음처럼 분리한다.
```text
Raw JSONL
→ 원본에 가깝게 보존

Staging Parquet
→ 평탄화·타입 정리·표준화
```

# 21. Staging에서 수행할 변환 규칙

Raw 주문 이벤트는 `payload`가 중첩되어 있다.
```json
{
  "event_id": "evt-order-001",
  "payload": {
    "order_id": "ORDER-1001",
    "total_amount": 89000
  }
}
```

Staging에서는 다음처럼 하나의 행과 컬럼 구조로 만든다.
```text
event_id       order_id      total_amount
evt-order-001  ORDER-1001    89000
```

변환 규칙:

| Raw | Staging |
|---|---|
| `event_id` | `event_id` |
| `event_type` | `event_type` |
| `schema_version` | `schema_version` |
| `source_system` | `source_system` |
| `event_time` | UTC datetime 타입 |
| `payload.order_id` | `order_id` |
| `payload.customer_id` | `customer_id` |
| `payload.total_amount` | 숫자 타입 |
| `payload.currency` | `currency` |
| `payload.item_count` | nullable 정수 타입 |

이 설계가 `flatten_order_event()` 함수와 pandas 타입 변환 코드로 구현된다.

# 22. 왜 Staging을 Parquet으로 저장하는가?

Parquet을 사용하는 이유는 “일반 데이터베이스가 대량 데이터를 저장하지 못하기 때문”이 아니다.
대량 데이터도 데이터베이스나 데이터 웨어하우스 테이블에 저장할 수 있다.
현재 실습에서는 **레이크하우스형 파일 기반 분석 구조**를 경험하기 위해 Parquet을 사용한다.

`장점:`
```text
컬럼 단위 저장
필요한 컬럼만 읽기 쉬움
압축 효율이 좋음
데이터 타입을 보존
DuckDB, pandas, Spark에서 사용하기 쉬움
Mart와 AI 데이터셋으로 확장하기 쉬움
```

# 23. DuckDB 조회 요구사항

Staging 파일을 만들었다고 해서 작업이 끝난 것은 아니다.

다음 내용을 검증해야 한다.
```text
Parquet 파일이 정상적으로 열리는가?
payload 필드가 컬럼으로 평탄화되었는가?
날짜와 숫자 타입이 분석 가능한가?
주문 건수와 매출을 SQL로 집계할 수 있는가?
```

따라서 다음 조회를 설계한다.

`전체 주문 조회`
```sql
SELECT
    event_id,
    order_id,
    customer_id,
    total_amount,
    currency,
    item_count,
    event_time
FROM read_parquet(?)
ORDER BY event_time
```

`주문 요약 조회`
```sql
SELECT
    COUNT(*) AS order_count,
    SUM(total_amount) AS total_sales,
    AVG(total_amount) AS average_order_amount,
    SUM(item_count) AS total_item_count
FROM read_parquet(?)
```

DuckDB는 Parquet 전용 도구가 아니지만, 별도의 DB 서버 없이 Parquet을 바로 SQL로 읽을 수 있어 이 실습에 적합하다.

# 30. 이 코드의 한 문장 해석

> 쇼핑몰 주문 시스템에서 `order_created` 이벤트가 발생하면 Collector API가 JSON을 받아 데이터 계약으로 검증하고, 정상 이벤트는 Raw JSONL에 원본에 가깝게 보존하며, 오류 이벤트는 오류 이유와 함께 Dead Letter에 보관한다. 이후 Raw를 평탄화하고 타입을 표준화하여 Staging Parquet으로 만들고, DuckDB SQL로 분석 가능한 데이터인지 확인한다.

# 32. 최종 정리

현재 2단계 종합 미니 프로젝트의 코드는
```text
도메인 정의
→ 주문 업무

도메인 요소 정의
→ 고객, 주문, 금액, 통화, 상품 수

업무 사건 정의
→ 주문이 생성되었다.

도메인 이벤트 정의
→ order_created

데이터 구조 설계
→ 공통 필드 + payload

데이터 계약 설계
→ 필수값·타입·범위

수집 구조 설계
→ FastAPI Collector

정상·오류 정책
→ Raw / Dead Letter

저장 구조 설계
→ JSONL

분석 구조 설계
→ Staging Parquet

검증 방법 설계
→ DuckDB SQL

역할 분리
→ routes / schemas / services / core / scripts
```
이 설계 결정이 순서대로 코드와 폴더가 된 것이다.

따라서 코드를 이해할 때는 파일을 따로 외우기보다 다음 질문으로 해석해야 한다.
```text
이 파일은 앞에서 결정한 어떤 설계 기준을 구현한 것인가?
```

이 질문을 기준으로 보면 각 파일의 존재 이유가 명확해진다.
