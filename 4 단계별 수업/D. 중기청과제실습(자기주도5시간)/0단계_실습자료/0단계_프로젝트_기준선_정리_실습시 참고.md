## 1. 현재 시작 상태

수업은 완성된 프로젝트에서 시작하지 않는다.

처음 제공되는 프로젝트는 다음 수준의 최소 껍데기 상태를 기준으로 한다.
```text
Django 프로젝트 기본 구조
requirements.txt
.env.example
README.md 기본 안내
templates/ 및 static/ 구조
기본 화면 또는 대시보드 화면 껍데기

# 아래 폴더는 소스를 내려 받은후 직접 vscode에서 생성한다.
docs/ 폴더
sample_events/ 폴더
seed/ 폴더
```

초기 프로젝트에는 다음 기능이 없어야 한다.
```text
완성된 DB 모델 없음
완성된 Raw/Staging/Mart 테이블 없음
완성된 수집 API 없음
완성된 Sensor Simulator 없음
완성된 Airflow DAG 없음
완성된 Kafka/Spark 스트리밍 없음
완성된 dbt Test 없음
완성된 RAG 파이프라인 없음
완성된 AI 이상탐지 모델 없음
완성된 DataOps 모니터링 없음
완성된 Docker/Kubernetes 배포 없음
```

초기 상태를 이렇게 제한하는 이유는 학생들이 단순히 완성 코드를 실행하는 것이 아니라, 데이터가 생성되고 이동하고 검증되고 활용되는 과정을 단계별로 직접 만들도록 하기 위해서이다.

### 3.4 무엇을 만들 것인가?

본 수업에서는 산업안전 관제플랫폼을 예제로 사용하여 AI 네이티브 데이터 플랫폼을 구축한다.

플랫폼은 산업 현장의 유해가스 센서, 전력 장비, 작업자 위치 데이터를 수집하고 위험 상태를 판단한다.  
또한 알람 이력, AI 이상탐지 결과, RAG 대응 매뉴얼, 운영자 피드백, 서비스 로그와 오류 로그를 데이터 플랫폼 관점에서 저장하고 활용한다.

최종적으로는 다음을 구현하는 것을 목표로 한다.

```text
센서 데이터 수집
AI 서비스 로그 수집
문서 데이터 수집
Raw/Staging/Mart 구조 설계
Lakehouse 파일 저장 구조 설계
Airflow 기반 자동화
Kafka/Spark 기반 실시간 처리
Data Quality와 Lineage 관리
RAG 문서 검색 파이프라인
알람과 피드백 데이터 수집
DataOps 모니터링
최종 기업 프로젝트 수준의 통합 플랫폼
```

### 3.5 수업에서 사용할 데이터

기존 기준선에서는 유해가스, 전력, 작업자 위치 데이터 3가지를 중심으로 다뤘다.  
최종 로드맵 기준에서는 다음 10가지 데이터 범위를 기준으로 한다.

| 데이터 | 예시 | 사용 목적 |
|---|---|---|
| 유해가스 센서 데이터 | CO, H2S, CO2, O2, NO2, SO2, O3, NH3, VOC | 임계치 기반 위험도 판단, AI 이상탐지 |
| 전력 사용량 데이터 | voltage, current, power_kw, power_status | 장비 이상 탐지, 전력 패턴 분석 |
| 작업자 위치 데이터 | worker_id, x, y, zone_id | 위험구역 진입 판단, 지오펜스 이벤트 생성 |
| 위험구역/지오펜스 데이터 | zone, polygon, access_level | 공간 기반 위험 판단 |
| 임계치 기준 데이터 | gas_type, warning, danger, unit | 코드가 아닌 데이터 기반 위험 기준 관리 |
| 알람 발생/처리 데이터 | alarm_created, acknowledged, resolved | 운영 이력, 피드백, 학습 데이터 후보 |
| AI 이상탐지 결과 데이터 | model_name, prediction, confidence | 룰 기반 판단 보조, 검토 알람 생성 |
| RAG 대응 문서 데이터 | 매뉴얼, 정의서, 장비 문서, metadata, chunk | 알람 대응 매뉴얼 검색 |
| 사용자 피드백 데이터 | true_alarm, false_alarm, comment | 재학습 후보, 운영 품질 개선 |
| 서비스 호출/오류 로그 | trace_id, endpoint, latency_ms, error_code | 중간 프로젝트, 장애 분석, 학습 데이터셋 생성 |

### 3.6 AI 네이티브 데이터 유형 구분

이 수업에서 데이터는 단순히 “DB에 저장할 값”이 아니라 AI 서비스 운영 목적에 따라 구분한다.

| 데이터 유형  | 관제플릿폼 예시                       | 설명                            |
| ------- | ------------------------------ | ----------------------------- |
| 학습 데이터  | 과거 센서값, 알람 이력, 피드백 결과          | 모델 학습 또는 평가 후보 데이터            |
| 추론 데이터  | 현재 센서값, 현재 작업자 위치, 최근 전력 패턴    | 룰 엔진 또는 AI가 즉시 판단에 사용하는 입력    |
| 피드백 로그  | 알람 확인, 오탐/정탐, 조치 결과            | 모델 개선과 운영 정책 보정에 사용하는 데이터     |
| RAG 데이터 | 가스 정의서, 대응 매뉴얼, 장비 문서          | 알람 발생 시 대응 방법을 검색하기 위한 문서 데이터 |
| 서비스 로그  | API 호출, 오류, 지연, 재시도, 사용자 행동 로그 | 품질 분석, 장애 분석, 학습 데이터 생성 기준    |

## 4. 기준 데이터 흐름

전체 로드맵 기준의 플랫폼 흐름은 다음과 같다.

```text
1. 데이터 생성
   Sensor Simulator / AI Service Log Generator / Document Loader
   → 수업용 가짜 센서 데이터, AI 서비스 로그, 안전 매뉴얼 문서를 생성하거나 준비

        ↓

2. 데이터 수집
   FastAPI Collector / Log Collector / Document Ingestion API
   → 생성된 데이터를 API로 받아들인다.
   → 이 단계는 데이터를 저장소로 보내기 전 입구 역할을 함.

        ↓

3. 원본 데이터 저장
   Raw Zone / PostgreSQL Raw Tables / Raw Files
   → 들어온 데이터를 먼저 원본 그대로 저장.
   → 센서값이 이상하거나 누락이 있어도 바로 버리지 않고 Raw 영역에 남김.

        ↓

4. 데이터 검증과 정제
   Staging Validation / Schema Check / Dedup / Late Event Handling
   → 데이터 형식이 맞는지 확인.
   → 필수값이 빠졌는지, 중복 데이터인지, 너무 늦게 도착한 데이터인지 검사.
   → 검증을 통과한 데이터만 다음 단계로 보냄.

        ↓

5. 서비스용 데이터셋 생성
   Mart / Feature Dataset / Training Dataset / RAG Metadata Dataset
   → 대시보드, AI, RAG, 리포트에서 사용하기 좋은 형태로 데이터를 가공.
   → 예를 들어 최신 센서 상태, 알람 요약, AI 학습 후보 데이터셋, RAG 문서 메타데이터를 듦

        ↓

6. 판단과 활용
   Risk Engine / AI Inference / RAG Search / Feedback Collector
   → Risk Engine은 센서값과 임계치를 비교해 위험도를 판단.
   → AI Inference는 이상 패턴을 탐지한다.
   → RAG Search는 알람 상황에 맞는 안전 대응 매뉴얼을 검색.
   → Feedback Collector는 운영자의 확인, 조치, 오탐/정탐 피드백을 저장.

        ↓

7. 서비스 화면과 운영 결과
   Alarm Service / Dashboard / Data Quality Report / DataOps Monitoring
   → 위험 상황은 알람으로 저장.
   → 대시보드는 현재 센서 상태, 작업자 위치, 알람, AI 결과를 보여줌.
   → 데이터 품질 리포트는 중복, 오류, 지연 데이터를 확인.
   → DataOps Monitoring은 데이터 흐름이 정상인지 감시.

        ↓

8. 운영 모니터링과 개선
   Prometheus / Grafana / CI/CD / 운영 리포트 / 재학습 후보 데이터셋
   → Prometheus와 Grafana로 수집 지연, 오류, 알람 수, AI 처리 상태를 모니터링함.
   → CI/CD로 테스트와 배포 과정을 자동화함.
   → 운영 리포트와 피드백 데이터를 바탕으로 AI 재학습 후보 데이터셋을 만듦.
```

0단계에서는 이 흐름을 코드로 구현하지 않는다.  
다만 이 흐름이 이후 모든 실습의 기준임을 문서로 고정한다.

## 5. 위험도 판단 기준선

처음부터 AI가 모든 위험도를 판단하게 만들지 않는다.

초기 위험도 판단은 다음 원칙을 따른다.

```text
1. 기본 위험 판단은 임계치와 지오펜스 규칙으로 한다.
2. AI 이상탐지는 초기에는 보조 신호 또는 review 상태로 연결한다.
3. 산업안전 도메인에서는 설명 가능한 룰 기반 판단이 먼저 필요하다.
4. AI 결과는 대시보드 표시, 검토 알람, 피드백 학습 데이터로 확장한다.
```

### 5.1 위험도 단계

| 상태 | 의미 | 설명 |
|---|---|---|
| normal | 정상 | 현재 값이 안전한 범위 안에 있음 |
| warning | 주의 | 위험 기준에 가까워졌거나 확인이 필요함 |
| danger | 위험 | 즉시 확인 또는 조치가 필요한 상태 |
| sensor_error | 센서 오류 | 통신 불능, 비정상 값, 누락 값 등 |
| review | 검토 필요 | AI 이상탐지 또는 운영자 판단이 필요한 상태 |

### 5.2 유해가스 위험도 예시

```text
CO 25ppm 미만 → normal
CO 25ppm 이상 200ppm 미만 → warning
CO 200ppm 이상 → danger
```

가스별 상세 기준은 `docs/threshold-definition.md`와 `seed/thresholds.seed.json`에서 관리한다.

### 5.3 전력 위험도 예시

전력 사용량은 가스처럼 단일 고정 임계치만으로 판단하기 어렵다.  
수업용 기준은 다음처럼 시작한다.

```text
최근 평균보다 일정 비율 이상 증가 → warning
급격한 증가 또는 비정상 패턴 → danger 또는 review
통신불능 값 또는 누락 값 → sensor_error
```

### 5.4 작업자 위치 위험도 예시

```text
작업자가 일반 구역에 있음 → normal
작업자가 위험구역에 들어감 → warning
작업자가 위험구역에 있고 해당 구역 센서가 danger → danger
```

## 6. 저장소와 데이터 계층 기준선

### 6.1 Raw & Lakehouse

Raw는 원본 데이터를 최대한 그대로 보존하는 계층이다.  
여기서 Raw는 “로우”라고 읽으며, “가공되지 않은 원본 데이터”라는 뜻이다.

센서 데이터나 로그 데이터가 시스템에 처음 들어오면, 바로 위험도를 판단하거나 대시보드용 데이터로 바꾸지 않는다.  

### 먼저 Raw 계층에 원본 형태로 저장한다.

예를 들어 센서에서 다음과 같은 데이터가 들어왔다고 가정한다.
```json
{
  "event_id": "gas-001",
  "sensor_id": "GAS-001",
  "co": 230,
  "h2s": 5,
  "measured_at": "2026-07-21T09:00:00"
}
```

이 데이터는 CO 값이 위험한지 먼저 판단하기 전에, Raw 계층에 그대로 저장한다.  
그래야 나중에 오류가 발생했을 때 “처음 들어온 데이터가 무엇이었는지” 다시 확인할 수 있다.

```text
Raw의 핵심 목적:
- 원본 데이터 보존
- 나중에 다시 처리할 수 있도록 재처리 가능성 확보
- 장애나 오류가 났을 때 원인 분석
- 데이터가 어디서 시작되어 어디로 이동했는지 계보 추적
```

Raw 계층이 필요한 이유
Raw 계층이 없으면 문제가 생겼을 때 원인을 찾기 어렵다.
예를 들어 대시보드에 잘못된 알람이 표시되었을 때 다음을 확인해야 한다.
```
처음 센서 데이터가 잘못 들어온 것인가?
수집 API에서 잘못 처리한 것인가?
검증 로직에서 잘못 판단한 것인가?
위험도 판단 로직이 잘못된 것인가?
대시보드 표시만 잘못된 것인가?
```
이때 Raw 데이터가 있으면 “처음 들어온 원본값”을 기준으로 다시 확인할 수 있다.

Raw 예시: 아래 이름들은 필드명이 아니라 Raw 데이터를 저장할 테이블명 또는 저장 영역 이름이다.
```text
raw_gas_events
raw_power_events
raw_worker_location_events
raw_ai_service_logs
raw_rag_query_logs
raw_feedback_logs
raw_documents
```

###### 각 이름의 의미는 다음과 같다.
| 이름                           | 의미                        |
| ---------------------------- | ------------------------- |
| `raw_gas_events`             | 유해가스 센서에서 들어온 원본 이벤트 저장   |
| `raw_power_events`           | 전력 장비에서 들어온 원본 이벤트 저장     |
| `raw_worker_location_events` | 작업자 위치 원본 이벤트 저장          |
| `raw_ai_service_logs`        | AI 서비스 호출 로그 원본 저장        |
| `raw_rag_query_logs`         | RAG 검색 요청 로그 원본 저장        |
| `raw_feedback_logs`          | 운영자 피드백 원본 저장             |
| `raw_documents`              | 업로드된 문서 원본 또는 문서 메타데이터 저장 |

예시
Django 모델로 구현할 경우
수업에서는 Raw 계층을 Django 모델로 만들 수 있다.
예를 들어 가스 센서 Raw 데이터는 다음과 같은 모델이 될 수 있다.
```python
class RawGasEvent(models.Model):
    event_id = models.CharField(max_length=100, unique=True)
    source_system = models.CharField(max_length=100)
    schema_version = models.CharField(max_length=20)
    payload = models.JSONField()
    measured_at = models.DateTimeField()
    ingested_at = models.DateTimeField(auto_now_add=True)
    quality_status = models.CharField(max_length=30, default="raw")
```
여기서 중요한 점은 `payload`이다.  
`payload`에는 센서에서 들어온 원본 JSON 데이터를 최대한 그대로 저장한다.

즉, Raw 모델은 처음부터 모든 값을 깔끔하게 나누어 저장하기보다,  
**원본 JSON을 보존하는 역할**을 먼저 한다.

PostgreSQL 테이블로 보면
Django 모델을 만들고 migration을 하면 PostgreSQL에는 다음과 비슷한 테이블이 만들어진다.
```
raw_gas_events
```

이 테이블에는 다음과 같은 컬럼이 들어갈 수 있다.
```
id
event_id
source_system
schema_version
payload
measured_at
ingested_at
quality_status
created_at
```
따라서 정리하면 다음과 같다.
```
raw_gas_events
→ 테이블명

event_id, source_system, payload, measured_at
→ 테이블 안의 컬럼명

payload 안의 co, h2s, o2 같은 값
→ 센서에서 들어온 실제 원본 데이터
```

### 파일 기반 Lakehouse로 구현할 경우

Raw는 반드시 DB 테이블만 의미하지 않는다.  
파일 기반으로 저장할 수도 있다.

예를 들어 다음과 같은 폴더 구조를 만들 수 있다.
```
data_lake/
  raw/
    gas_events/
      date=2026-07-21/
        gas_events_09.jsonl
    power_events/
      date=2026-07-21/
        power_events_09.jsonl
```
이 경우 `raw_gas_events`는 DB 테이블이 아니라,  
`data_lake/raw/gas_events/` 같은 파일 저장 영역으로 볼 수 있다.

원본 데이터 저장 방식은 크게 2가지로 보면 됩니다
```
1. DB Raw Table 방식  
2. File / Lakehouse Raw Zone 방식
```

`1.` 가스 센서 데이터가 들어오면 PostgreSQL의 `raw_gas_events` 테이블에 저장하는 방식

장점
```
- 초보자가 이해하기 쉽다.  
- Django Admin이나 Django ORM으로 조회하기 쉽다.  
- 대시보드와 바로 연결하기 쉽다.  
- 알람, 피드백, 운영 데이터와 조인하기 쉽다.
```

단점
```
- 데이터가 아주 많아지면 DB 용량과 성능 부담이 커진다.  
- 센서 로그, AI 로그처럼 대량으로 쌓이는 데이터에는 장기적으로 부담이 된다.  
- 원본 파일을 그대로 보존하는 데이터 레이크 구조와는 다르다.
```

`2.` Lakehouse Raw Zone 방식
이 방식은 원본 데이터를 DB 테이블이 아니라 파일로 저장하는 방식으로 대량 데이터에 적합

장점
```
- 센서 로그, 서비스 로그처럼 대량으로 쌓이는 데이터를 저장하기 좋다.  
- 원본 보존에 적합하다.  
- Parquet로 변환하면 분석 성능이 좋아진다.  
- Spark, DuckDB, Airflow, dbt와 연결하기 좋다.  
- AI 학습 데이터셋 생성에 적합하다.
```

단점
```
- 초보자가 처음 이해하기에는 DB 테이블보다 어렵다.  
- 파일 경로, 파티션, 포맷, 메타데이터 관리가 필요하다.  
- 대시보드에서 바로 조회하기에는 불편하다.
```

현업에서는 보통 하나만 사용하지 않고 섞어서 사용한다
가장 현실적인 구조는 다음과 같다
```
대량 원본 데이터  
→ Lakehouse Raw Zone에 저장  
  
운영에 바로 필요한 데이터  
→ PostgreSQL 같은 DB에 저장  
  
대시보드용 요약 데이터  
→ Mart Table에 저장  
  
문서 검색용 데이터  
→ Vector DB에 저장  
  
알람, 피드백, 사용자 조치 이력  
→ PostgreSQL에 저장
```
즉, 현장에서는 보통 이런 하이브리드 구조가 많다
```
Raw 원본 장기 보관:
S3 / MinIO / Data Lake / Lakehouse

운영 서비스 데이터:
PostgreSQL / MySQL

분석용 데이터:
Parquet / Spark / DuckDB / BigQuery / Snowflake

RAG 검색:
Vector DB / pgvector / Chroma / FAISS

실시간 이벤트:
Kafka
```

그래서 수업할때는 아래와 같은 단계로 진행된다
```
# 초반
가짜 센서 데이터 생성  
   ↓  
FastAPI가 API로 받음  
   ↓  
PostgreSQL Raw Table에 저장  
   ↓  
Django에서 조회  
   ↓  
대시보드에 표시

# 중반 : 중반부터는 Lakehouse 개념을 추가
FastAPI Collector  
   ↓  
PostgreSQL Raw Table 저장  
   +  
data_lake/raw/*.jsonl 파일 저장

# 후반
Raw JSONL  
   ↓  
Staging Parquet  
   ↓  
Mart Parquet / Mart Table  
   ↓  
AI Training Dataset  
   ↓  
Data Quality Report
```
이렇게 하면 전체 로드맵의 Lakehouse, Airflow, Kafka/Spark, dbt, AI 학습 데이터셋과 자연스럽게 연결된다.

### 6.2 Staging

Staging은 **Raw에 저장된 원본 데이터를 검증하고 표준화한 계층**이다.

Raw가 “처음 들어온 원본을 그대로 보관하는 곳”이라면,  
Staging은 “이 데이터를 실제로 사용할 수 있는 상태인지 검사하고 정리하는 곳”이다.

즉, Staging은 데이터의 **전처리, 정제, 검증 단계**라고 이해하면 된다.
```
Raw
→ 원본 데이터 보관

Staging
→ 원본 데이터를 검사하고 정리한 데이터

Mart
→ 대시보드, AI, RAG, 리포트에서 바로 사용할 수 있게 가공한 데이터
```

Staging이 필요한 이유
센서 데이터나 로그 데이터는 항상 깨끗하게 들어오지 않는다.

예를 들어 다음과 같은 문제가 생길 수 있다.
```
event_id가 없는 데이터가 들어올 수 있다.
CO 값이 숫자가 아니라 문자열로 들어올 수 있다.
측정 시간이 없는 데이터가 들어올 수 있다.
같은 event_id가 두 번 들어올 수 있다.
센서 시간이 현재보다 너무 오래된 데이터일 수 있다.
schema_version이 현재 시스템과 맞지 않을 수 있다.
CO 값이 -999처럼 말이 안 되는 값일 수 있다.
```
이런 데이터를 바로 대시보드나 AI에 사용하면 잘못된 알람이 발생하거나, AI 학습 데이터가 오염될 수 있다.

그래서 Raw 데이터를 바로 사용하지 않고, Staging 단계에서 먼저 검사한다.

Staging에서 하는 일
```
Staging의 목적:
- Raw 데이터의 필수값을 확인한다.
- 데이터 타입이 맞는지 검사한다.
- 단위가 맞는지 확인한다.
- 값의 범위가 정상인지 검사한다.
- 중복 event_id를 제거하거나 표시한다.
- 너무 늦게 도착한 데이터를 구분한다.
- schema_version이 현재 처리 가능한 버전인지 확인한다.
- 검증을 통과한 데이터만 표준화된 구조로 저장한다.
```

검증 기준
```text
- 필수값 누락
- 타입 오류
- 단위 오류
- 범위 초과
- 중복 event_id
- 지연 도착 데이터
- schema_version 불일치
```

각 기준은 다음과 같이 이해하면 된다.

| 검증 기준              | 의미                   | 예시                            |
| ------------------ | -------------------- | ----------------------------- |
| 필수값 누락             | 반드시 있어야 하는 값이 없음     | `event_id`가 없음                |
| 타입 오류              | 값의 자료형이 맞지 않음        | `co` 값이 숫자가 아니라 `"high"`로 들어옴 |
| 단위 오류              | 정해진 단위와 다름           | CO는 ppm이어야 하는데 `%`로 들어옴       |
| 범위 초과              | 물리적으로 말이 안 되는 값      | CO가 `-10ppm`                  |
| 중복 event_id        | 같은 이벤트가 두 번 들어옴      | `gas-001`이 두 번 저장됨            |
| 지연 도착 데이터          | 측정 시각보다 너무 늦게 들어옴    | 2시간 전 데이터가 이제 도착              |
| schema_version 불일치 | 현재 처리 가능한 데이터 구조가 아님 | 시스템은 `1.0`을 기대하는데 `0.8`이 들어옴  |

예시로 이해하면 다음과 같다.
Raw에 다음 데이터가 들어왔다고 가정한다.
```json
{
  "event_id": "gas-001",
  "schema_version": "1.0",
  "event_type": "gas_sensor_measured",
  "source_system": "sensor_simulator",
  "device_id": "GAS-001",
  "measured_at": "2026-07-21T09:00:00",
  "payload": {
    "co": "230",
    "h2s": 5,
    "co2": 600,
    "o2": 20.8
  }
}
```

여기서 `co` 값은 `"230"`처럼 문자열로 들어왔다.  
하지만 Staging에서는 CO 값을 숫자로 사용해야 한다.

따라서 Staging 단계에서는 다음처럼 정리한다.
```
co: "230"  
→ 문자열이지만 숫자로 변환 가능함  
→ 230.0으로 표준화  
→ 검증 통과
```
Staging에 저장되는 데이터는 다음처럼 더 정리된 형태가 된다.
```
event_id: gas-001  
sensor_id: GAS-001  
gas_type: co  
value: 230.0  
unit: ppm  
event_time: 2026-07-21 09:00:00  
quality_status: valid
```
즉, Raw는 원본 JSON을 보관하고,  
Staging은 분석과 판단에 쓰기 쉬운 형태로 정리한다.

Staging 예시
아래 이름들은 필드명이 아니라 Staging 데이터를 저장할 테이블명 또는 데이터셋 이름이다.
```text
stg_gas_measurements  
stg_power_measurements  
stg_worker_locations  
stg_ai_service_logs  
stg_rag_query_logs  
stg_feedback_events  
stg_document_metadata
```

###### 각 이름의 의미는 다음과 같다.
| 이름                       | 의미               |
| ------------------------ | ---------------- |
| `stg_gas_measurements`   | 검증된 가스 측정 데이터    |
| `stg_power_measurements` | 검증된 전력 측정 데이터    |
| `stg_worker_locations`   | 검증된 작업자 위치 데이터   |
| `stg_ai_service_logs`    | 검증된 AI 서비스 호출 로그 |
| `stg_rag_query_logs`     | 검증된 RAG 검색 요청 로그 |
| `stg_feedback_events`    | 검증된 운영자 피드백 데이터  |
| `stg_document_metadata`  | 검증된 문서 메타데이터     |

수업 초반에는 Pandas로 Staging 개념을 설명하면 이해하기 쉽다.
예를 들어 Raw JSON 데이터를 읽어서 필수값을 검사하고, 타입을 변환하고, 이상한 값을 걸러낼 수 있다.
```python
import pandas as pd

raw_data = [
    {
        "event_id": "gas-001",
        "sensor_id": "GAS-001",
        "gas_type": "co",
        "value": "230",
        "unit": "ppm",
        "event_time": "2026-07-21T09:00:00"
    },
    {
        "event_id": "gas-002",
        "sensor_id": "GAS-001",
        "gas_type": "co",
        "value": None,
        "unit": "ppm",
        "event_time": "2026-07-21T09:00:01"
    }
]

df = pd.DataFrame(raw_data)

# 필수값 누락 제거
df = df.dropna(subset=["event_id", "sensor_id", "value", "event_time"])

# value를 숫자로 변환
df["value"] = pd.to_numeric(df["value"], errors="coerce")

# 변환 실패 데이터 제거
df = df.dropna(subset=["value"])

# 범위 검증
df = df[df["value"] >= 0]

print(df)
```
하지만 현장에서는 Pandas만 사용하는 것은 아니다.

실제 구현에서는 어떤 도구를 쓰는가?
Staging은 상황에 따라 여러 방식으로 구현할 수 있다.

| 방식                      | 사용 위치         | 설명                           |
| ----------------------- | ------------- | ---------------------------- |
| Python 기본 코드            | 수업 초반         | if문, 함수로 검증 로직 작성            |
| Pandas                  | 소규모 데이터 전처리   | CSV, JSON, 작은 로그 데이터 정제      |
| Django / DRF Serializer | API 입력 검증     | 화면이나 API에서 들어오는 데이터 검증       |
| Pydantic                | FastAPI 입력 검증 | Collector API에서 JSON 구조 검증   |
| SQL                     | DB 안에서 검증·정제  | Raw Table에서 Staging Table 생성 |
| Airflow                 | 배치 자동화        | Raw → Staging 작업을 매일/매시간 실행  |
| dbt                     | 데이터 품질 테스트    | Staging/Mart 테이블의 품질 검증      |
| Spark                   | 대용량 데이터 처리    | Kafka, 로그, 센서 대량 데이터 정제      |
수업에서는 다음 순서로 이해 한다
```
처음에는 Python 또는 Pandas로 Staging 개념을 이해한다.
그 다음 FastAPI Pydantic으로 수집 시점의 기본 검증을 한다.
이후 Airflow와 SQL로 Raw → Staging 변환을 자동화한다.
후반에는 dbt와 Spark로 품질 검증과 대용량 처리를 확장한다.
```

Django 모델로 구현할 경우
Staging 테이블도 Django 모델로 만들 수 있다.

예를 들어 가스 측정 Staging 모델은 다음과 같이 만들 수 있다.
```python
class StgGasMeasurement(models.Model):
    event_id = models.CharField(max_length=100, unique=True)
    sensor_id = models.CharField(max_length=100)
    gas_type = models.CharField(max_length=30)
    value = models.FloatField()
    unit = models.CharField(max_length=20)
    event_time = models.DateTimeField()
    ingestion_time = models.DateTimeField()
    quality_status = models.CharField(max_length=30, default="valid")
    validation_message = models.TextField(blank=True, null=True)
```
Raw 모델과의 차이는 다음과 같다.
```
RawGasEvent
→ 원본 JSON payload를 보존하는 데 집중

StgGasMeasurement
→ 검증되고 정리된 컬럼 구조를 갖는 데 집중
```
즉, Raw는 “원본 보관용”이고,  
Staging은 “검증 후 사용 준비용”이다.

###### Raw와 Staging의 차이
| 구분     | Raw              | Staging                   |
| ------ | ---------------- | ------------------------- |
| 목적     | 원본 보존            | 검증과 표준화                   |
| 데이터 상태 | 들어온 그대로          | 정리된 상태                    |
| 오류 데이터 | 포함될 수 있음         | 오류 데이터는 제외하거나 표시          |
| 구조     | JSON payload 중심  | 컬럼 구조 중심                  |
| 사용 목적  | 재처리, 추적, 장애 분석   | Mart 생성, AI 입력, 위험도 판단 준비 |
| 예시     | `raw_gas_events` | `stg_gas_measurements`    |

### 6.3 Mart

Mart는 Raw와 Staging을 거친 데이터를 목적별로 다시 가공한 “서비스용 데이터셋”이다

여기서 Mart는 “데이터 마트(Data Mart)”를 줄여서 말하는 것이고,  
마트처럼 여러 사람이 바로 가져다 쓸 수 있게 목적별로 정리된 데이터 진열대라고 설명하면 이해하기 쉽다.

Raw가 “원본 보관소”,  
Staging이 “검사·정제 작업대”,  
Mart는 “서비스에서 바로 쓰는 완성 데이터셋”이다.

다시 정리하면
Mart는 대시보드, AI, RAG, 운영 리포트에서 바로 사용할 수 있도록 목적별로 가공한 데이터셋이다.

Raw와 Staging을 거친 데이터는 아직 서비스가 바로 쓰기에는 불편할 수 있다.  
예를 들어 Staging에는 센서 측정값이 시간순으로 계속 쌓여 있지만, 대시보드는 “현재 센서 상태”만 빠르게 보고 싶을 수 있다.

이때 Staging 데이터를 다시 목적에 맞게 가공해서 만든 것이 Mart이다.
```
Raw
→ 원본 데이터 보관

Staging
→ 원본 데이터를 검증하고 표준화

Mart
→ 대시보드, AI, RAG, 리포트가 바로 사용할 수 있게 목적별로 가공
```

Mart가 필요한 이유
Staging 데이터는 깨끗하게 정리된 데이터이지만, 아직 사용 목적별로 최적화된 데이터는 아니다.
예를 들어 대시보드에서 현재 상태를 보여주려면 매번 다음 작업을 해야 한다.
```
1. 센서별 최신 데이터를 찾는다.  
2. 임계치와 비교한다.  
3. normal / warning / danger를 계산한다.  
4. 구역 이름과 센서 이름을 붙인다.  
5. 최근 알람 수를 계산한다.  
6. 화면에 보여줄 형태로 정리한다.
```
이 작업을 대시보드가 열릴 때마다 반복하면 느려질 수 있다.

그래서 미리 다음과 같은 형태로 만들어 둔다.
```
mart_current_sensor_status
→ 현재 센서 상태를 바로 조회할 수 있는 데이터셋

mart_alarm_summary
→ 알람 통계를 바로 조회할 수 있는 데이터셋

mart_ai_training_dataset
→ AI 학습에 바로 사용할 수 있는 데이터셋
```

Mart 예시

아래 이름들은 필드명이 아니라 목적별 Mart 테이블명 또는 데이터셋 이름이다.
```text
mart_current_sensor_status
mart_risk_status
mart_alarm_summary
mart_ai_training_dataset
mart_rag_document_index
mart_feedback_summary
mart_quality_summary
```

###### 각 이름의 의미는 다음과 같다.
| 이름                           | 의미                                                      |
| ---------------------------- | ------------------------------------------------------- |
| `mart_current_sensor_status` | 대시보드에서 현재 센서 상태를 빠르게 보여주기 위한 데이터셋                       |
| `mart_risk_status`           | 구역별, 센서별, 작업자별 현재 위험도를 보여주기 위한 데이터셋                     |
| `mart_alarm_summary`         | 일별, 시간별, 유형별 알람 통계를 보여주기 위한 데이터셋                        |
| `mart_ai_training_dataset`   | AI 이상탐지 모델 학습이나 평가에 사용할 데이터셋                            |
| `mart_rag_document_index`    | RAG 검색에 사용할 문서 chunk, metadata, embedding 정보를 관리하는 데이터셋 |
| `mart_feedback_summary`      | 운영자 피드백, 오탐/정탐, 조치 결과를 분석하기 위한 데이터셋                     |
| `mart_quality_summary`       | 중복, 지연, 오류, 결측 등 데이터 품질 상태를 요약한 데이터셋                    |

Mart는 데이터 종류에 따라 모양이 달라진다
센서 데이터는 숫자 데이터이므로 평균, 최대값, 최신값, 위험도 계산이 중요하다.  
문서 데이터는 텍스트 데이터이므로 chunk, metadata, embedding, 출처 관리가 중요하다.  
피드백 데이터는 운영 이력 데이터이므로 오탐/정탐 비율, 조치 시간, 담당자 처리 상태가 중요하다.
```
숫자 데이터
→ 집계, 평균, 최대값, 위험도 계산

문서 데이터
→ chunking, metadata 부여, embedding, 검색 인덱스 생성

로그 데이터
→ trace_id 연결, 오류 분류, latency 계산

피드백 데이터
→ 오탐/정탐 분류, 조치 상태 요약, 학습 label 후보 생성

품질 데이터
→ 중복 수, 오류 수, 지연 수, 품질 실패율 계산
```
즉, Mart는 단순히 테이블 하나를 만드는 것이 아니라,  
각 데이터가 어디에 쓰일지에 맞게 사용하기 좋은 형태로 바꾸는 과정이다.

예시1: 대시보드용 Mart

```

Staging에서는 검증된 센서 측정값이 저장된다.

그래서 다음과 같은 Mart를 만든다.
```

```

```

zone_id
zone_name
gas_type
latest_value
unit
risk_level
last_measured_at
last_ingested_at
status_message
```

예를 들어 다음과 같은 데이터가 들어갈 수 있다.
```

sensor_name: A구역 가스센서
zone_id: ZONE-A
zone_name: A구역

이렇게 만들어두면 대시보드는 복잡한 계산 없이 `mart_current_sensor_status`만 조회해서 화면에 보여줄 수 있다.

예시 5. RAG 문서 검색용 Mart

RAG는 센서 숫자 데이터와 다르게 문서 데이터를 사용한다.

예를 들어 다음 문서가 있다고 하자.
```
CO 위험 대응 매뉴얼.pdf
가스별 임계치 정의서.pdf
스마트 파워 시스템 장비 설명서.pdf
```

이 문서를 그대로 저장한다고 RAG가 검색할 수 있는 것은 아니다.

RAG에서 사용하려면 다음 작업이 필요하다.
```
1. 문서를 텍스트로 추출한다.
2. 긴 문서를 작은 chunk로 나눈다.
3. 각 chunk에 metadata를 붙인다.
4. embedding을 생성한다.
5. Vector DB에 저장한다.
6. 검색 결과에 출처를 표시할 수 있게 한다.
```

그래서 다음 Mart를 만든다.
```
mart_rag_document_index
```

다만 이 Mart는 일반 PostgreSQL 테이블 하나만 의미하지 않을 수 있다.  
문서 메타데이터는 PostgreSQL에 저장하고, embedding vector는 Vector DB에 저장할 수 있다.

예시 구조는 다음과 같다.
```
PostgreSQL:
mart_rag_document_index
- document_id
- chunk_id
- source_doc
- page_no
- gas_type
- risk_level
- equipment_type
- content_preview
- vector_id
- version
- updated_at

Vector DB:
vector_id
embedding
chunk_text
metadata
```

즉, RAG용 Mart는 다음 두 가지를 연결하는 역할을 한다.
```
문서 내용
+
검색용 벡터
+
출처 metadata
```

예시 데이터는 다음과 같다.
```
document_id: DOC-001
chunk_id: CHUNK-001
source_doc: CO 위험 대응 매뉴얼.pdf
page_no: 3
gas_type: CO
risk_level: danger
content_preview: CO 농도가 위험 기준을 초과하면 즉시 작업자를 대피시킨다.
vector_id: vec-001
version: 1.0
```

Mart는 어떻게 만드는가?
Mart는 보통 Staging 데이터를 기반으로 만든다.

###### 수업에서는 처음에는 Python이나 SQL로 만들 수 있고, 이후 Airflow, dbt, Spark로 확장한다.
| 방식              | 설명                             | 수업 적용 |
| --------------- | ------------------------------ | ----- |
| Python / Pandas | 작은 데이터를 가공하기 쉬움                | 초반 실습 |
| Django ORM      | DB 데이터를 조회해서 Mart 모델에 저장       | 초반~중반 |
| SQL             | Staging 테이블을 조인하고 집계해서 Mart 생성 | 중반    |
| Airflow         | Mart 생성 작업을 정기적으로 자동 실행        | 중반    |
| dbt             | Staging/Mart 모델과 품질 테스트 관리     | 후반    |
| Spark           | 대용량 로그나 스트리밍 데이터를 Mart로 가공     | 후반    |
| Vector DB       | RAG 검색용 embedding index 관리     | 후반    |

예를 들어 SQL로는 다음처럼 만들 수 있다.
```sql
INSERT INTO mart_alarm_summary (
    summary_date,
    zone_id,
    risk_type,
    risk_level,
    alarm_count
)
SELECT
    DATE(created_at) AS summary_date,
    zone_id,
    risk_type,
    risk_level,
    COUNT(*) AS alarm_count
FROM alarm_records
GROUP BY
    DATE(created_at),
    zone_id,
    risk_type,
    risk_level;
```

Python/Pandas로는 다음처럼 이해할 수 있다.
```python
import pandas as pd

alarms = pd.DataFrame([
    {"created_at": "2026-07-21", "zone_id": "ZONE-A", "risk_type": "gas_co_danger", "risk_level": "danger"},
    {"created_at": "2026-07-21", "zone_id": "ZONE-A", "risk_type": "gas_co_danger", "risk_level": "danger"},
    {"created_at": "2026-07-21", "zone_id": "ZONE-B", "risk_type": "power_overload", "risk_level": "warning"},
])

summary = (
    alarms
    .groupby(["created_at", "zone_id", "risk_type", "risk_level"])
    .size()
    .reset_index(name="alarm_count")
)

print(summary)
```

이 예시는 `alarm_records`를 요약해서 `mart_alarm_summary`를 만드는 개념이다.

---
#### Raw, Staging, Mart 차이 정리
| 구분     | Raw              | Staging                | Mart                         |
| ------ | ---------------- | ---------------------- | ---------------------------- |
| 목적     | 원본 보존            | 검증과 표준화                | 목적별 활용                       |
| 데이터 상태 | 들어온 그대로          | 정리된 데이터                | 서비스가 바로 쓰기 좋은 데이터            |
| 주요 작업  | 저장               | 필수값, 타입, 범위, 중복 검증     | 집계, 조인, 요약, feature 생성       |
| 사용 대상  | 재처리, 장애 분석       | Mart 생성 준비             | 대시보드, AI, RAG, 운영 리포트        |
| 예시     | `raw_gas_events` | `stg_gas_measurements` | `mart_current_sensor_status` |
| 데이터 형태 | JSON payload 중심  | 컬럼 구조 중심               | 목적별 테이블, 파일, Vector index    |

---

쉬운 비유
```
Raw는 택배 박스를 받은 그대로 창고에 보관하는 단계이다.

Staging은 박스를 열어서 물건이 맞는지, 수량이 맞는지, 깨진 것은 없는지 검사하는 단계이다.

Mart는 검사된 물건을 매장 진열대에 보기 좋게 분류해서 올려두는 단계이다.
```

데이터로 바꾸면 다음과 같다.
```
Raw
→ 센서 데이터가 들어온 그대로 저장

Staging
→ 센서 데이터가 정상인지 검사하고 정리

Mart
→ 대시보드, AI, RAG, 리포트가 바로 사용할 수 있게 목적별로 정리
```

---
한 줄 설명
```
Mart는 검증된 Staging 데이터를 대시보드, AI 학습, RAG 검색, 운영 리포트 등 사용 목적에 맞게 다시 가공한 최종 활용 데이터셋이다.
```

수업에서는 이렇게 이해하면 된다.
```
Raw에 원본 데이터가 저장된다.
↓
Staging에서 데이터 오류를 검사하고 표준화한다.
↓
Mart에서 목적별로 데이터를 다시 만든다.
↓
대시보드, AI, RAG, 운영 리포트가 Mart 데이터를 사용한다.
```

즉, Mart는 데이터를 저장하는 마지막 단계라기보다, 서비스를 위해 데이터를 꺼내 쓰기 좋게 준비하는 계층이다.

### 6.4 Lakehouse란 무엇인가?

Lakehouse는 **Data Lake와 Data Warehouse의 장점을 함께 사용하려는 저장 구조**이다.
아주 쉽게 말하면 다음과 같다.
```
Data Lake
→ 원본 파일을 대량으로 저장하기 좋다.

Data Warehouse
→ 정리된 데이터를 분석하고 조회하기 좋다.

Lakehouse
→ 원본 파일 저장과 분석용 데이터 관리를 함께 하려는 구조이다.
```

Lakehouse는 센서 로그, AI 서비스 로그, 문서 데이터, 피드백 데이터처럼
대량으로 쌓이는 원본 데이터를 파일 기반으로 저장하고,
이후 분석과 AI 학습에 사용할 수 있도록 정리하는 저장 구조이다.

수업 초반에는 로컬 파일 시스템으로 시작한다.
```
data_lake/
  raw/
  staging/
  mart/
```

후반에는 MinIO 또는 S3 호환 구조로 확장할 수 있다.
```
s3://diconai-data-lake/raw/
s3://diconai-data-lake/staging/
s3://diconai-data-lake/mart/
```

수업에서는 실제 AWS S3를 반드시 사용하지 않아도 된다.  
로컬 폴더나 MinIO만으로도 Lakehouse의 기본 구조를 충분히 실습할 수 있다.

Lakehouse의 기본 폴더 구조
Lakehouse는 보통 Raw, Staging, Mart 영역을 폴더로 나누어 관리한다.
```
data_lake/
  raw/
    gas_events/date=YYYY-MM-DD/hour=HH/
    power_events/date=YYYY-MM-DD/hour=HH/
    worker_location_events/date=YYYY-MM-DD/hour=HH/
    ai_service_logs/date=YYYY-MM-DD/hour=HH/
    rag_query_logs/date=YYYY-MM-DD/hour=HH/
    feedback_logs/date=YYYY-MM-DD/hour=HH/

  staging/
    gas_measurements/date=YYYY-MM-DD/
    power_measurements/date=YYYY-MM-DD/
    worker_locations/date=YYYY-MM-DD/
    ai_service_logs/date=YYYY-MM-DD/
    rag_query_logs/date=YYYY-MM-DD/
    feedback_events/date=YYYY-MM-DD/

  mart/
    current_sensor_status/date=YYYY-MM-DD/
    risk_status/date=YYYY-MM-DD/
    alarm_summary/date=YYYY-MM-DD/
    ai_training_dataset/date=YYYY-MM-DD/
    rag_document_index/date=YYYY-MM-DD/
    feedback_summary/date=YYYY-MM-DD/
    quality_summary/date=YYYY-MM-DD/
```
여기서 `date=YYYY-MM-DD/hour=HH`처럼 폴더를 나누는 것을 **파티셔닝**이라고 한다.
파티셔닝을 하면 특정 날짜나 시간의 데이터만 빠르게 읽을 수 있다.
예를 들어 2026년 7월 21일 9시의 가스 데이터만 읽고 싶다면 다음 경로만 보면 된다.
```
data_lake/raw/gas_events/date=2026-07-21/hour=09/
```

JSONL과 Parquet의 차이
Lakehouse에서는 보통 Raw에는 JSONL을 저장하고, Staging이나 Mart에는 Parquet를 사용할 수 있다.
```text
JSONL
→ 원본 로그를 저장하기 쉽다.
→ 사람이 열어보고 이해하기 쉽다.
→ 수집 초기 단계에 적합하다.

Parquet
→ 분석용 컬럼 기반 파일 형식이다.
→ 대량 데이터를 빠르게 조회하기 좋다.
→ Spark, DuckDB, BigQuery, Athena 등 분석 도구와 잘 맞는다.
```

수업에서는 다음처럼 진행한다
```
Raw
→ JSONL로 저장

Staging
→ 검증 후 Parquet로 변환

Mart
→ 분석 목적에 맞게 Parquet 또는 PostgreSQL Table로 저장
```

예를 들면 다음과 같다.
```
data_lake/raw/gas_events/date=2026-07-21/hour=09/gas_events_0001.jsonl
        ↓
data_lake/staging/gas_measurements/date=2026-07-21/part-0001.parquet
        ↓
data_lake/mart/current_sensor_status/date=2026-07-21/part-0001.parquet
```

쉽게 비유하여
```
PostgreSQL Raw Table은 사무실 장부에 기록하는 방식과 비슷하다.  
필요한 데이터를 빠르게 조회하고, 화면과 연결하기 좋다.  
  
Lakehouse Raw Zone은 원본 서류와 파일을 대형 창고에 날짜별로 보관하는 방식과 비슷하다.  
양이 많아도 오래 보관할 수 있고, 나중에 다시 분석하거나 재처리하기 좋다.
```

### 6.5 Vector DB

Vector DB는 RAG 문서 검색을 위한 저장소이다.

센서 데이터, 전력 데이터, 작업자 위치 데이터는 대부분 숫자나 좌표 데이터이다.  
하지만 RAG에서 사용하는 데이터는 PDF, 매뉴얼, 정의서, 장비 설명서 같은 **문서 데이터**이다.

문서 데이터는 센서 데이터처럼 바로 비교하거나 계산하기 어렵다.  
예를 들어 다음과 같은 문장이 있다고 하자.
```
CO 농도가 위험 기준을 초과하면 작업자를 즉시 대피시키고 환기 장치를 가동한다.
```

이 문장을 컴퓨터가 검색에 잘 사용하려면, 문장의 의미를 숫자 형태로 바꾸어 저장해야 한다.  
이때 문장을 의미 기반 숫자 배열로 바꾼 것을 Embedding, 그 Embedding을 저장하고 검색하는 저장소를 Vector DB라고 한다.

---
Vector DB가 필요한 이유
일반 데이터베이스는 보통 정확한 단어 검색이나 조건 검색에 강하다.

예를 들어 PostgreSQL에서는 이런 검색을 할 수 있다.
```
gas_type = 'CO'
risk_level = 'danger'
zone_id = 'ZONE-A'
```

하지만 사용자가 다음처럼 질문하면 단순 단어 검색만으로는 부족할 수 있다.
```
CO가 높을 때 작업자는 어떻게 해야 하나요?
일산화탄소 위험 상황에서 먼저 해야 할 조치는 무엇인가요?
가스 누출 시 대피 절차를 알려주세요.
```

이 질문들은 표현은 다르지만 의미는 비슷하다.  
Vector DB는 이런 의미가 비슷한 문서 조각을 찾아주는 역할을 한다.

즉, Vector DB는 다음 질문에 답하기 위해 사용한다.
```
질문과 의미가 가장 비슷한 문서 내용은 무엇인가?
이 알람 상황과 관련 있는 대응 매뉴얼은 어디에 있는가?
RAG 답변을 만들 때 근거로 사용할 문서 조각은 무엇인가?
```

---
#### RAG 문서 처리 흐름

RAG 문서 데이터는 다음 흐름으로 처리된다.
```
문서 업로드
→ 텍스트 추출
→ Chunking
→ Metadata 부여
→ Embedding
→ Vector DB 저장
→ Hybrid Search
→ RAG 답변 생성
```

각 단계의 의미는 다음과 같다.

|단계|의미|
|---|---|
|문서 업로드|PDF, DOCX, Markdown, 매뉴얼 파일을 시스템에 넣는다.|
|텍스트 추출|문서에서 실제 글자 내용을 뽑아낸다.|
|Chunking|긴 문서를 작은 문단 단위로 나눈다.|
|Metadata 부여|문서 출처, 페이지 번호, 가스 종류, 위험도 같은 정보를 붙인다.|
|Embedding|문서 조각의 의미를 숫자 벡터로 변환한다.|
|Vector DB 저장|벡터와 문서 조각을 검색 가능한 형태로 저장한다.|
|Hybrid Search|키워드 검색과 의미 기반 벡터 검색을 함께 사용한다.|
|RAG 답변 생성|검색된 문서를 근거로 답변을 생성한다.|

---
예시로 이해하기
예를 들어 `CO 위험 대응 매뉴얼.pdf`라는 문서가 있다고 하자.

문서 안에 이런 내용이 있다.
```
CO 농도가 200ppm 이상이면 즉시 위험 상태로 판단하고 작업자를 대피시킨다.
```

이 문서를 RAG에서 사용하려면 먼저 긴 문서를 작은 조각으로 나눈다.

```
chunk_id: CHUNK-001
content: CO 농도가 200ppm 이상이면 즉시 위험 상태로 판단하고 작업자를 대피시킨다.
source_doc: CO 위험 대응 매뉴얼.pdf
page_no: 3
gas_type: CO
risk_level: danger
```

그 다음 이 문장 내용을 Embedding으로 바꾼다.
```
content
→ embedding vector
→ [0.12, -0.43, 0.87, 0.05, ...]
```

실제 벡터는 수백 개 또는 수천 개의 숫자로 이루어져 있다.  
학생들이 모든 숫자를 이해할 필요는 없다. 중요한 것은 문장의 의미를 숫자로 바꿔 검색할 수 있게 만든다는 점이다.

---
Vector DB에 저장되는 것

Vector DB에는 보통 다음 정보가 저장된다.
```
chunk_id
문서 조각 내용
embedding vector
metadata
```

예시는 다음과 같다.
```
chunk_id: CHUNK-001
text: CO 농도가 200ppm 이상이면 즉시 작업자를 대피시킨다.
embedding: [0.12, -0.43, 0.87, ...]
metadata:
  source_doc: CO 위험 대응 매뉴얼.pdf
  page_no: 3
  gas_type: CO
  risk_level: danger
  document_version: 1.0
```

여기서 중요한 것은 `metadata`이다.  
RAG 답변은 단순히 답을 생성하는 것에서 끝나면 안 된다.  
어떤 문서를 근거로 답했는지 출처를 보여줄 수 있어야 한다.

---
Metadata가 중요한 이유
RAG에서 Metadata는 검색 품질과 출처 표시를 위해 필요하다.

예를 들어 CO 위험 알람이 발생했을 때는 CO 관련 문서만 우선 검색하는 것이 좋다.
```
alarm_type = gas_co_danger
gas_type = CO
risk_level = danger
```

이 정보를 문서 chunk의 metadata와 연결하면 다음처럼 검색할 수 있다.
```
CO와 관련된 문서 중에서
danger 상황에 해당하고
대응 절차가 포함된 문서 조각을 찾아라.
```

따라서 문서 chunk에는 다음과 같은 metadata를 붙이는 것이 좋다.
```
source_doc
page_no
document_type
gas_type
risk_level
equipment_type
version
published_at
access_level
```

---
Hybrid Search란 무엇인가?
Hybrid Search는 **키워드 검색과 벡터 검색을 함께 사용하는 방식**이다.

키워드 검색은 정확한 단어를 찾는 데 좋다.
```
CO
200ppm
대피
환기
```

벡터 검색은 의미가 비슷한 문장을 찾는 데 좋다.
```
일산화탄소가 높을 때 어떻게 해야 하나요?
CO 농도가 위험하면 조치 방법은?
가스 위험 상황에서 작업자를 어떻게 보호해야 하나요?
```

그래서 RAG에서는 두 방식을 함께 쓰는 것이 좋다.
```
Keyword Search
→ 정확한 용어 검색에 강함

Vector Search
→ 의미가 비슷한 문서 검색에 강함

Hybrid Search
→ 정확한 단어와 의미 기반 검색을 함께 사용
```

---
#### PostgreSQL과 Vector DB의 차이
| 구분          | PostgreSQL               | Vector DB                       |
| ----------- | ------------------------ | ------------------------------- |
| 주로 저장하는 데이터 | 센서값, 알람, 피드백, 사용자 정보     | 문서 조각, embedding, metadata      |
| 검색 방식       | 조건 검색, 조인, 정렬, 집계        | 의미 기반 유사도 검색                    |
| 예시 질문       | `CO 값이 200 이상인 알람을 조회하라` | `CO 위험 상황에서 어떻게 대응해야 하나?`       |
| 사용 위치       | 운영 데이터, 대시보드, 리포트        | RAG 문서 검색                       |
| 예시 도구       | PostgreSQL, MySQL        | Chroma, FAISS, pgvector, Milvus |

단, `pgvector`를 사용하면 PostgreSQL 안에서도 Vector 검색을 할 수 있다.  
즉, Vector DB는 반드시 별도 서버일 필요는 없고, 수업 환경에서는 `Chroma`, `FAISS`, 또는 `pgvector` 중 하나로 단순하게 시작할 수 있다.

---
#### 관제플랫폼 프로젝트에서 Vector DB가 쓰이는 위치
관제플랫폼에서는 알람이 발생했을 때 RAG가 관련 대응 매뉴얼을 찾아준다.

예를 들어 CO 위험 알람이 발생한 경우 흐름은 다음과 같다.
```
CO 위험 알람 발생
↓
alarm_type = gas_co_danger
↓
RAG Search API 호출
↓
Vector DB에서 CO danger 관련 문서 chunk 검색
↓
검색된 문서를 근거로 대응 절차 생성
↓
대시보드 알람 상세 화면에 표시
```

대시보드에는 다음과 같이 표시할 수 있다.
```
[위험] CO 230ppm / A구역

권장 대응:
1. 작업자를 즉시 대피시킨다.
2. 환기 장치를 가동한다.
3. 안전관리자에게 보고한다.

출처:
- CO 위험 대응 매뉴얼.pdf, 3페이지
- 가스별 임계치 정의서.pdf, 2페이지
```

## 3. 프로젝트 목적

본 프로젝트는 산업안전 관제플랫폼을 예제로 사용하여, AI 서비스가 필요로 하는 데이터를 수집·저장·검증·검색·운영하는 데이터 플랫폼을 구축하는 것을 목표로 한다.

플랫폼은 유해가스 센서, 전력 장비, 작업자 위치 데이터로 위험 상태를 판단한다.

## 4. 이 프로젝트가 단순 대시보드가 아닌 이유

일반적인 대시보드는 데이터를 화면에 보여주는 데 집중한다.

하지만 본 수업에서는 다음을 함께 구현한다.

데이터 계약
Raw/Staging/Mart
Lakehouse 저장 구조
Airflow 자동화
Kafka/Spark 실시간 처리
Data Quality
Data Lineage
RAG 문서 데이터 파이프라인
피드백 데이터 수집
재학습 후보 데이터셋
DataOps 모니터링
```

따라서 이 프로젝트는 단순 웹 대시보드가 아니라 AI 서비스 운영을 위한 데이터 플랫폼이다.

서비스 로그는 디버깅용 로그가 아니라 AI 서비스 품질을 개선하는 데이터 자산이다.

# 임계치 정의

## 1. 목적

이 문서는 수업용 위험도 판단 기준을 정의한다.

초기 위험도 판단은 AI가 아니라 임계치와 지오펜스 규칙을 기준으로 한다. AI 이상탐지는 후반부에서 보조 판단 또는 review 상태로 연결한다.

## 2. 위험도 단계

| 단계 | 의미 |
|---|---|
| normal | 정상 |
| warning | 주의 |
| danger | 위험 |
| sensor_error | 센서 오류 또는 통신 불능 |
| review | AI 또는 운영자 검토 필요 |

## 3. 가스별 임계치

| 가스 | 단위 | normal | warning | danger |
|---|---|---|---|---|
| CO | ppm | 25 미만 | 25 이상 200 미만 | 200 이상 |

## 4. 전력 위험도 기준

1. 센서 시뮬레이터에서 정상 데이터가 발생한다.
2. FastAPI Collector가 데이터를 수집하고 Raw에 저장한다.
3. Staging 검증을 통과한 데이터가 Mart로 생성된다.
4. 실시간 스트리밍으로 대시보드에 현재 상태가 표시된다.
5. 위험 시나리오를 실행한다.
6. CO 또는 H2S 수치가 위험 기준을 초과한다.
7. 작업자가 위험구역에 진입한다.
8. Risk Engine이 위험 이벤트를 생성한다.
9. 알람이 대시보드에 표시된다.
10. RAG가 해당 위험 유형의 대응 매뉴얼을 검색한다.
11. 운영자가 알람을 확인하고 조치 결과를 피드백으로 남긴다.
12. 피드백 데이터가 재학습 후보 데이터셋으로 연결된다.
13. dbt/Data Quality 결과와 Data Lineage를 확인한다.
14. Grafana에서 수집 지연, 오류, 품질 실패, RAG 검색 상태를 확인한다.
15. 최종적으로 전체 데이터 흐름이 운영 가능한 구조임을 설명한다.
```

## 3. 시연 시나리오 상세

### 시나리오 1. 정상 데이터 수집

- Gas Sensor Simulator가 정상 데이터를 생성한다.
- Power Sensor Simulator가 전력 데이터를 생성한다.
- Worker Location Simulator가 위치 데이터를 생성한다.
- Collector가 데이터를 수집한다.
- Raw에 원본이 저장된다.
- Staging 검증을 통과한다.
- Mart에 현재 상태가 만들어진다.
- 대시보드에 normal 상태가 표시된다.

### 시나리오 2. 위험 데이터 발생

- CO 또는 H2S 값이 warning/danger 기준을 넘는다.
- Risk Engine이 위험도를 판단한다.
- risk_event_detected 이벤트가 생성된다.
- alarm_created 이벤트가 생성된다.
- 대시보드에 알람이 표시된다.

### 시나리오 3. 작업자 위험구역 진입

- 작업자 위치 이벤트가 들어온다.
- 지오펜스 내부 여부를 확인한다.
- 위험구역 진입 이벤트를 생성한다.
- 해당 구역의 센서 상태와 결합한다.
- danger 조건이면 알람을 생성한다.

### 시나리오 4. AI 이상탐지 연결

- 최근 센서 또는 전력 패턴을 AI 추론 입력으로 사용한다.
- AI 이상탐지 결과를 저장한다.
- AI 결과는 즉시 danger로 확정하지 않고 review 또는 보조 정보로 표시한다.
- 이후 운영자 피드백과 연결한다.

### 시나리오 5. RAG 대응 매뉴얼 검색

- 알람 유형을 기준으로 관련 문서를 검색한다.
- 문서 chunk와 metadata를 사용한다.
- 대응 절차와 출처를 알람 상세 화면에 표시한다.

### 시나리오 6. 피드백과 재학습 후보

- 운영자가 알람을 확인한다.
- true_alarm 또는 false_alarm 피드백을 남긴다.
- 피드백은 mart_ai_training_dataset 후보로 연결된다.

### 시나리오 7. Data Quality와 DataOps

- 중복 event_id 데이터를 감지한다.
- 지연 도착 데이터를 감지한다.
- 결측 또는 범위 오류 데이터를 validation_errors로 분리한다.
- dbt/Data Quality 결과를 확인한다.
- Grafana에서 수집 지연, 오류율, 품질 실패율을 확인한다.

# 34. 0단계의 최종 의미

0단계는 개발을 늦추는 단계가 아니다.  
오히려 이후 개발이 흔들리지 않도록 기준을 고정하는 단계이다.

0단계가 끝나면 학생들은 다음을 알고 있어야 한다.

```text
우리가 만드는 것은 단순 관제 대시보드가 아니라 AI 네이티브 데이터 플랫폼이다.
디코나이 관제플랫폼은 실습 도메인이다.
센서 데이터뿐 아니라 로그, 문서, 피드백, 품질 데이터까지 다룬다.
데이터는 Raw/Staging/Mart/Lakehouse/Vector DB로 목적에 따라 나뉜다.
AI와 RAG는 데이터 흐름 위에 연결된다.
피드백은 운영 데이터이자 학습 후보 데이터이다.
수업은 7개 교과목과 3개 프로젝트 구조로 진행된다.
```

한 문장으로 정리하면 다음과 같다.

> 0단계는 Django 껍데기 프로젝트를 AI 네이티브 데이터 플랫폼 수업 프로젝트로 확장하기 위해, 코드 작성 전에 목적·데이터·흐름·산출물·브랜치 기준을 고정하는 단계이다.
