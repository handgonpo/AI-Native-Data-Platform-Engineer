#### 4.1 교과목 목표

이 과목의 목표는 AI 서비스에서 발생하는 **대용량 로그와 실시간 이벤트를 안정적으로 처리하고, 위험 판단 결과를 관제 화면에 끊기지 않게 전달하는 구조를 이해하고 구현하는 것**이다.

1단계에서는 전체 아키텍처와 데이터 흐름을 정의했다.  
2단계에서는 센서, 전력, 작업자 위치, 로그, 피드백 데이터를 수집하고 Raw Zone에 저장했다.  
3단계에서는 Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환하는 배치 파이프라인을 만들었다.

4단계에서는 여기서 한 단계 더 나아가, **실시간으로 계속 들어오는 이벤트를 Kafka Topic으로 흘려보내고, Spark Structured Streaming 또는 Consumer를 통해 Window 집계, 중복 제거, 지연 이벤트 처리를 수행한 뒤, AI 위험 판단 결과와 대시보드 Metric으로 연결하는 흐름**을 만든다.

AI 관제 서비스에서는 단순히 데이터를 저장하는 것만으로는 부족하다.  
센서값이 들어오는 즉시 위험 여부를 판단하고, 작업자 위치 변화와 위험구역 진입을 감지하며, 알람과 AI 판단 결과를 실시간으로 화면에 반영해야 한다.

따라서 이 과목에서는 다음을 학습한다.
```text
실시간 이벤트란 무엇인가?
배치 처리와 스트리밍 처리는 무엇이 다른가?
Kafka Topic, Partition, Producer, Consumer는 어떤 역할을 하는가?
Consumer Group과 Offset은 왜 필요한가?
event_time과 processing_time은 왜 구분해야 하는가?
Window 집계는 왜 필요한가?
Watermark는 지연 이벤트 처리에 어떻게 사용되는가?
중복 이벤트는 어떻게 제거하는가?
실시간 위험 판단 결과는 어떻게 Dashboard Metric으로 바뀌는가?
WebSocket은 실시간 대시보드에서 어떤 역할을 하는가?
```

산업안전 관제플랫폼 실습에서는 유해가스 센서 이벤트, 전력 사용량 이벤트, 작업자 위치 이벤트, AI 추론 이벤트, 알람 이벤트를 Kafka Topic으로 분리하고, 실시간 위험 판단 결과를 Django/DRF/WebSocket을 통해 관제 대시보드에 반영한다.

#### 4.2 이 과목의 위치

4단계는 3단계에서 만든 배치 기반 데이터 파이프라인 위에 실시간 이벤트 처리 흐름을 추가하는 단계이다.
```text
1단계: 어떤 데이터를 다룰지와 전체 구조를 정의한다.
→ 2단계: 데이터를 수집하고 Raw Zone에 저장한다.
→ 3단계: Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환한다.
→ 4단계: 실시간 이벤트를 Kafka/Spark로 처리하고 Dashboard에 연결한다.
→ 5단계: 실시간/배치 데이터의 품질, 계보, 거버넌스를 점검한다.
```

3단계까지 만든 Mart와 기준정보는 4단계 실시간 판단의 기준 데이터가 된다.  
예를 들어 `gas_thresholds`, `zones`, `mart_current_sensor_status`, `mart_risk_status`는 실시간 이벤트가 들어왔을 때 위험 여부를 판단하는 기준으로 사용된다.

즉, 4단계는 다음 흐름을 만드는 단계이다.
```text
실시간 이벤트 발생
→ Kafka Topic 발행
→ Consumer 또는 Spark Streaming 처리
→ Window 집계 / 중복 제거 / 지연 이벤트 처리
→ Risk Engine 판단
→ AIResult / AlarmEvent 저장
→ WebSocket으로 Dashboard 반영
```

#### 4.12 Window와 Watermark 기준

실시간 데이터는 한 건씩만 보면 위험 흐름을 판단하기 어렵다.  
그래서 최근 일정 시간의 데이터를 묶어 Window로 본다.

##### Window 예시
```text
1분 Window:
최근 1분 동안 구역별 평균 가스 농도 계산

5분 Window:
최근 5분 동안 전력 사용량 변화율 계산

최근 N개 Window:
최근 30개 센서값을 기준으로 Z-score 또는 변화 추세 계산

작업자 체류 Window:
작업자가 위험구역에 머문 시간을 계산
```

##### event_time과 processing_time
```text
event_time:
센서값이 실제로 발생한 시간

processing_time:
시스템이 그 이벤트를 처리한 시간
```

두 시간이 다른 이유는 네트워크 지연, 장비 지연, 서버 처리 지연이 발생할 수 있기 때문이다.

##### Watermark
Watermark는 “얼마나 늦게 도착한 이벤트까지 집계에 포함할 것인가”를 정하는 기준이다.
```text
예시:
event_time 기준 5분 Window를 집계한다.
Watermark를 2분으로 둔다.
그러면 최대 2분 늦게 도착한 이벤트까지는 집계에 반영한다.
```

#### 4.13 중복 이벤트와 지연 이벤트 처리 기준

##### 중복 이벤트

같은 `event_id`가 여러 번 들어오면 같은 알람이 여러 번 생성될 수 있다.  
따라서 실시간 처리에서는 event_id 기준 중복 제거가 필요하다.

```text
중복 제거 기준:
event_id가 같으면 같은 이벤트로 본다.
같은 sensor_id + event_time + event_type 조합도 중복 후보로 볼 수 있다.
```

##### 지연 이벤트

늦게 도착한 이벤트는 무조건 버리면 안 된다.  
위험 상황이 늦게 도착했더라도 품질 리포트와 계보 추적에는 필요할 수 있다.

```text
처리 기준:
Watermark 안에 들어오면 집계에 포함한다.
Watermark를 초과하면 late_event로 분리한다.
late_event는 품질 리포트와 재처리 후보로 남긴다.
```

##### 지연 이벤트 저장 위치 예시
```text
data_lake/
  streaming/
    late_events/
    duplicate_events/
    processing_errors/
```

#### 4.14 실시간 위험 판단 엔진

4단계에서는 복잡한 AI 모델보다, 먼저 실시간 판단 흐름을 이해하는 것이 중요하다.  
따라서 다음 순서로 위험 판단을 구성한다.

```text
1. Threshold 즉시 판단
2. Sliding Window로 최근 데이터 유지
3. Z-score로 평소보다 튄 값 감지
4. Change Point로 추세 변화 감지
5. 간단한 이상탐지 모델 또는 Mock AI 결과 연결
6. 최종 Risk Level 결정
7. AlarmEvent 생성
```

##### 판단 모듈 역할

| 판단 모듈 | 역할 | 출력 예시 |
|---|---|---|
| Threshold | 현재값이 임계치를 넘었는지 즉시 판단 | `normal`, `warning`, `danger` |
| Sliding Window | 최근 N개 값을 유지 | 최근 30개 센서값 |
| Z-score | 평소보다 갑자기 튄 값인지 판단 | `ANOMALY_WARNING` |
| Change Point | 값의 흐름이 바뀌는 지점 감지 | `TREND_SHIFT` |
| Mock AI / ML Model | 복합 패턴 이상 여부 판단 | `ML_ANOMALY` |
| Policy Engine | 여러 결과를 합쳐 최종 위험도 결정 | `final_risk_level` |

##### 최종 Risk Event 예시
```json
{
  "event_id": "risk-20260721-0001",
  "event_type": "risk_event_detected",
  "sensor_id": "gas_sensor_01",
  "zone_id": "A_ZONE",
  "risk_level": "warning",
  "reason": "CO 농도가 최근 5분 평균 대비 급격히 상승했습니다.",
  "source": "streaming_risk_engine",
  "event_time": "2026-07-21T09:05:00"
}
```

#### 4.18 데이터 엔지니어링 디자인 패턴 적용

4단계에서는 오류 관리, 데이터 흐름, 관찰 가능성 패턴을 중심으로 적용한다.  
패턴을 암기하는 것이 목적이 아니라, 실시간 데이터에서 자주 발생하는 문제를 어떻게 설계로 해결하는지 이해하는 것이 목적이다.

| 패턴 영역 | 적용 패턴 | 4단계 적용 방식 |
|---|---|---|
| 오류 관리 | 윈도 중복 제거 | Window 안에서 같은 event_id를 가진 이벤트 제거 |
| 오류 관리 | 지연 데이터 탐지기 | event_time과 processing_time 차이로 지연 이벤트 감지 |
| 오류 관리 | 정적 지연 데이터 통합기 | 고정 Watermark 안에 도착한 지연 이벤트를 집계에 포함 |
| 오류 관리 | 동적 지연 데이터 통합기 | 이벤트 유형별 허용 지연 시간을 다르게 적용 |
| 데이터 흐름 | 정렬된 팬인 | 가스, 전력, 위치 이벤트를 event_time 기준으로 통합 |
| 데이터 흐름 | 비정렬 팬인 | 순서가 완벽하지 않아도 수집 후 집계 가능하게 처리 |
| 데이터 흐름 | 병렬 분할 | 동일 이벤트를 저장, 대시보드, AI 판단, 품질 모니터링으로 분기 |
| 데이터 흐름 | 배타적 선택 | risk_level에 따라 normal, warning, danger 처리 경로 분리 |
| 관찰 가능성 | 지연 탐지기 | 수집 지연과 처리 지연을 Metric으로 기록 |
| 관찰 가능성 | 흐름 중단 탐지기 | 일정 시간 이벤트가 들어오지 않으면 수집 중단으로 표시 |

#### 4.21 4단계에서 하지 않는 것

4단계는 실시간 이벤트 처리와 대시보드 연결을 만드는 단계이다.  
다음 작업은 이후 단계에서 다룬다.
```text
데이터 품질 전체 체계 완성하지 않기
dbt Test 전체 구현하지 않기
Data Lineage 리포트 완성하지 않기
RAG 문서 Chunking과 Embedding 구현하지 않기
RAG 답변 생성 기능 완성하지 않기
피드백 재학습 후보 데이터셋 완성하지 않기
Prometheus/Grafana 운영 대시보드 전체 완성하지 않기
Kubernetes 배포까지 확장하지 않기
```

단, 5단계 이후 품질과 관찰 가능성으로 연결될 수 있도록 다음 Metric은 남길 수 있게 한다.
```text
late_event_count
duplicate_event_count
processing_latency_ms
consumer_lag
streaming_job_status
dashboard_push_failure_count
```

4단계가 끝났을 때 다음 질문에 답할 수 있어야 한다.
```text
배치 처리와 스트리밍 처리는 무엇이 다른가?
Kafka Topic은 왜 이벤트 유형별로 나누는가?
Partition은 왜 필요한가?
Message Key는 어떤 기준으로 정하는가?
Producer와 Consumer는 각각 어떤 역할을 하는가?
Consumer Group은 왜 필요한가?
Offset과 Consumer Lag은 무엇인가?
event_time과 processing_time은 왜 구분해야 하는가?
Window 집계는 일반 집계와 무엇이 다른가?
Watermark는 지연 이벤트 처리에 어떻게 사용되는가?
중복 이벤트는 AI 판단과 대시보드에 어떤 문제를 만드는가?
지연 이벤트를 무조건 버리면 어떤 문제가 생기는가?

4단계에서 생성한 실시간 이벤트와 Metric이 5단계 품질/계보/관찰 가능성으로 어떻게 연결되는가?
```

#### 4.23 5단계와의 연결

4단계의 결과물은 5단계의 입력이 된다.
```text
4단계 결과물
- Kafka Topic 설계
- 실시간 이벤트 흐름
- Window Metric
- 중복 이벤트 기록
- 지연 이벤트 기록
- Risk Event
- AlarmEvent
- Dashboard Metric
- Consumer Lag 기록
- 처리 지연 Metric

5단계에서 할 일
- 실시간 데이터 품질 기준을 정의한다.
- 지연 이벤트와 중복 이벤트를 품질 리포트에 포함한다.
- Risk Event가 어떤 Raw Event에서 시작되었는지 Lineage를 추적한다.
- Dashboard Metric의 신뢰성을 검증한다.
- Consumer Lag, 처리 지연, 흐름 중단을 관찰 가능성 지표로 만든다.
```

따라서 4단계의 핵심은 다음 한 문장으로 정리할 수 있다.
```text
4단계는 실시간으로 발생하는 데이터를 Kafka/Spark로 안전하게 처리하고,
위험 판단 결과를 대시보드에 끊기지 않게 전달하며,
이 과정에서 발생하는 중복, 지연, 처리 실패를 추적 가능한 데이터로 남기는 단계이다.
```

#### 4.24 최종 정리 문장
```text
실시간 이벤트 스트리밍은 단순히 데이터를 빠르게 보내는 일이 아니다.
AI 관제 서비스가 현재 상황을 놓치지 않도록,
이벤트를 안전하게 전달하고,
시간 기준으로 집계하고,
중복과 지연을 처리하고,
위험 판단 결과를 화면과 운영 지표로 연결하는 일이다.
```
