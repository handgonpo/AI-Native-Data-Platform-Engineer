#### 3.1 교과목 목표

이 과목의 목표는 2단계에서 수집한 Raw 데이터를 **자동으로 검증하고, Staging과 Mart로 변환하며, AI 학습 후보 데이터셋과 품질 리포트를 생성하는 데이터 파이프라인을 설계하고 구현하는 것**이다.

2단계에서는 FastAPI Collector, Data Contract, Raw Zone, Dead Letter, 기준정보 구조를 만들었다.  
3단계에서는 이 데이터를 수동으로 처리하지 않고, Airflow와 Python 파이프라인을 사용해 반복 가능한 자동 처리 흐름으로 바꾼다.

AI 서비스는 Raw 데이터를 그대로 사용하지 않는다.  
센서값, 전력 데이터, 작업자 위치 데이터, 알람 데이터, 피드백 데이터는 검증, 정제, 조인, 집계 과정을 거쳐야 대시보드, AI 학습 데이터셋, 운영 리포트에 사용할 수 있다.

따라서 이 과목에서는 다음을 학습한다.
```text
Airflow는 무엇인가?
DAG와 Task는 무엇인가?
Raw 데이터를 Staging으로 변환한다는 것은 무엇인가?
Staging 데이터와 Mart 데이터는 어떻게 다른가?
AI Training Dataset은 어떻게 만들어지는가?
Quality Report는 왜 필요한가?
Retry와 Backfill은 어떻게 다른가?
Checkpoint와 Marker는 왜 필요한가?
멱등성은 왜 운영 파이프라인에서 중요한가?
같은 파이프라인을 다시 실행해도 결과가 안전하려면 어떻게 설계해야 하는가?
```

산업안전 관제플랫폼 실습에서는 2단계에서 저장한 유해가스 센서 Raw 데이터, 전력 Raw 데이터, 작업자 위치 Raw 데이터, AI 서비스 로그, 피드백 로그를 읽어 Staging 데이터, Risk Mart, Alarm Summary Mart, AI Training Dataset, Feedback Mart, Quality Report로 변환하는 구조를 만든다.

---
#### 3.2 이 과목의 위치

3단계는 2단계에서 만든 데이터 수집 구조를 운영 가능한 자동 파이프라인으로 확장하는 단계이다.
```text
1단계: 어떤 데이터를 다룰지와 전체 구조를 정의한다.
→ 2단계: 데이터를 실제로 수집하고 Raw/Staging/Mart 저장 구조를 설계한다.
→ 3단계: 수집된 Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환한다.
→ 4단계: 실시간 이벤트와 AI 판단 결과를 대시보드에 연결한다.
```

3단계에서 만든 Staging, Mart, AI Training Dataset, Quality Report는 이후 4단계 실시간 이벤트 처리, 5단계 데이터 품질/계보, 7단계 DataOps 운영의 기준 데이터가 된다.

즉, 3단계는 데이터 플랫폼이 “수집된 파일 모음”에서 “운영 가능한 데이터 처리 시스템”으로 바뀌는 단계이다.

#### 3.9 Pipeline 패키지 구조

3단계에서는 반복되는 데이터 처리 코드를 `pipeline/` 패키지로 분리한다.  
Airflow DAG는 직접 모든 로직을 작성하는 곳이 아니라, `pipeline/`에 있는 함수를 호출하는 실행 관리자 역할을 한다.

권장 구조
```text
project-root/
  pipeline/
    __init__.py
    config.py
    paths.py
    raw_reader.py
    validators.py
    staging.py
    mart.py
    training_dataset.py
    feedback_mart.py
    freshness.py
    quality_report.py
    markers.py
    backfill.py
    utils.py

  airflow/
    dags/
      validate_raw_to_staging.py
      build_risk_mart.py
      build_alarm_summary.py
      build_ai_training_dataset.py
      build_feedback_mart.py
      check_data_freshness.py
      backfill_missing_sensor_data.py
      export_quality_report.py
```

역할은 다음과 같다.

| 파일 | 역할 |
|---|---|
| `config.py` | 환경 변수, 기본 경로, 실행 옵션 관리 |
| `paths.py` | Raw, Staging, Mart, Report 경로 생성 |
| `raw_reader.py` | Raw JSONL 파일 읽기 |
| `validators.py` | 필수값, 타입, 범위, 중복 검증 |
| `staging.py` | Raw 데이터를 Staging Parquet으로 변환 |
| `mart.py` | Risk Mart, Alarm Summary Mart 생성 |
| `training_dataset.py` | AI 학습 후보 데이터셋 생성 |
| `feedback_mart.py` | 피드백 분석용 Mart 생성 |
| `freshness.py` | 최근 데이터 수집 여부 점검 |
| `quality_report.py` | 품질 리포트 생성 |
| `markers.py` | 처리 완료 위치와 실행 상태 기록 |
| `backfill.py` | 특정 기간 재처리 |

#### 3.10 Airflow DAG 설계

3단계에서 구현할 기본 DAG는 다음과 같다.
```text
01_validate_raw_to_staging
02_build_risk_mart
03_build_alarm_summary
04_build_ai_training_dataset
05_build_feedback_mart
06_check_data_freshness
07_backfill_missing_sensor_data
08_export_quality_report
```

##### DAG별 역할

| DAG | 목적 | 주요 입력 | 주요 출력 |
|---|---|---|---|
| `validate_raw_to_staging` | Raw 데이터를 검증하여 Staging으로 적재 | Raw JSONL, Raw Tables | `stg_*`, `validation_errors` |
| `build_risk_mart` | 위험도 판단에 필요한 Mart 생성 | `stg_gas`, `stg_power`, `thresholds`, `zones` | `mart_risk_status` |
| `build_alarm_summary` | 알람 통계 생성 | `alarm_records`, `risk_events` | `mart_alarm_summary` |
| `build_ai_training_dataset` | AI 학습 후보 데이터셋 생성 | `stg_*`, `alarm`, `feedback` | `mart_ai_training_dataset` |
| `build_feedback_mart` | 피드백 분석용 Mart 생성 | `feedback_logs`, `alarm_records` | `mart_feedback_summary` |
| `check_data_freshness` | 최근 데이터 수집 여부 점검 | raw/staging data | `freshness_check_results` |
| `backfill_missing_sensor_data` | 누락 기간 재처리 | raw files, target date | stg/mart 재생성 |
| `export_quality_report` | 품질 결과 문서화 | validation errors, freshness results | quality report |

##### DAG 실행 흐름
```text
validate_raw_to_staging
        ↓
build_risk_mart
        ↓
build_alarm_summary
        ↓
build_ai_training_dataset
        ↓
build_feedback_mart
        ↓
check_data_freshness
        ↓
export_quality_report
```

Backfill DAG는 일반 스케줄 DAG와 분리해서 필요할 때 실행한다.

#### 3.11 Raw → Staging 설계

Raw 데이터는 원본 보존이 목적이고, Staging 데이터는 분석과 처리에 사용할 수 있도록 정리된 데이터이다.

##### Raw 데이터의 특징
```text
원본 JSON 구조를 최대한 유지한다.
schema_version을 포함한다.
event_time과 ingestion_time을 함께 가진다.
오류가 있더라도 보존될 수 있다.
재처리의 기준이 된다.
```

##### Staging 데이터의 특징
```text
필수 필드가 존재한다.
타입이 정리되어 있다.
시간 필드가 표준 형식으로 변환되어 있다.
중복 후보가 제거되거나 표시되어 있다.
분석과 조인에 필요한 컬럼이 분리되어 있다.
Parquet 또는 PostgreSQL 테이블로 저장된다.
```

##### 검증 항목
```text
event_id 존재 여부
event_id 중복 여부
event_type 허용값 여부
schema_version 지원 여부
sensor_id 또는 worker_id 존재 여부
event_time 형식 확인
ingestion_time 존재 여부
가스 농도 범위 확인
전력 사용량 범위 확인
작업자 위치 좌표 범위 확인
zone_id 기준정보 연결 여부
```

##### Staging 출력 예시
```text
data_lake/
  staging/
    gas_measurements/date=YYYY-MM-DD/
    power_measurements/date=YYYY-MM-DD/
    worker_locations/date=YYYY-MM-DD/
    ai_service_logs/date=YYYY-MM-DD/
    feedback_events/date=YYYY-MM-DD/
```

#### 3.12 Mart와 AI Training Dataset 설계

Mart는 목적별로 만들어진 데이터셋이다.  
Raw나 Staging은 범용 처리용 데이터에 가깝고, Mart는 실제 사용 목적이 분명한 데이터이다.

##### Risk Mart
```text
목적:
센서값, 전력 사용량, 작업자 위치, 위험구역, 임계치 기준을 결합하여 위험 판단에 사용할 수 있는 데이터셋을 만든다.

입력:
stg_gas_measurements
stg_power_measurements
stg_worker_locations
gas_thresholds
zones
geofences

출력:
mart_risk_status
```

##### Alarm Summary Mart
```text
목적:
알람 유형, 위험도, 구역, 시간대별 알람 발생 현황을 대시보드와 운영 리포트에서 사용할 수 있게 집계한다.
```

#### 3.13 Marker, Checkpoint, 멱등성, Backfill

3단계에서 가장 중요한 운영 개념은 Marker, Checkpoint, 멱등성, Backfill이다.

##### Marker

Marker는 특정 데이터 또는 특정 날짜의 처리가 완료되었는지 표시하는 작은 기록이다.
```text
예시:
2026-07-21 gas_events Raw 처리 완료
2026-07-21 stg_gas_measurements 생성 완료
2026-07-21 mart_risk_status 생성 완료
```

##### Checkpoint

Checkpoint는 파이프라인이 어디까지 처리했는지 기록하는 기준이다.
```text
마지막 처리 event_time
마지막 처리 event_id
마지막 성공한 partition
마지막 성공한 DAG run id
```

##### 멱등성

멱등성은 같은 작업을 여러 번 실행해도 결과가 중복되거나 깨지지 않는 성질이다.
```text
같은 날짜의 Staging을 다시 만들면 같은 결과가 나와야 한다.
같은 event_id가 여러 번 들어와도 중복 저장되지 않아야 한다.
실패 후 재실행해도 Mart 결과가 두 배로 늘어나면 안 된다.
```

권장 방식은 다음과 같다.
```text
처리 대상 날짜를 명시한다.
해당 날짜 partition을 삭제 후 재생성한다.
임시 경로에 먼저 쓰고 성공 후 최종 경로로 교체한다.
event_id 기준 중복 제거를 수행한다.
실행 로그와 row_count, checksum을 남긴다.
```

##### Backfill

Backfill은 과거 기간의 데이터를 다시 처리하는 작업이다.
```text
누락된 날짜 데이터 재처리
스키마 수정 후 과거 Raw 재처리
임계치 기준 변경 후 Risk Mart 재생성
품질 오류 수정 후 Training Dataset 재생성
```

#### 3.17 데이터 엔지니어링 디자인 패턴 적용

3단계에서는 오류 관리, 멱등성, 데이터 가치, 데이터 흐름, 관찰 가능성 패턴을 적용한다.  
패턴을 암기하는 것이 목적이 아니라, “운영 가능한 파이프라인을 왜 이렇게 설계하는가”를 이해하는 것이 목적이다.

| 패턴 영역 | 적용 패턴 | 3단계 적용 방식 |
|---|---|---|
| 데이터 수집 | 준비 마커 | Raw 데이터 적재 완료 표시가 있는 날짜만 Staging 처리 |
| 오류 관리 | 데드 레터 | Staging 검증 실패 데이터를 별도 보관 |
| 오류 관리 | 체크포인터 | 실패 후 재실행 시 어디서부터 처리할지 기록 |
| 멱등성 | 데이터 덮어쓰기 | 특정 날짜 Staging/Mart partition을 삭제 후 재생성 |
| 멱등성 | 병합기 | 새 피드백과 기존 피드백 요약을 병합 |
| 멱등성 | 키 기반 멱등성 | event_id 기준 중복 적재 방지 |
| 멱등성 | 트랜잭션 기반 작성자 | 검증 완료 후 결과를 한 번에 반영 |
| 데이터 가치 | 정적 조이너 | 센서 데이터와 임계치 기준정보 조인 |
| 데이터 가치 | 동적 조이너 | 최근 위치 상태와 위험구역 상태 결합 |
| 데이터 가치 | 로컬 집계기 | 구역별, 시간대별, 알람 유형별 집계 |
| 데이터 흐름 | 단일 실행기 | 같은 날짜의 Mart 생성은 한 번만 성공 상태로 관리 |

#### 3.20 3단계에서 하지 않는 것

3단계는 배치 파이프라인 자동화 단계이다.  
다음 작업은 이후 단계에서 다룬다.
```text
Kafka Producer/Consumer 구현하지 않기
Spark Streaming 구현하지 않기
실시간 WebSocket 대시보드 구현하지 않기
AI 모델을 본격 학습하지 않기
RAG 임베딩 생성하지 않기
dbt 품질 체계를 본격 구축하지 않기
Prometheus/Grafana 운영 모니터링 구현하지 않기
Kubernetes 배포를 구현하지 않기
```

단, 4단계 이후에 연결될 수 있도록 Mart, Training Dataset, Quality Report, Handoff 문서는 미리 만들어둔다.

---
#### 3.21 점검 기준

3단계가 끝났을 때 다음 질문에 답할 수 있어야 한다.
```text
Airflow는 왜 필요한가?
DAG와 Task는 무엇인가?
Raw 데이터를 Staging으로 변환한다는 것은 무엇인가?
Staging과 Mart는 어떻게 다른가?
Mart 데이터는 왜 Raw에서 바로 만들지 않는가?
AI Training Dataset은 어떤 데이터로 만들어지는가?
Retry와 Backfill은 어떻게 다른가?
Marker와 Checkpoint는 왜 필요한가?
멱등성은 왜 운영 파이프라인에서 중요한가?
같은 DAG를 다시 실행해도 데이터가 중복되지 않게 하려면 어떻게 해야 하는가?
Freshness Check는 무엇을 확인하는가?
Quality Report에는 어떤 항목이 들어가야 하는가?
3단계에서 만든 Mart와 Training Dataset은 4단계 실시간 처리와 어떻게 연결되는가?
```

---
#### 3.22 4단계와의 연결

3단계의 결과물은 4단계의 입력이 된다.
```text
3단계 결과물
- Staging Parquet
- Risk Mart
- Alarm Summary Mart
- AI Training Dataset
- Feedback Mart
- Freshness Check Result
- Quality Report
- Marker / Checkpoint

4단계에서 할 일
- 실시간 센서 이벤트를 Kafka Topic으로 보낸다.
- 실시간 이벤트를 Window 단위로 처리한다.
- 중복 이벤트와 지연 이벤트를 처리한다.
- Risk Mart와 실시간 이벤트를 비교하거나 보완한다.
- AI 위험 판단 결과를 생성한다.
- Dashboard Metric을 만든다.
- WebSocket으로 관제 화면에 반영한다.
```

따라서 3단계의 핵심은 다음 한 문장으로 정리할 수 있다.
```text
3단계는 2단계에서 수집한 Raw 데이터를 자동으로 검증하고,
AI와 대시보드가 사용할 수 있는 Staging, Mart, Training Dataset으로 바꾸며,
실패해도 재실행 가능한 운영 파이프라인을 만드는 단계이다.
```

#### 3.23 최종 정리 문장
```text
데이터 파이프라인 자동화는 단순히 스크립트를 Airflow에 올리는 일이 아니다.
Raw 데이터를 신뢰 가능한 Staging으로 바꾸고,
목적별 Mart와 AI 학습 후보 데이터셋을 만들며,
실패와 재실행, 품질 점검, 재처리까지 고려한 운영 가능한 데이터 흐름을 만드는 일이다.
```
