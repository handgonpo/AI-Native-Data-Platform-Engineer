#### 2.1 교과목 목표

이 과목의 목표는 AI 서비스가 사용할 수 있는 데이터를 **안정적으로 수집하고, 원본을 보존하며, 검증 가능한 저장 구조를 설계하는 것**이다.

1단계에서는 AI 서비스와 데이터 플랫폼의 전체 아키텍처, 데이터 흐름, 도메인 이벤트, 시스템 경계를 정의했다.  
2단계에서는 그 설계를 실제 데이터 수집 구조로 바꾼다.

AI 서비스는 단순히 DB 테이블 하나에 데이터를 저장한다고 운영되지 않는다.  
원본 데이터는 손상되지 않게 보존되어야 하고, 검증 실패 데이터는 추적 가능해야 하며, 이후 AI, RAG, 대시보드, DataOps가 사용할 수 있도록 Raw, Staging, Mart 구조가 분리되어야 한다.

따라서 이 과목에서는 다음을 학습한다.
```text
데이터 수집이란 무엇인가?
API로 데이터를 받는다는 것은 무엇인가?
JSON, CSV, JSONL, Parquet은 어떻게 다른가?
Data Contract는 왜 필요한가?
schema_version은 왜 관리해야 하는가?
Raw 데이터는 왜 원본 그대로 저장해야 하는가?
Staging 데이터는 왜 검증된 구조로 분리해야 하는가?
Mart 데이터는 어떤 목적을 위해 만드는가?
오류 데이터는 왜 Dead Letter로 분리해야 하는가?
레이크하우스 구조는 AI 서비스 운영과 어떻게 연결되는가?
```

산업안전 관제플랫폼 실습에서는 유해가스 센서 데이터, 전력 사용량 데이터, 작업자 위치 데이터, AI 서비스 로그, RAG 문서 메타데이터, 사용자 피드백 데이터를 수집하고 Raw Zone에 저장하는 구조를 만든다.

---
#### 2.2 이 과목의 위치

2단계는 1단계에서 정의한 아키텍처를 실제 데이터 수집 구조로 구현하는 단계이다.
```text
1단계: 어떤 데이터를 다룰지와 전체 구조를 정의한다.
→ 2단계: 데이터를 실제로 수집하고 Raw/Staging/Mart 저장 구조를 설계한다.
→ 3단계: 수집된 Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환한다.
```

2단계에서 만든 Collector API, Data Contract, Raw Zone, Dead Letter 구조는 3단계 Airflow 파이프라인의 입력이 된다.

즉, 2단계는 이후 모든 데이터 처리의 출발점이다.

#### 2.3 핵심 질문

```text
AI 서비스가 사용할 데이터를 신뢰할 수 있게 만들려면,
데이터를 어떤 계약으로 받고,
어떤 형식으로 저장하고,
정상 데이터와 오류 데이터를 어떻게 분리해야 하는가?
```

이 질문을 다음 관점으로 나누어 이해한다.
```text
데이터 발생 관점:
이 데이터는 센서, 로그, 문서, 사용자 피드백 중 어디에서 발생하는가?

데이터 수집 관점:
이 데이터는 API, 파일, 로그, 이벤트 중 어떤 방식으로 들어오는가?

데이터 계약 관점:
필수 필드, 타입, 단위, schema_version은 어떻게 정의되는가?

저장 관점:
원본 데이터는 Raw에 어떻게 저장되는가?

검증 관점:
Staging으로 이동하기 전에 무엇을 확인해야 하는가?

오류 관리 관점:
잘못된 데이터는 버리는가, 아니면 Dead Letter로 남기는가?

운영 관점:
수집 실패, 검증 실패, 중복 데이터, 스키마 오류를 어떻게 추적할 것인가?

활용 관점:
이 데이터는 이후 AI, RAG, 대시보드, 품질 리포트 중 어디에 쓰이는가?
```

이 과목부터 실제 코드와 저장 구조를 만든다.


#### 2.10 레이크하우스 저장 구조

2단계에서는 완성된 Lakehouse 플랫폼을 구축하는 것이 아니라, Local File System 기반으로 레이크하우스 구조를 실습한다.  
후반부에는 MinIO/S3 호환 구조로 확장할 수 있도록 폴더와 파티션 기준을 맞춘다.

##### 권장 폴더 구조
```text
project-root/
  collector/
  schemas/
  sample_events/
  seed/
  docs/
  data_lake/
    raw/
    staging/
    mart/
    dead_letter/
    _metadata/
```

##### Raw Zone

Raw Zone은 원본 데이터를 최대한 그대로 보존하는 영역이다.
```text
data_lake/
  raw/
    gas_events/date=YYYY-MM-DD/hour=HH/
    power_events/date=YYYY-MM-DD/hour=HH/
    worker_location_events/date=YYYY-MM-DD/hour=HH/
    ai_service_logs/date=YYYY-MM-DD/hour=HH/
    rag_document_metadata/date=YYYY-MM-DD/
    feedback_logs/date=YYYY-MM-DD/hour=HH/
```

Raw Zone의 원칙은 다음과 같다.
```text
원본 데이터를 임의로 고치지 않는다.
수집 시점과 발생 시점을 함께 남긴다.
event_id와 schema_version을 반드시 남긴다.
나중에 재처리할 수 있도록 저장한다.
```

##### Dead Letter

Dead Letter는 처리할 수 없는 데이터를 보관하는 영역이다.
```text
data_lake/
  dead_letter/
    validation_errors/
    schema_errors/
    unsupported_version/
    duplicate_events/
    unknown_event_type/
```

Dead Letter를 만드는 이유는 다음과 같다.
```text
잘못된 데이터를 버리지 않는다.
어떤 데이터가 왜 실패했는지 추적한다.
스키마 수정 후 재처리할 수 있다.
데이터 품질 리포트의 근거로 사용한다.
```

##### Staging Zone

Staging은 Raw 데이터를 검증하고 분석 가능한 구조로 정리한 영역이다.
```text
data_lake/
  staging/
    gas_measurements/
    power_measurements/
    worker_locations/
    ai_service_logs/
    rag_document_metadata/
    feedback_events/
```

2단계에서는 Staging 파일을 일부 샘플로만 생성하고, 본격적인 자동 변환은 3단계 Airflow에서 진행한다.

##### Mart Zone

Mart는 AI, RAG, 대시보드, 운영 리포트에서 사용하기 좋게 목적별로 가공한 데이터셋이다.
```text
data_lake/
  mart/
    current_sensor_status/
    risk_status/
    alarm_summary/
    ai_training_dataset/
    rag_document_index/
    feedback_summary/
    quality_summary/
```

2단계에서는 Mart의 설계와 폴더 기준을 잡고, 실제 Mart 자동 생성은 3단계에서 구현한다.

#### 2.12 PostgreSQL 기준정보 설계

2단계에서 PostgreSQL은 모든 이벤트를 다 저장하는 주 저장소라기보다, 기준정보와 운영 메타데이터를 관리하는 용도로 사용한다.

권장 기준정보 테이블은 다음과 같다.
```text
sensors
power_devices
workers
zones
geofences
gas_thresholds
power_thresholds
event_schema_versions
```

기준정보가 필요한 이유
```text
센서 이벤트의 sensor_id가 실제 등록된 센서인지 확인한다.
작업자 위치 이벤트의 worker_id가 유효한지 확인한다.
zone_id와 위험구역 기준을 연결한다.
가스별 임계치를 코드가 아니라 데이터로 관리한다.
schema_version별 필드 변경 이력을 관리한다.
```

#### 2.15 데이터 엔지니어링 디자인 패턴 적용

2단계에서는 데이터 수집, 오류 관리, 스토리지, 품질 패턴을 가볍게 적용한다.

| 패턴 영역 | 적용 패턴 | 2단계 적용 방식 |

| 데이터 수집 | 외부 트리거 | 시뮬레이터나 API 요청으로 이벤트 수집 시작 |
| 오류 관리 | 데드 레터 | 검증 실패 데이터를 버리지 않고 별도 저장 |
| 오류 관리 | 필터 인터셉터 | 필수 필드 누락, 잘못된 schema_version 데이터 차단 |
| 스토리지 | 수평 파티셔너 | 날짜와 시간 기준으로 Raw 파일 분리 |
| 스토리지 | 정규화기 | sensors, workers, zones, thresholds 기준정보 정리 |
| 품질 | 제약 조건 적용자 | 필수값, 타입, 단위, 범위 검증 |
| 품질 | 스키마 호환성 적용자 | schema_version으로 변경 관리 |
