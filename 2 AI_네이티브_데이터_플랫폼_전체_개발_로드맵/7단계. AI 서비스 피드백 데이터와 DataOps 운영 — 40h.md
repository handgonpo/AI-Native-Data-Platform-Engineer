#### 7.1 교과목 목표

이 과목의 목표는 AI 서비스 운영 과정에서 발생하는 **사용자 피드백, 운영자 피드백, AI 추론 로그, RAG 검색 로그, 오류 로그, 운영 지표를 수집하고, 이를 DataOps 관점에서 관찰·분석·개선 데이터로 전환하는 구조**를 이해하고 구현하는 것이다.

1단계에서는 AI 서비스와 데이터 플랫폼의 전체 아키텍처를 정의했다.  
2단계에서는 데이터를 수집하고 Raw Zone, Dead Letter, Data Contract 구조를 만들었다.  
3단계에서는 Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환하는 Airflow 파이프라인을 만들었다.  
4단계에서는 Kafka/Spark 기반 실시간 이벤트 처리와 WebSocket 대시보드 연결을 만들었다.  
5단계에서는 데이터 품질, 계보, 거버넌스 기준을 만들었다.  
6단계에서는 산업안전 문서를 RAG 검색이 가능한 벡터 데이터 파이프라인으로 변환했다.

7단계에서는 지금까지 만든 AI 데이터 플랫폼이 운영 중에도 개선될 수 있도록, **피드백 데이터와 DataOps 운영 구조**를 만든다.

AI 서비스는 한 번 만들고 끝나는 시스템이 아니다.  
운영 중에는 오탐, 정탐, 미탐, AI 추론 실패, RAG 검색 실패, 출처 없는 답변, 사용자 재질문, 데이터 품질 실패, 수집 지연, 대시보드 반영 지연이 계속 발생할 수 있다.  
이러한 운영 결과를 데이터로 남기지 않으면 AI 서비스는 개선될 수 없다.

따라서 이 과목에서는 다음을 학습한다.
```text
피드백 데이터란 무엇인가?
오탐, 정탐, 미탐은 어떻게 구분하는가?
AI 추론 로그는 왜 저장해야 하는가?
RAG 검색 로그와 RAG 답변 피드백은 왜 필요한가?
운영 로그는 단순 장애 로그가 아니라 왜 개선 데이터인가?
재학습 후보 데이터셋은 어떤 기준으로 만드는가?
DataOps란 무엇인가?
데이터 플랫폼 운영 지표는 무엇을 봐야 하는가?
Prometheus와 Grafana는 어떤 역할을 하는가?
SLA, SLI, SLO는 무엇인가?
Celery와 Redis는 비동기 작업에서 어떤 역할을 하는가?
Docker Compose는 여러 서비스를 함께 실행할 때 왜 필요한가?
GitHub Actions는 데이터 플랫폼 운영 신뢰성과 어떻게 연결되는가?
```

산업안전 관제플랫폼 실습에서는 알람 확인, 오탐/정탐/미탐 피드백, RAG 답변 평가, AI 추론 결과 평가, 사용자 재질문, 실패 케이스, 운영 지표를 수집하고, 이를 재학습 후보 데이터셋과 DataOps 모니터링으로 연결한다.

#### 7.2 이 과목의 위치

7단계는 1단계부터 6단계까지 만든 데이터 플랫폼을 운영 가능한 구조로 정리하는 마지막 이론/실습 단계이다.
```text
1단계: 어떤 데이터를 다룰지와 전체 구조를 정의한다.
→ 2단계: 데이터를 수집하고 Raw Zone에 저장한다.
→ 3단계: Raw 데이터를 Staging, Mart, AI Training Dataset으로 자동 변환한다.
→ 4단계: 실시간 이벤트를 Kafka/Spark로 처리하고 Dashboard에 연결한다.
→ 5단계: 데이터 품질, 계보, 거버넌스 기준을 적용한다.
→ 6단계: 산업안전 문서를 RAG 벡터 데이터 파이프라인으로 변환한다.
→ 7단계: 피드백 데이터와 운영 로그를 DataOps 구조로 연결한다.
```

7단계는 새로운 기능을 무리하게 많이 추가하는 단계가 아니다.  
앞에서 만든 데이터 수집, 파이프라인, 실시간 처리, 품질 관리, RAG 검색 구조가 운영 중에 어떻게 관찰되고 개선되는지 확인하는 단계이다.

즉, 7단계는 다음 질문에 답하는 단계이다.
```text
AI 서비스가 틀렸을 때 그 사실을 어떻게 알 수 있는가?
운영자가 남긴 피드백은 어떻게 데이터로 저장되는가?
RAG 답변이 부정확했을 때 어떤 로그와 피드백을 남기는가?
반복되는 실패 케이스는 어떻게 재학습 후보가 되는가?
데이터 흐름이 멈추거나 지연되면 어떻게 관찰하는가?
운영 지표를 통해 서비스 개선 포인트를 어떻게 찾는가?
```

#### 7.3 핵심 질문

```text
AI 서비스가 운영 중에 틀리거나 실패했을 때,
그 결과를 어떻게 데이터로 남기고,

```

이 질문을 다음 관점으로 나누어 이해한다.
```text
피드백 관점:
운영자와 사용자는 어떤 피드백을 남길 수 있는가?

정답 관리 관점:
오탐, 정탐, 미탐은 어떤 기준으로 구분할 것인가?

AI 로그 관점:
AI 추론 요청, 응답, 실패, latency는 어떻게 저장할 것인가?

RAG 로그 관점:
검색 질문, 검색된 문서, 출처, 답변, 사용자 평가는 어떻게 기록할 것인가?

재학습 관점:
어떤 피드백과 실패 케이스를 재학습 후보 데이터셋으로 만들 것인가?

운영 지표 관점:
수집 지연, 처리 실패, 품질 실패, 추론 실패, RAG 실패를 어떤 Metric으로 볼 것인가?

모니터링 관점:
Prometheus와 Grafana로 무엇을 관찰할 것인가?

자동화 관점:
반복 작업과 리포트 생성을 Airflow, Celery, GitHub Actions와 어떻게 연결할 것인가?

운영 안정성 관점:
Docker Compose로 여러 서비스를 함께 실행하고 기본 CI로 오류를 조기에 발견하는 이유는 무엇인가?
```

#### 7.6 수업 운영 방식

7단계는 총 40시간이며, 5일 × 8시간 구조로 운영한다.
```text
하루 8시간
= 범용 이론 3시간
+ 미니 실습과 질문 답변
+ 산업안전 관제플랫폼 응용 실습 5시간
```

수업 순서는 다음을 기준으로 한다.
```text
범용 이론 설명
→ 간단한 미니 실습
→ 이해도 점검 질문
→ 산업안전 관제플랫폼 응용 실습
→ 코드/데이터/문서 산출물 정리
```

7단계는 운영 도구를 모두 깊게 배우는 시간이 아니다.  
핵심은 **AI 서비스의 운영 결과를 데이터로 남기고, 그 데이터를 다시 개선과 모니터링으로 연결하는 구조**를 이해하는 것이다.

따라서 수업은 다음 순서로 진행한다.
```text
피드백 데이터 구조 설계
→ 피드백 API 작성
→ AI/RAG 로그 저장
→ 실패 케이스 분류
→ 재학습 후보 데이터셋 생성
→ DataOps Metric 정의
→ Prometheus/Grafana 연결
→ Docker Compose와 CI 기본 정리
```

```text
sensor_noise

```

#### 7.10 오탐, 정탐, 미탐 기준

AI 관제 서비스에서 피드백을 분석하려면 오탐, 정탐, 미탐 기준이 필요하다.

##### 정탐
```text
시스템이 위험이라고 판단했고,
운영자가 실제 위험 또는 주의 상황이라고 확인한 경우
```

##### 오탐
```text
시스템이 위험이라고 판단했지만,
운영자가 실제 위험이 아니라고 확인한 경우
```

##### 미탐
```text
시스템은 위험을 감지하지 못했지만,
운영자 또는 사후 확인 결과 실제 위험 상황이 있었던 경우
```

##### 산업안전 예시

| 구분 | 상황 | 피드백 |
|---|---|---|
| 정탐 | CO 농도 상승 알람이 발생했고 실제 현장에서 환기 조치가 필요했다 | `true_positive` |
| 오탐 | 센서 노이즈로 가스 알람이 발생했지만 실제 위험은 없었다 | `false_positive` |
| 미탐 | 시스템은 normal로 판단했지만 작업자가 위험구역에 오래 머물렀다 | `false_negative` |
| 검토 필요 | 데이터 품질 문제로 판단 결과를 확정할 수 없다 | `needs_review` |

#### 7.11 RAG 피드백 데이터 설계

RAG 답변은 사용자가 도움이 되었다고 느꼈는지, 출처가 맞았는지, 필요한 정보가 누락되지 않았는지 확인해야 한다.

##### RAG 답변 피드백 필드
```text
rag_feedback_id
query_id
answer_id
trace_id
user_id
user_role
rating
is_helpful
missing_information
wrong_source
outdated_document
comment
```

#### 7.16 SLA, SLI, SLO 기준

초보자는 SLA, SLI, SLO를 어렵게 느낄 수 있다.  
간단히 말하면 다음과 같다.

```text
SLI:
실제로 측정하는 지표

SLO:
목표로 삼는 기준

SLA:
외부 또는 고객에게 약속하는 수준
```

##### 산업안전 관제플랫폼 예시

| 구분 | 예시 |
|---|---|
| SLI | 센서 이벤트 수집 지연 시간 |
| SLO | 95% 이벤트를 5초 이내 처리 |
| SLA | 관제 서비스가 업무 시간 중 99% 이상 정상 동작 |

##### 수업에서 사용할 SLO 예시
```text
센서 이벤트는 5초 이내 Raw에 저장된다.
위험 이벤트는 10초 이내 Dashboard에 반영된다.
RAG 검색 응답은 3초 이내 반환된다.
Dead Letter 비율은 전체 이벤트의 5% 이하로 유지한다.
AI 추론 실패율은 2% 이하로 유지한다.
```

#### 7.22 데이터 엔지니어링 디자인 패턴 적용

7단계에서는 데이터 관찰 가능성, 데이터 흐름, 데이터 가치, 보안 패턴을 중심으로 적용한다.  
패턴을 암기하는 것이 목적이 아니라, 운영 중 발생하는 결과를 어떻게 다시 데이터 개선 사이클로 연결하는지 이해하는 것이 목적이다.

| 패턴 영역 | 적용 패턴 | 7단계 적용 방식 |
|---|---|---|
| 데이터 관찰 가능성 | 흐름 중단 탐지기 | 일정 시간 센서 이벤트가 없으면 수집 중단으로 판단 |
| 데이터 관찰 가능성 | 스큐 탐지기 | 특정 센서나 구역 데이터가 과도하게 많거나 적은지 탐지 |
| 데이터 관찰 가능성 | 지연 탐지기 | event_time과 ingestion_time 차이를 모니터링 |
| 데이터 관찰 가능성 | SLA 위반 탐지기 | 수집, 판단, 대시보드 표시 시간이 기준을 넘는지 추적 |
| 데이터 관찰 가능성 | 데이터셋 추적기 | Raw, Staging, Mart, AI 결과, RAG Index 생성 상태 추적 |
| 데이터 관찰 가능성 | 세밀한 추적기 | 특정 event_id가 Raw에서 Dashboard까지 이동한 경로 추적 |
| 데이터 흐름 | 병렬 분할 | 피드백 데이터를 운영 리포트, 재학습 후보, 품질 개선으로 분기 |
| 데이터 가치 | 메타데이터 데코레이터 | 피드백 데이터에 alarm_id, trace_id, model_version, source를 추가 |
| 데이터 보안 | 비밀 없는 커넥터 | 코드에 비밀값을 두지 않고 환경변수와 Secret으로 연결 |
| 데이터 품질 | 오프라인 옵서버 | 일별 운영 리포트와 품질 리포트 생성 |

#### 7.25 7단계에서 하지 않는 것

7단계는 피드백 데이터와 DataOps 운영 구조를 만드는 단계이다.  
다음 작업은 후속 프로젝트 또는 기업 프로젝트에서 확장할 수 있다.
```text
실제 운영 수준의 Kubernetes 배포까지 확장하지 않기
모델 자동 재학습 전체 파이프라인 완성하지 않기
복잡한 MLflow 모델 레지스트리까지 깊게 구현하지 않기
고급 보안 시스템 전체 구현하지 않기
실제 SMS, 카카오톡, 이메일 알림 연동까지 필수로 만들지 않기
대규모 클라우드 모니터링 시스템까지 확장하지 않기
운영 대시보드를 상용 서비스 수준으로 완성하려고 하지 않기
```

단, 후속 프로젝트와 연결될 수 있도록 다음 기준은 정리한다.
```text
재학습 후보 데이터셋 기준
AI/RAG 피드백 기준
운영 지표 기준
SLA/SLO 기준
Event Trace 기준
운영 리포트 기준
통합 실행 기준
```

#### 7.27 전체 과정과의 연결

7단계의 결과물은 전체 이론/실습 교과목의 마지막 정리 기준이 된다.
```text
1단계 결과물:
AI 서비스와 데이터 플랫폼 아키텍처

2단계 결과물:
Data Contract, Collector API, Raw Zone, Dead Letter

3단계 결과물:
Staging, Mart, AI Training Dataset, Airflow Pipeline

4단계 결과물:
Kafka/Spark 실시간 이벤트, Risk Event, WebSocket Dashboard

5단계 결과물:
Data Quality, Lineage, Governance

6단계 결과물:
RAG Document Pipeline, Vector DB, Source Citation

7단계 결과물:
Feedback Data, Retraining Candidate, DataOps Metric, Operation Report
```

7단계가 끝나면 전체 흐름은 다음과 같이 정리된다.
```text
센서/로그/문서/피드백 데이터 수집
→ Raw 저장
→ Staging 검증
→ Mart 생성
→ 실시간 위험 판단
→ RAG 대응 매뉴얼 검색
→ 대시보드 표시
→ 운영자 피드백 수집
→ 품질/운영 지표 관찰
→ 재학습 후보 데이터셋 생성
→ 운영 리포트와 개선 기준 도출
```

따라서 7단계의 핵심은 다음 한 문장으로 정리할 수 있다.
```text
7단계는 AI 서비스 운영 중 발생하는 결과를 피드백 데이터와 운영 지표로 수집하고,
이를 재학습 후보 데이터셋과 DataOps 모니터링으로 연결하여
AI 데이터 플랫폼이 계속 개선될 수 있는 구조를 만드는 단계이다.
```
